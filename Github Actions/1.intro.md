# GitHub Actions Quick Notes

## 1) What is a workflow file?

A **workflow file** is a YAML file in a GitHub repository that defines an automated process using GitHub Actions.

It tells GitHub Actions:

- **when** to run
- **what** jobs to run
- **what** steps each job should perform
- **which runner** should execute the jobs

Workflow files are usually stored in:

```bash
.github/workflows/
```

They typically use the `.yml` or `.yaml` extension.

Example:

```yaml
name: CI Pipeline

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Check out code
        uses: actions/checkout@v4

      - name: Run a command
        run: echo "Hello from GitHub Actions"
```

### Main parts of a workflow file

- `name:` gives the workflow a readable name
- `on:` defines the event(s) that trigger the workflow
- `jobs:` contains one or more jobs
- `runs-on:` defines the runner used for a job
- `steps:` lists the tasks inside a job
- `uses:` runs a reusable action
- `run:` executes shell commands

---

## 2) Difference between workflow, job, step, action, runner, and event

### Event
An **event** is something that happens in the repository that triggers automation.

Examples:
- push
- pull request
- issue labeled
- scheduled time

### Workflow
A **workflow** is the complete automation process defined in one YAML file.

A workflow contains one or more jobs.

### Job
A **job** is a group of steps that run together on the same runner.

A workflow can have multiple jobs.

### Step
A **step** is a single task inside a job.

A step can:
- run a shell command using `run:`
- use a reusable action using `uses:`

### Action
An **action** is a reusable unit of automation that performs a specific task.

Examples:
- checking out code
- setting up a programming language
- uploading artifacts
- deploying an app

### Runner
A **runner** is the server or machine that executes a job.

Examples:
- `ubuntu-latest`
- `windows-latest`
- `macos-latest`

### Simple hierarchy

```text
Event -> Workflow -> Job -> Step
                    -> runs on Runner
                    -> may use Action
```

---

## 3) What is an action exactly?

An **action** is a reusable component in GitHub Actions that performs a specific task.

Instead of writing all logic manually, you can use an action that already knows how to do something common.

Example:

```yaml
steps:
  - name: Check out repository
    uses: actions/checkout@v4
```

Here, `actions/checkout@v4` is an action.

It checks out your repository code so the workflow can access the files.

### `uses` vs `run`

- `uses:` means use a prebuilt action
- `run:` means execute your own shell command

Example:

```yaml
steps:
  - uses: actions/checkout@v4
  - run: python app.py
```

### Why actions are useful

- reduce repeated work
- simplify workflows
- reuse tested automation
- make complex tasks easier

### Types of actions

- GitHub official actions
- community actions
- custom actions you create yourself

---

## 4) What is a workflow run?

A **workflow run** is one actual execution of a workflow after it is triggered by an event.

### Important difference

- **workflow** = the YAML definition
- **workflow run** = one execution of that workflow

Example:

If a workflow is triggered on every push, and you push code 5 times, then GitHub creates **5 workflow runs**.

### Analogy

- recipe = workflow
- cooking it one time = workflow run

### What happens during a workflow run?

- GitHub detects an event
- the workflow starts
- jobs are created
- each job runs its steps on a runner
- GitHub records success, failure, or cancellation

Example:

```yaml
on:
  push:
    branches: [main]
```

Every push to `main` creates a new workflow run.

### Why workflow runs matter

- you can inspect logs
- you can see which job failed
- you can track automation history
- you can rerun jobs or workflows in some cases

### Flow

```text
Event -> Workflow Run -> Jobs -> Steps -> Result
```

## 5) How to make one job depend on another job

To make one job wait for another, use the `needs` keyword.

Example:

```yaml
name: Build then Test

on:
  push:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Building app"

  test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: echo "Testing app"
```

### What this means

- `build` runs first
- `test` waits for `build`
- if `build` fails, `test` usually does not run

### Multiple dependencies

A job can depend on more than one job.

```yaml
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Linting"

  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Building"

  deploy:
    needs: [lint, build]
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying"
```

Here:
- `lint` and `build` can run in parallel
- `deploy` starts only after both finish successfully

### Rule of thumb

- no `needs` -> jobs may run in parallel
- with `needs` -> jobs follow dependency order

## 6) Full example combining everything

```yaml
name: CI Example

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Check out code
        uses: actions/checkout@v4

      - name: Build project
        run: echo "Building project"

  test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - name: Check out code
        uses: actions/checkout@v4

      - name: Run tests
        run: echo "Running tests"

  deploy:
    needs: [build, test]
    runs-on: ubuntu-latest
    steps:
      - name: Deploy app
        run: echo "Deploying app"
```

### What happens here

1. A `push` to `main` or a `pull_request` triggers the workflow
2. GitHub starts a **workflow run**
3. The `build` job runs first
4. The `test` job waits for `build`
5. The `deploy` job waits for both `build` and `test`
6. Each job runs on a runner
7. Each job executes its steps in order

---

## 7) Quick summary

- A **workflow file** is the YAML file that defines automation
- An **event** triggers the workflow
- A **workflow run** is one execution of the workflow
- A **job** is a group of steps
- A **step** is a single task
- An **action** is a reusable automation component used in a step
- A **runner** is the machine that executes the job
- `needs` is used to make one job depend on another
