Here's a comprehensive guide to passing environment variables in Docker — covering **what** they are, **why** you'd use each method, and **how** to implement them.

---

## What are Environment Variables?

Think of environment variables like **sticky notes attached to a running program**. They tell the program things like "use this database address" or "run in production mode" — without you having to hardcode those values into the program itself.

For example, instead of writing `db_host = "192.168.1.5"` inside your code, you write `db_host = os.getenv("DB_HOST")` and then *tell Docker* what `DB_HOST` should be at runtime.

**Why is this powerful?** Because the same Docker image can run in development, staging, or production just by changing the environment variables — no code changes needed.

## Method 1 — `ENV` in Dockerfile

### What?
You hardcode the default value of an environment variable *inside* the image itself when you build it.

### Why?
Use this for **non-sensitive defaults** that rarely change — like setting the language locale, default port, or application mode. Anyone pulling your image gets sensible defaults out of the box.

### How?

```dockerfile
# Dockerfile
FROM python:3.11-slim

# Set default environment variables baked into the image
ENV APP_ENV=development
ENV PORT=8080
ENV LOG_LEVEL=info

WORKDIR /app
COPY app.py .

CMD ["python", "app.py"]
```

```python
# app.py — your application reads them
import os

app_env   = os.getenv("APP_ENV",   "development")
port      = int(os.getenv("PORT",  "8080"))
log_level = os.getenv("LOG_LEVEL", "info")

print(f"Running in {app_env} mode on port {port} with log level {log_level}")
```

**Build and run:**
```bash
docker build -t my-app .
docker run my-app
# Output: Running in development mode on port 8080 with log level info
```

**Key rule:** Values set here can still be *overridden* at runtime using any of the other methods below. Think of `ENV` as "the fallback if nobody says otherwise."

---

## Method 2 — `-e` flag with `docker run`

### What?
You pass individual environment variables directly on the command line when starting a container.

### Why?
Perfect for **quick testing**, one-off overrides, or CI/CD pipelines where values are available as shell variables. No files to manage.

### How?

```bash
# Pass values directly as key=value
docker run \
  -e APP_ENV=production \
  -e DB_HOST=192.168.1.100 \
  -e DB_PORT=5432 \
  my-app

# Or inherit a variable from YOUR terminal's environment
export SECRET_KEY="supersecret123"
docker run -e SECRET_KEY my-app   # Docker reads it from your shell automatically
```

```python
# app.py — no change needed, reads same way
import os

db_host    = os.getenv("DB_HOST")
db_port    = os.getenv("DB_PORT")
secret_key = os.getenv("SECRET_KEY")

print(f"Connecting to DB at {db_host}:{db_port}")
```

**Key rule:** `-e` values override anything set in the Dockerfile's `ENV`. Think of it as a sticky note on top of the default sticky note.

## Method 3 — `.env` file (auto-loaded by Docker Compose)

### What?
A plain text file named `.env` that lives in the same folder as your `docker-compose.yml`. Docker Compose automatically reads it — you don't have to reference it explicitly.

### Why?
This is the **most common real-world approach** for local development. You keep all your dev secrets in one tidy file, keep it out of Git (add `.env` to `.gitignore`), and Compose handles the rest.

### How?

```bash
# .env  (this file is auto-detected by Docker Compose)
APP_ENV=development
DB_HOST=localhost
DB_PORT=5432
DB_PASSWORD=mydevpassword
SECRET_KEY=dev-secret-key-123
```

```yaml
# docker-compose.yml
version: "3.8"

services:
  app:
    build: .
    ports:
      - "8080:8080"
    environment:
      - APP_ENV          # ← pulls value from .env file
      - DB_HOST          # ← pulls value from .env file
      - DB_PORT          # ← pulls value from .env file
      - DB_PASSWORD      # ← pulls value from .env file
      - SECRET_KEY       # ← pulls value from .env file
```

```bash
# Just run this — Compose finds .env automatically
docker compose up
```

**Key rule:** Add `.env` to your `.gitignore` so passwords and keys never get committed to source control. Instead, commit a `.env.example` file with fake placeholder values so teammates know what variables are needed.

## Method 4 — `--env-file` flag

### What?
You explicitly point `docker run` (or `docker compose`) at a specific file containing variables, instead of relying on the auto-detection of `.env`.

### Why?
Use this when you have **multiple environment files** for different scenarios — like `dev.env`, `staging.env`, and `prod.env`. You choose which one to load each time.

### How?

**Your env files:**
```bash
# dev.env
APP_ENV=development
DB_HOST=localhost
DB_PASSWORD=devpassword

# prod.env
APP_ENV=production
DB_HOST=db.myapp.com
DB_PASSWORD=superSecureProdPassword!
```

**Run with a specific env file:**
```bash
# For development
docker run --env-file dev.env my-app

# For production (same image, different config!)
docker run --env-file prod.env my-app
```

**With Docker Compose:**
```yaml
# docker-compose.yml
version: "3.8"

services:
  app:
    build: .
    env_file:
      - prod.env        # explicitly named file
```

**Key rule:** This is the method that best demonstrates Docker's power — **one image, many configurations**. The same Docker image runs identically in dev and prod; only the env file changes.

## Method 5 — `environment:` in Docker Compose YAML

### What?
You list variables and their values directly inside `docker-compose.yml`, under the `environment:` key.

### Why?
Good for **non-sensitive, config-level variables** that are project-specific and okay to live in source control. Also great for mixing hardcoded values with variables pulled from `.env`.

### How?

```yaml
# docker-compose.yml
version: "3.8"

services:
  web:
    build: .
    ports:
      - "8080:8080"
    environment:
      # Hardcoded values directly in the YAML
      APP_ENV: production
      LOG_LEVEL: info
      MAX_CONNECTIONS: 100

      # Pull sensitive values from .env (value stays out of YAML)
      DB_PASSWORD: ${DB_PASSWORD}
      SECRET_KEY: ${SECRET_KEY}

  db:
    image: postgres:15
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: ${DB_PASSWORD}   # same .env variable reused
```

```bash
# .env  (only sensitive values needed here now)
DB_PASSWORD=superSecurePassword!
SECRET_KEY=my-secret-key-xyz
```

```bash
docker compose up
```

Notice the `${DB_PASSWORD}` syntax — this is called **variable substitution**. Docker Compose reads the value from your `.env` file and injects it into the YAML at runtime. The password never literally appears in the YAML file.

---

## Comparison at a glance

| Method | Best for | Committed to Git? | Overrides Dockerfile? |
|---|---|---|---|
| `ENV` in Dockerfile | Safe defaults | Yes | No (it IS the default) |
| `docker run -e` | Quick tests, CI/CD | No | Yes |
| `.env` file (auto) | Local dev secrets | **No** | Yes |
| `--env-file` flag | Multi-environment setups | **No** | Yes |
| `environment:` in Compose | Non-sensitive config | Yes (hardcoded values) | Yes |

---

## A complete real-world example combining all of this

Here's how a professional project typically uses all methods together:

```dockerfile
# Dockerfile — safe, non-sensitive defaults only
FROM node:20-slim
ENV NODE_ENV=development
ENV PORT=3000
WORKDIR /app
COPY . .
RUN npm install
CMD ["node", "server.js"]
```

```bash
# .env — local secrets, NEVER committed to Git
DB_PASSWORD=devpassword123
JWT_SECRET=dev-jwt-secret
REDIS_URL=redis://localhost:6379
```

```yaml
# docker-compose.yml — committed to Git
version: "3.8"
services:
  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      NODE_ENV: development       # safe to hardcode, it's just config
      LOG_LEVEL: debug            # safe to hardcode
      DB_PASSWORD: ${DB_PASSWORD} # pulled from .env
      JWT_SECRET: ${JWT_SECRET}   # pulled from .env
```

```javascript
// server.js — your app reads variables the same way regardless of source
const dbPassword = process.env.DB_PASSWORD;
const jwtSecret  = process.env.JWT_SECRET;
const port       = process.env.PORT || 3000;

console.log(`Server starting on port ${port} in ${process.env.NODE_ENV} mode`);
```

The golden rule: **separate config from code, and separate secrets from config.** Environment variables are the mechanism Docker provides to do exactly that.
