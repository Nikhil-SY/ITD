## Docker `COPY` vs `ADD` — What, Why, and How

Before diving in, imagine Docker as a **recipe-making process**. When you cook, you bring ingredients from your kitchen shelf (your computer) into the pot (the Docker container). `COPY` and `ADD` are the two ways Docker lets you do exactly that — bring files from your machine into the container image being built.

---

### What is `COPY`?

`COPY` is the **simple, straightforward instruction** that copies files or folders from your local machine (the "build context") into the Docker image. Nothing more, nothing less.

```dockerfile
COPY <source> <destination>
COPY index.html /usr/share/nginx/html/
```

### What is `ADD`?

`ADD` does everything `COPY` does, **plus two bonus superpowers**:

1. It can **automatically extract `.tar` archives** into the container.
2. It can **download files from a URL** directly into the container.

```dockerfile
ADD <source> <destination>
ADD myapp.tar.gz /opt/myapp/       # extracts the tar automatically
ADD https://example.com/file.txt /tmp/  # downloads from internet
```

---

### Why do both exist?

`COPY` was introduced *after* `ADD` because the Docker team felt `ADD` was doing too much — its behaviour was unpredictable and surprising. If you just want to copy a local file, `COPY` makes your intent clear. If you use `ADD` just to copy a plain file, a teammate reading the Dockerfile might wonder "does this URL do something? does this get auto-extracted?" — it's confusing.

The golden rule: **use `COPY` by default. Use `ADD` only when you need the tar-extraction feature.**

### Real-world examples with full context

**Example 1 — Simple web app (use `COPY`)**

```dockerfile
# Start from an nginx base image
FROM nginx:latest

# Copy your local HTML file into the nginx web folder inside the container
COPY index.html /usr/share/nginx/html/index.html

# Copy an entire folder
COPY ./static/ /usr/share/nginx/html/static/
```

Why `COPY` here? You're just moving plain files. Simple, readable, no surprises.

---

**Example 2 — Installing a pre-built binary from a tar archive (use `ADD`)**

```dockerfile
FROM ubuntu:22.04

# ADD will automatically extract this .tar.gz into /opt/myapp/
ADD myapp-1.0.tar.gz /opt/myapp/

CMD ["/opt/myapp/start.sh"]
```

Without `ADD`, you'd need two steps: `COPY` the tar file, then `RUN tar -xzf` to extract it. `ADD` saves you a step here — but only use it when this extraction behaviour is what you actually want.

---

**Example 3 — Downloading from a URL (avoid `ADD`, prefer `RUN curl`)**

```dockerfile
# ❌ Works but considered bad practice:
ADD https://example.com/config.json /app/config.json

# ✅ Better — intent is clear, and you can chain cleanup:
RUN curl -o /app/config.json https://example.com/config.json
```

Why avoid `ADD` for URLs? It offers no caching control, no error handling, and the Dockerfile becomes harder to understand. Using `RUN curl` or `RUN wget` is explicit and lets you chain commands (e.g. verify a checksum right after downloading).

---

### Quick summary

| Feature | `COPY` | `ADD` |
|---|---|---|
| Copy local files | ✅ Yes | ✅ Yes |
| Copy local folders | ✅ Yes | ✅ Yes |
| Download from URL | ✗ No | ✅ Yes (avoid it) |
| Auto-extract `.tar.gz` | ✗ No | ✅ Yes |
| Recommended default | ✅ **Yes** | Only for tar extraction |

The Dockerfile documentation itself recommends `COPY` over `ADD` whenever possible — because explicit is better than implicit. When someone reads your Dockerfile, `COPY` clearly says "I'm just moving a file." `ADD` raises questions. Use each for what it's actually good at.
