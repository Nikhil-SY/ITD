## What are CMD and ENTRYPOINT?

When you run a Docker container, something has to actually *execute* inside it. `CMD` and `ENTRYPOINT` are the two Dockerfile instructions that control what that "something" is.

**CMD** answers: *"What should run by default if nobody gives me any instructions?"*

**ENTRYPOINT** answers: *"What is the one job this container always does?"*

---

## CMD — the default command

Think of `CMD` as a sticky note inside the container that says *"if you don't tell me what to do, do this."* It is completely replaceable — the moment you type something after `docker run myimage`, Docker throws away whatever `CMD` said and does what you typed instead.

```dockerfile
FROM python:3.12
CMD ["python", "app.py"]
```

Running `docker run myimage` → executes `python app.py`.
Running `docker run myimage bash` → executes `bash`. CMD is gone, fully replaced.

The `["python", "app.py"]` format (called **exec form**) is recommended because it runs the program directly without a shell wrapper, which means signals like Ctrl+C reach your app cleanly.

---

## ENTRYPOINT — the container's fixed purpose

`ENTRYPOINT` says *"this container is a Python runner"* or *"this container is an nginx server"* — it locks in the executable. Things you type after `docker run` are appended as **arguments** to that executable, not replacements.

```dockerfile
FROM python:3.12
ENTRYPOINT ["python"]
```

Running `docker run myimage app.py` → executes `python app.py`.
Running `docker run myimage --version` → executes `python --version`.
Running `docker run myimage bash` → executes `python bash` (which would fail — `bash` is treated as a filename to pass to Python).

To override it, you need to be explicit: `docker run --entrypoint bash myimage`.

---

## The best pattern: using both together

This is where the real power is. When combined, `ENTRYPOINT` sets the program and `CMD` provides its default arguments — but those arguments can be swapped easily at runtime.

```dockerfile
FROM python:3.12
ENTRYPOINT ["python"]     # always runs python
CMD        ["app.py"]     # default: run app.py
```

`docker run myimage` → `python app.py` (both combined)
`docker run myimage other.py` → `python other.py` (CMD swapped, ENTRYPOINT kept)

This pattern makes your container behave like a proper CLI tool — it has a focused purpose, a sensible default, and flexibility for users who need something slightly different.

---

## Important rule: only the last one counts

If you write `CMD` twice in a Dockerfile, only the second one applies. Docker ignores all earlier ones. Same goes for `ENTRYPOINT`. This trips people up when they inherit from a base image that already has a `CMD` or `ENTRYPOINT` — yours quietly overwrites it.

## How Docker assembles the final command

Think of Docker as having a simple assembly rule. When a container starts, Docker builds the final command like this:

```
final command = ENTRYPOINT  +  CMD
```

That's it. The two values are concatenated into a single list. Here's what that looks like concretely:

| Dockerfile says | `docker run` says | Final command |
|---|---|---|
| `ENTRYPOINT ["python"]` + `CMD ["app.py"]` | _(nothing)_ | `python app.py` |
| `ENTRYPOINT ["python"]` + `CMD ["app.py"]` | `other.py` | `python other.py` |
| `CMD ["python", "app.py"]` | _(nothing)_ | `python app.py` |
| `CMD ["python", "app.py"]` | `bash` | `bash` |

Notice the key difference in rows 2 and 4 — when you pass something at `docker run` time, it replaces `CMD` entirely but never touches `ENTRYPOINT`. That's the whole mechanism.

---

## The real-world mental model: a CLI tool

The best way to think about it is this — an `ENTRYPOINT + CMD` container behaves exactly like a command-line program:

```bash
# Your container IS python. You're just passing it arguments.
docker run myapp app.py          # like typing:  python app.py
docker run myapp --version       # like typing:  python --version
docker run myapp -c "print(1)"   # like typing:  python -c "print(1)"
```

The container's name becomes the command. The arguments you pass after `docker run myimage` become the arguments to that command. This is exactly how official images like `redis`, `nginx`, and `postgres` are built — the image name *is* the program.

---

## The shell form trap — a very common mistake

Click "Common mistake" in the widget above. When you write `ENTRYPOINT python app.py` **without square brackets**, Docker silently wraps your command in `/bin/sh -c "..."`. This causes two nasty problems:

**Problem 1 — CMD is silently ignored.** The shell receives the full string at startup. Any CMD you write, and any argument a user passes at `docker run` time, simply never arrives. No error, no warning — it just vanishes.

**Problem 2 — Signals can't reach your app.** When you run `docker stop` or press Ctrl+C, Docker sends a `SIGTERM` signal. With shell form, that signal goes to `/bin/sh`, not to your Python process. Your app never finds out it's supposed to stop, leading to a forced kill after a timeout. This is why containers sometimes take 10 seconds to stop — they're waiting for a timeout rather than cleanly shutting down.

The fix is always to use exec form (square brackets): `ENTRYPOINT ["python", "app.py"]`.

## Putting it all together — a real Dockerfile for a web API

```dockerfile
FROM python:3.12-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .

ENTRYPOINT ["python", "-m", "uvicorn"]   # always: start a uvicorn server
CMD        ["main:app", "--port", "8000"] # default: run main.py on port 8000
```

With this setup:

- `docker run myapi` → starts the server on port 8000 with `main:app`
- `docker run myapi main:app --port 9000` → same app, different port
- `docker run myapi other:app --workers 4` → different app module, 4 workers
- `docker run --entrypoint bash myapi` → debug shell for investigation

The container has a clear job (run a uvicorn server), a sensible default (your main app on 8000), and full flexibility for whoever runs it. That's the pattern worth memorising.
