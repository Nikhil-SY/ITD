# 🟢 STEP 1 — Developer Pushes Code

## What Happens?

Developer pushes code to GitHub:

```bash
git add .
git commit -m "Added payment service validation"
git push origin feature/payment
```

Then PR → merge to `main`.

## Why Important?

* Version control
* Audit trail
* Commit generates unique hash (`a34f56b`)

---

# 🟢 STEP 2 — Jenkins Triggered (CI Starts)

In Jenkins:

Webhook from GitHub triggers pipeline.

## Jenkinsfile Example

```groovy
pipeline {
  agent any

  environment {
    VERSION = "1.2.3"
    GIT_HASH = sh(script: "git rev-parse --short HEAD", returnStdout: true).trim()
  }

  stages {

    stage('Checkout') {
      steps {
        git branch: 'main', url: 'https://github.com/org/app.git'
      }
    }
```

### What Happens?

* Jenkins pulls latest code
* Captures commit hash
* Prepares workspace

# 🟢 STEP 5 — Docker Image Build

Dockerfile:

```dockerfile
FROM openjdk:17-jdk-slim
COPY target/app.jar app.jar
ENTRYPOINT ["java","-jar","/app.jar"]
```

Jenkins Stage:

```groovy
    stage('Docker Build') {
      steps {
        sh """
        docker build -t myapp:${VERSION}-${GIT_HASH} .
        """
      }
    }
```

### What Happens?

* App packaged into container
* Immutable image created
* Tagged with semantic + git hash

Example:

```
myapp:1.2.3-a34f56b
```

---

# 🟢 STEP 6 — Push to JFrog

```groovy
    stage('Push Image') {
      steps {
        sh """
        docker tag myapp:${VERSION}-${GIT_HASH} myrepo/myapp:${VERSION}-${GIT_HASH}
        docker push myrepo/myapp:${VERSION}-${GIT_HASH}
        """
      }
    }
```

Push to JFrog

### What Happens?

* Image stored securely
* Available for deployment
* Rollback possible

# 🟢 STEP 7 — Deploy to Kubernetes (CD)

Deployment.yaml:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
  template:
    spec:
      containers:
      - name: myapp
        image: myrepo/myapp:1.2.3-a34f56b
        ports:
        - containerPort: 8080
        readinessProbe:
          httpGet:
            path: /health
            port: 8080
```

Deploy:

```bash
kubectl apply -f deployment.yaml
```

# 🟢 STEP 8 — What Kubernetes Does Internally

In Kubernetes:

1. Pulls image from JFrog
2. Creates new ReplicaSet
3. Starts new pods
4. Waits for readiness probe
5. Gradually kills old pods
6. Traffic shifts automatically

This is Rolling Update.

# 🚫 First Rule: Where Secrets Should NOT Be Stored

❌ Not in source code
❌ Not in Dockerfile
❌ Not hardcoded in YAML
❌ Not in GitHub repo
❌ Not as plain text environment variables

If interviewer hears “hardcoded” → immediate red flag.

---

# 🟢 1️⃣ Secrets in GitHub (CI Trigger Level)

In GitHub:

Use:

* Repository Secrets
* Organization Secrets

Example:

* SONAR_TOKEN
* JFROG_PASSWORD

These are encrypted and injected at runtime.

---

# 🟢 2️⃣ Secrets in Jenkins (CI Stage)

In Jenkins:

Use:

* Credentials Manager
* Secret Text
* Username/Password
* SSH Key

Example in Jenkinsfile:

```groovy
withCredentials([string(credentialsId: 'sonar-token', variable: 'SONAR_TOKEN')]) {
   sh "mvn sonar:sonar -Dsonar.login=$SONAR_TOKEN"
}
```

What happens:

* Secret injected temporarily
* Not printed in logs
* Masked automatically

Best practice:

* Never echo secrets
* Use credential binding

---

# 🟢 3️⃣ Docker Level

Never pass secrets during `docker build`.

Because:

* Docker image becomes immutable
* Secret becomes part of image layer
* Anyone pulling image can extract it

Bad:

```dockerfile
ENV DB_PASSWORD=12345
```

Never do this.

---

# 🟢 4️⃣ Kubernetes Level (Runtime Secrets)

In Kubernetes:

Use Kubernetes Secret object.

Example:

```bash
kubectl create secret generic db-secret \
  --from-literal=username=admin \
  --from-literal=password=strongpass
```

YAML:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  username: YWRtaW4=
  password: c3Ryb25ncGFzcw==
```

Use in Deployment:

```yaml
env:
  - name: DB_USER
    valueFrom:
      secretKeyRef:
        name: db-secret
        key: username
```

# 🔥 Even Better (Advanced Practice)

Instead of plain Kubernetes secrets:

Use:

* External Secret Manager (AWS Secrets Manager / HashiCorp Vault)
* Sealed Secrets
* CSI Secret Store Driver

That is senior-level maturity.

# 🧠 Interview-Ready Answer (Short Version)

If interviewer asks:

> Where should secrets be stored in CI/CD?

You answer:

> Secrets should never be stored in source code or Docker images. In CI, they should be stored in Jenkins Credentials or GitHub Secrets and injected at runtime. For runtime in Kubernetes, secrets should be stored as Kubernetes Secret objects or ideally managed via external secret management solutions.

That is clean, professional, secure answer.
