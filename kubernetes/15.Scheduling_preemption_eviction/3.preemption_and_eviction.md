## Introduction

Imagine a restaurant with limited seating during peak hours. When a VIP customer arrives but all tables are full, the manager might ask regular customers to move to smaller tables to free up the best table. Similarly, Kubernetes uses **preemption** to ensure high-priority workloads get resources when needed.

**Three Key Concepts**:
1. **Preemption** = High-priority pod cancels lower-priority pods to get resources
2. **Eviction** = Pod is forcefully removed from a node (can happen due to resource pressure)
3. **Priority Classes** = Define pod importance levels

---

## Preemption: What, Why, How

### What is Preemption?

**Preemption** is the process where the Kubernetes scheduler:
1. Receives a high-priority pod that cannot be scheduled
2. Finds lower-priority pods running on nodes
3. Terminates those lower-priority pods
4. Schedules the high-priority pod in their place

```
Before Preemption          Preemption Happens        After Preemption
┌──────────────┐          ┌──────────────┐          ┌──────────────┐
│   Node-A     │          │   Node-A     │          │   Node-A     │
│ Memory: 8GB  │          │ Memory: 8GB  │          │ Memory: 8GB  │
│              │          │              │          │              │
│ ✓ Low-pri-1  │          │ ✗ Terminating│          │ HIGH-PRI-POD │
│   (2GB)      │          │   (2GB)      │          │   (2GB)      │
│ ✓ Low-pri-2  │          │ ✓ Low-pri-2  │          │ ✓ Low-pri-2  │
│   (2GB)      │          │   (2GB)      │          │   (2GB)      │
│ ✗ Available  │  High    │ ✓ Available  │          │ ✓ Available  │
│   (4GB)      │  Pri Pod │   (2GB)      │          │   (4GB)      │
│              │  Pending │              │          │              │
└──────────────┘ Request  └──────────────┘          └──────────────┘
```

---

### Why Use Preemption?

| Scenario | Reason |
|----------|--------|
| **SLA Protection** | Ensure critical workloads (databases, APIs) always get resources |
| **Cost Optimization** | Run low-priority batch jobs; evict them for important work |
| **Multi-tenant Clusters** | Prevent one team's workload from blocking another's |
| **Mission-Critical Tasks** | Guarantee real-time systems can run when needed |
| **Resource Fairness** | Give important work priority over experiments/dev |

---

### How Preemption Works: Technical Flow

```
Step 1: Pod Created with High Priority
         ↓
Step 2: Scheduler Tries to Schedule Pod
         ↓
Step 3: Pod Cannot Fit on Any Node
         ↓
Step 4: Scheduler Looks for Preemption Victims
         (Find lower-priority pods on nodes with free space if victim removed)
         ↓
Step 5: Find Best Victim Candidate
         (Lowest priority + least disruptive)
         ↓
Step 6: Evict Victim Pod(s)
         (Send SIGTERM, wait grace period, force delete if needed)
         ↓
Step 7: Schedule High-Priority Pod
         ↓
Step 8: Victim Pod's Controller Creates Replacement
         (If it has a Deployment/ReplicaSet)
         ↓
Step 9: New Pod Starts on Another Node
```

---

### Key Preemption Rules

**Rule 1: Priority Difference Required**
```
High-priority pod can only preempt lower-priority pods
If priorities are similar → No preemption
```

**Rule 2: Resource Availability**
```
Preemption only happens if evicting victims creates space
Cannot preempt just to get "nicer" nodes
```

**Rule 3: Disruption Budget Respected**
```
If victim has PodDisruptionBudget (PDB) → Preemption respects it
Cannot preempt if it violates PDB constraints
```

**Rule 4: Graceful Termination**
```
Victim pod gets grace period (default 30 seconds)
Time to shut down cleanly, save state, etc.
```

## Priority Classes: What, Why, How

### What are Priority Classes?

A **PriorityClass** is a Kubernetes object that defines priority levels for pods. Think of it like airline ticket classes: First Class > Business Class > Economy Class.

**Structure**:
```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000                    # Higher number = higher priority
globalDefault: false           # Set as default for all pods?
description: "For critical system workloads"
```

---

### Why Use Priority Classes?

| Reason | Example |
|--------|---------|
| **Categorization** | System pods > App pods > Batch jobs |
| **Cluster Resource Protection** | Ensure core services always run |
| **Fair Queuing** | Prevent one user from hogging cluster |
| **Graceful Degradation** | Run less important tasks when resources allow |

---

### How Priority Classes Work

```
Comparison: No PriorityClass          With PriorityClass
┌──────────────┐                      ┌──────────────┐
│   First-In   │                      │   Priority   │
│ First-Out    │                      │    1000      │
│              │                      │              │
│ Pod-A FIFO   │ Scheduled            │ Pod-B High   │ Priority-based
│ Pod-B FIFO   │ then Pod-B when      │ Pod-A Low    │ Pod-B scheduled
│ Node: 4GB    │ resources available  │ Node: 4GB    │ first, Pod-A waits
└──────────────┘                      └──────────────┘
```

---

### Built-in Priority Classes

Kubernetes comes with system priority classes:

```bash
kubectl get priorityclasses
```

**Output**:
```
NAME                      VALUE        GLOBAL-DEFAULT
system-cluster-critical   2000000000   false
system-node-critical      2147483647   false
```

These are reserved for Kubernetes system pods:
- `system-node-critical` = kubelet, kube-proxy (highest priority)
- `system-cluster-critical` = kube-apiserver, etcd

## Eviction: What, Why, How

### What is Eviction?

**Eviction** is the process of forcefully removing a pod from a node. Unlike preemption (scheduler-initiated), eviction can be:
1. **Scheduler-initiated** = Preemption (high-priority pod needs resources)
2. **Kubelet-initiated** = Node resource pressure (out of memory, disk, etc.)
3. **API-initiated** = Manual eviction via API

---

### Why Eviction Happens

| Type | Trigger | Reason |
|------|---------|--------|
| **Scheduler Preemption** | High-priority pod pending | Resource guarantee for important work |
| **Kubelet Pressure Eviction** | Node running out of resources | Prevent node crash |
| **API Eviction** | Admin command | Manual maintenance or policy enforcement |
| **Pod Disruption Budget** | Checking if pod can be evicted | Graceful pod eviction during maintenance |

---

### Eviction Process

```
Eviction Initiated (3 Methods)
         ↓
┌─────────────────────────────────────────┐
│                                         │
├─ Scheduler Preemption                  ├─ Kubelet Resource Pressure
│  (High-pri pod pending)                │  (Memory/Disk/PID pressure)
│                                        │
├─ API Eviction                          │
│  (kubectl evict or API call)           │
│                                        │
└─────────────────────────────────────────┘
         ↓
Pod Receives SIGTERM
         ↓
Wait for Grace Period (default 30s)
         ↓
┌─────────────────────────────────────────┐
│ Pod Shuts Down Cleanly?                 │
├─ YES: Pod terminates gracefully        │
│ NO:  Force delete after grace period   │
└─────────────────────────────────────────┘
         ↓
Pod Removed from Node
         ↓
Controller (Deployment/RS) Creates Replacement
```

## Eviction Without Priority Classes

### What Happens When No Priorities Are Set?

When no PriorityClass is assigned, pods have a default priority of **0**. In this scenario:

```yaml
# Default priority = 0 for all pods
apiVersion: v1
kind: Pod
metadata:
  name: app-1
spec:
  containers:
  - name: nginx
    image: nginx:latest
  # No priorityClassName specified
  # Default priority = 0
```

---

### Eviction Order Without Priorities (FIFO-like)

When a high-priority pod (with explicit priority class) arrives and lower-priority pods exist:

```
Scenario: All pods have default priority (0)
┌─────────────────────────────────────────────────┐
│ Node Resources: 8GB Memory                       │
│                                                 │
│ Pod-A (priority: 0)  - 2GB - Running since 1h  │
│ Pod-B (priority: 0)  - 2GB - Running since 30m │
│ Pod-C (priority: 0)  - 2GB - Running since 5m  │
│ Available: 2GB                                  │
│                                                 │
│ New Pod: High-Priority (priority: 100) - 4GB   │
│ Status: PENDING (needs 4GB)                     │
└─────────────────────────────────────────────────┘

Eviction Decision WITHOUT Priorities:
├─ All pods have SAME priority (0)
├─ Scheduler looks at other factors:
│  ├─ PodQoS class (Guaranteed > Burstable > BestEffort)
│  ├─ Request vs Actual usage
│  ├─ Pod age (newer pods evicted first)
│  └─ Whether pod is managed by controller
│
└─ Result: Likely evict Pod-C (newest, lowest QoS)
          then Pod-B if more space needed
```

---

### QoS Classes (When No Priorities Set)

When priorities are equal, Kubernetes uses **Quality of Service (QoS)** classes:

| QoS Class | Definition | Eviction Priority |
|-----------|------------|-------------------|
| **Guaranteed** | Requests = Limits for CPU & Memory | 🟢 Evicted LAST |
| **Burstable** | Requests < Limits | 🟡 Evicted SECOND |
| **BestEffort** | No Requests/Limits set | 🔴 Evicted FIRST |

```yaml
# Example 1: Guaranteed QoS
apiVersion: v1
kind: Pod
metadata:
  name: guaranteed-pod
spec:
  containers:
  - name: app
    image: app:latest
    resources:
      requests:
        memory: "2Gi"
        cpu: "1"
      limits:
        memory: "2Gi"
        cpu: "1"
# Requests == Limits → GUARANTEED

---

# Example 2: Burstable QoS
apiVersion: v1
kind: Pod
metadata:
  name: burstable-pod
spec:
  containers:
  - name: app
    image: app:latest
    resources:
      requests:
        memory: "1Gi"
        cpu: "0.5"
      limits:
        memory: "2Gi"
        cpu: "1"
# Requests < Limits → BURSTABLE

---

# Example 3: BestEffort QoS
apiVersion: v1
kind: Pod
metadata:
  name: besteffort-pod
spec:
  containers:
  - name: app
    image: app:latest
    # No resources specified → BESTEFFORT
```

### 1. Scheduler (kube-scheduler)

**Role**: The traffic controller of preemption

**Responsibilities**:
- Monitors all pending pods
- Checks each pod's `priorityClassName`
- Calculates preemption victims if needed
- Terminates lower-priority pods
- Schedules high-priority pod

**Key File**: `/etc/kubernetes/manifests/kube-scheduler.yaml`

**Configuration**:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: kube-scheduler
  namespace: kube-system
spec:
  containers:
  - name: kube-scheduler
    image: k8s.gcr.io/kube-scheduler:v1.25.0
    command:
    - kube-scheduler
    - --config=/etc/kubernetes/scheduler-config.yaml
```

**How It Detects Preemption Victims**:
```
Algorithm:
1. Find all pods on candidate nodes
2. Filter pods with lower priority value
3. Calculate "disruptiveness" score:
   - Newer pods = less disruptive (evict first)
   - Pods with fewer replicas = less disruptive
   - BestEffort pods = more disruptive (evict first)
4. Select pod with highest disruptiveness
5. Send termination signal
```

---

### 2. API Server (kube-apiserver)

**Role**: The gatekeeper and record keeper

**Responsibilities**:
- Receives pod creation requests
- Validates PriorityClass exists
- Stores priority information in etcd
- Handles API-level evictions (`kubectl evict`)
- Updates pod status during termination

**Key Endpoints**:
```bash
# API endpoint for creating pods
POST /api/v1/namespaces/{namespace}/pods

# API endpoint for evictions
POST /api/v1/namespaces/{namespace}/pods/{name}/eviction

# Get pod priority
kubectl get pod POD_NAME -o jsonpath='{.spec.priorityClassName}'
```

---

### 3. Controller Manager (kube-controller-manager)

**Role**: The recovery specialist

**Responsibilities**:
- Watches pod termination events
- Detects pods created by Deployment/ReplicaSet
- Automatically creates replacement pods
- Maintains desired replica count
- Coordinates with scheduler

**Key Controllers**:
- **Deployment Controller**: Ensures N replicas exist
- **ReplicaSet Controller**: Maintains pod count
- **StatefulSet Controller**: Maintains ordered pods
- **DaemonSet Controller**: Ensures one pod per node

**Example Flow**:
```
1. Scheduler evicts pod-A (part of deployment)
2. Deployment controller notices pod-A missing
3. Creates new pod-B to maintain replica count
4. Scheduler schedules pod-B on available node
5. Pod-B starts running
```

---

### 4. Kubelet (kubelet)

**Role**: The node's personal manager

**Responsibilities**:
- Receives eviction signal from scheduler
- Monitors local node resources (memory, disk, PID)
- Triggers local evictions on pressure
- Sends SIGTERM to pod containers
- Waits for grace period
- Force-deletes if graceful shutdown fails
- Reports pod status to API server

**Resource Monitoring**:
```bash
# View kubelet configuration
cat /etc/kubernetes/kubelet.conf

# Check eviction policy
kubectl describe node NODE_NAME | grep -A 20 "Conditions\|Allocatable\|Pressure"
```

**Eviction Signals Kubelet Monitors**:
```yaml
# Memory pressure
memory.available < 100Mi

# Disk pressure
nodefs.available < 10%
nodefs.inodesFree < 5%

# PID pressure
pid.available < 100
```

---

### 5. Container Runtime

**Role**: The executor

**Responsibilities**:
- Receives SIGTERM from kubelet
- Sends signal to pod containers
- Monitors process shutdown
- Kills pod after grace period
- Cleans up resources

**Examples**: Docker, containerd, CRI-O

## Practical Examples

### Example 1: Basic Preemption Setup

**Step 1: Create Priority Classes**

```bash
# Create low-priority class
kubectl apply -f - <<EOF
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: low-priority
value: 10
description: "For background batch jobs"
EOF

# Create high-priority class
kubectl apply -f - <<EOF
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 100
description: "For critical services"
EOF

# View priority classes
kubectl get priorityclass
```

**Output**:
```
NAME                      VALUE        GLOBAL-DEFAULT
high-priority             100          false
low-priority              10           false
system-cluster-critical   2000000000   false
system-node-critical      2147483647   false
```

---

**Step 2: Create Low-Priority Pod**

```bash
kubectl apply -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: background-job
spec:
  replicas: 2
  selector:
    matchLabels:
      app: batch
  template:
    metadata:
      labels:
        app: batch
    spec:
      priorityClassName: low-priority
      containers:
      - name: processor
        image: python:3.9
        command: ["python", "-c", "import time; time.sleep(3600)"]
        resources:
          requests:
            memory: "2Gi"
            cpu: "2"
EOF

# Check pods
kubectl get pods -o wide
```

**Output**:
```
NAME                           READY   STATUS    RESTARTS   NODE
background-job-abc123         1/1     Running   0          node-1
background-job-def456         1/1     Running   0          node-2
```

---

**Step 3: Create High-Priority Pod (Will Trigger Preemption)**

```bash
kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: critical-app
spec:
  priorityClassName: high-priority
  containers:
  - name: critical
    image: nginx:latest
    resources:
      requests:
        memory: "3Gi"
        cpu: "2"
  restartPolicy: Never
EOF

# Watch the preemption happen
kubectl get pods -o wide --watch
```

**Step-by-Step Preemption**:
```
BEFORE:
NAME                           READY   NODE      STATUS
background-job-abc123         1/1     node-1    Running (2GB mem)
background-job-def456         1/1     node-2    Running (2GB mem)
critical-app                  0/1     <none>    Pending

↓ Scheduler runs
↓ Finds critical-app cannot fit
↓ Searches for preemption victims
↓ Finds background-job pods with lower priority

PREEMPTION IN PROGRESS:
NAME                           READY   NODE      STATUS
background-job-abc123         1/1     node-1    Terminating
background-job-def456         1/1     node-2    Running
critical-app                  0/1     node-1    Pending

↓ background-job-abc123 terminates after grace period (30s)
↓ critical-app scheduled on node-1
↓ background-job deployment controller creates replacement

AFTER:
NAME                           READY   NODE      STATUS
background-job-abc123         0/1     node-2    Pending (new)
background-job-def456         1/1     node-2    Running
critical-app                  1/1     node-1    Running
```

## Kubernetes Components Involved - Detailed Flow

### Complete Flow: Preemption Process

```
┌─────────────────────────────────────────────────────────────────┐
│ STEP 1: User Creates High-Priority Pod                          │
│                                                                 │
│ kubectl apply -f critical-pod.yaml                              │
│ → API Server receives request                                   │
│ → Validates PriorityClass "critical" exists                     │
│ → Creates pod object in etcd                                    │
│ → Sets status = Pending                                         │
└─────────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│ STEP 2: Scheduler Detects Pending Pod                           │
│                                                                 │
│ Scheduler watches for pending pods (informer cache)             │
│ → Sees "critical-pod" with status Pending                       │
│ → Retrieves pod spec from API Server                            │
│ → Reads priorityClassName = "critical"                          │
│ → Gets priority value = 1000 from PriorityClass object          │
└─────────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│ STEP 3: Scheduler Tries Regular Scheduling                      │
│                                                                 │
│ For each node:                                                  │
│ ├─ Check resources available                                    │
│ ├─ Check taints/tolerations                                     │
│ ├─ Check node selectors                                         │
│ ├─ Check affinity rules                                         │
│ ├─ If all checks pass → Node is suitable                        │
│                                                                 │
│ RESULT: No suitable nodes found                                 │
│ → Pod still cannot be scheduled                                 │
└─────────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│ STEP 4: Scheduler Checks Preemption                             │
│                                                                 │
│ Only if:                                                        │
│ ├─ Pod has priorityClassName (not default priority 0)           │
│ ├─ Pod cannot be scheduled normally                             │
│ └─ Preemption is enabled (default = true)                       │
│                                                                 │
│ FOR EACH NODE:                                                  │
│ ├─ Collect all lower-priority pods running on node              │
│ ├─ Filter out pods with higher/equal priority                   │
│ └─ If evicting victims → Check if space available               │
└─────────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│ STEP 5: Find Best Victim(s)                                     │
│                                                                 │
│ Scoring algorithm (lower score = more likely to evict):         │
│ ├─ Priority score: lower priority = higher chance               │
│ ├─ Pod age: newer pods = higher chance                          │
│ ├─ QoS class: BestEffort > Burstable > Guaranteed               │
│ ├─ Controller: unmanaged > managed (has replacement)            │
│ └─ Requested vs actual: actual users less requested             │
│                                                                 │
│ RESULT: Select pod with worst score to evict                    │
│ (Usually newest, lowest priority, BestEffort pod)               │
└─────────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│ STEP 6: Check PodDisruptionBudget                               │
│                                                                 │
│ If victim has matching PDB:                                     │
│ ├─ Check if evicting violates PDB constraints                   │
│ ├─ Count current running pods of same label                     │
│ ├─ Compare against minAvailable or maxUnavailable               │
│                                                                 │
│ IF VIOLATION:                                                   │
│ ├─ Cannot evict this pod                                        │
│ ├─ Try next victim                                              │
│ └─ If no valid victims → Preemption fails                       │
│                                                                 │
│ IF NO VIOLATION:                                                │
│ └─ Proceed with eviction                                        │
└─────────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│ STEP 7: Send Termination Request to API Server                  │
│                                                                 │
│ Scheduler sends pod deletion request:                           │
│ ├─ Updates pod.spec.terminationGracePeriodSeconds               │
│ ├─ Sets pod.metadata.deletionTimestamp                          │
│ ├─ Stores in etcd                                               │
│ └─ Notifies all watchers (kubelet, controllers)                 │
└─────────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│ STEP 8: Kubelet Receives Termination Signal                     │
│                                                                 │
│ Kubelet watches pod objects:                                    │
│ ├─ Detects deletionTimestamp is set                             │
│ ├─ Checks pod graceful shutdown handlers (preStop hooks)        │
│ ├─ Signals containers via container runtime                     │
│ │  └─ Container runtime sends SIGTERM to process                │
│ ├─ Waits for terminationGracePeriodSeconds (default 30s)        │
│ ├─ If still running after grace period:                         │
│ │  └─ Sends SIGKILL to force termination                        │
│ └─ Removes pod from node                                        │
└─────────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│ STEP 9: Pod Removed from Node                                   │
│                                                                 │
│ Kubelet cleanup:                                                │
│ ├─ Stops container via runtime                                  │
│ ├─ Cleans up mounts                                             │
│ ├─ Releases assigned resources                                  │
│ ├─ Reports pod status to API Server                             │
│ └─ Pod no longer in node.status.podCIDRs                        │
└─────────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│ STEP 10: Scheduler Schedules High-Priority Pod                  │
│                                                                 │
│ Now that victim pods are gone:                                  │
│ ├─ Node has free resources                                      │
│ ├─ Scheduler schedules high-priority pod on node                │
│ ├─ Updates pod.spec.nodeName                                    │
│ ├─ Sets pod.status = Running (when kubelet confirms)            │
│ └─ Pod starts running                                           │
└─────────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│ STEP 11: Controller Creates Replacement for Victims             │
│                                                                 │
│ Controller Manager monitors:                                    │
│ ├─ Detects victim pod is gone                                   │
│ ├─ Checks if pod has owner (Deployment, ReplicaSet, etc.)       │
│ ├─ If yes:                                                      │
│ │  ├─ Compares current replicas vs desired                      │
│ │  └─ Creates new pod to maintain count                         │
│ ├─ If no (standalone pod):                                      │
│ │  └─ Pod is gone forever                                       │
│ └─ New pod enters scheduling queue                              │
└─────────────────────────────────────────────────────────────────┘
```

## Troubleshooting & Best Practices

### Problem 1: Preemption Not Happening

**Symptom**: High-priority pod stays pending even though lower-priority pods exist.

**Root Causes**:

```bash
# Check 1: Is preemption enabled?
kubectl get configmap -n kube-system kube-scheduler-config \
  -o jsonpath='{.data.scheduler-config\.yaml}' | grep -i preempt

# Check 2: Does pod have priorityClassName?
kubectl get pod PODNAME -o jsonpath='{.spec.priorityClassName}'
# If empty → No priority set

# Check 3: Is PriorityClass valid?
kubectl get priorityclass
# Verify priorityClassName matches exactly

# Check 4: Check scheduler logs
kubectl logs -n kube-system -l component=kube-scheduler | grep -i preempt

# Check 5: Check for PodDisruptionBudget blocking
kubectl get pdb -A
# See if victim pod has active PDB

# Fix: Create valid PriorityClass
kubectl apply -f - <<EOF
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 100
EOF

# Then add to pod spec
kubectl patch deployment DEPLOYMENT_NAME \
  -p '{"spec":{"template":{"spec":{"priorityClassName":"high-priority"}}}}'
```

---

### Problem 2: Pod Evicted Unexpectedly

**Symptom**: Pod shows "Evicted" status without any scheduling request.

**Root Cause**: Likely kubelet eviction due to node resource pressure.

```bash
# Check node status for pressure
kubectl describe node NODE_NAME

# Look for:
Conditions:
  MemoryPressure       True
  DiskPressure         True
  PIDPressure          True

# Check evicted pod details
kubectl describe pod EVICTED_POD

# Output will show:
Status:  Failed
Reason:  Evicted
Message: Pod evicted due to memory pressure

# Fix: Increase resource requests/limits
kubectl set resources deployment DEPLOYMENT_NAME \
  -c CONTAINER_NAME \
  --requests=memory=4Gi,cpu=2 \
  --limits=memory=8Gi,cpu=4

# Or scale down other workloads
kubectl scale deployment OTHER_DEPLOYMENT --replicas=0
```

---

### Problem 3: Wrong QoS Class Assigned

**Symptom**: Pod with important workload has BestEffort QoS and gets evicted first.

**Root Cause**: No resource requests/limits defined.

```bash
# Check QoS class
kubectl get pod POD_NAME -o jsonpath='{.status.qosClass}'

# To change to Guaranteed:
# 1. Set requests = limits
# 2. Set for both memory and CPU

kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: important-app
spec:
  containers:
  - name: app
    image: app:latest
    resources:
      requests:
        memory: "2Gi"
        cpu: "2"
      limits:
        memory: "2Gi"
        cpu: "2"
# Now QoS = Guaranteed
EOF
```

---

### Problem 4: Preemption Respects PDB Too Much

**Symptom**: High-priority pod cannot be scheduled because PDB prevents enough evictions.

**Root Cause**: PDB minAvailable or maxUnavailable is too strict.

```bash
# Check PDB constraints
kubectl get pdb -o wide

# Check disruption count
kubectl describe pdb PDB_NAME

# Output:
Allowed Disruptions:  0
Current Healthy:      3
Desired Healthy:      2

# PDB prevents eviction: current (3) - disruptions (0) = min available (3)

# Fix: Adjust PDB
kubectl patch pdb PDB_NAME --type merge \
  -p '{"spec":{"minAvailable":1}}'

# Or remove PDB temporarily
kubectl delete pdb PDB_NAME
```

```bash
  # OR
  priority: 1000  # Direct priority value

# Check pod priority
kubectl get pod POD_NAME -o jsonpath='{.spec.priorityClassName}'
kubectl get pod POD_NAME -o jsonpath='{.spec.priority}'
```

### Eviction Commands

```bash
# Evict pod via API
kubectl evict POD_NAME -n NAMESPACE

# Evict with grace period
kubectl evict POD_NAME -n NAMESPACE --grace-period=30

# Check eviction policy
kubectl describe node NODE_NAME | grep -i eviction

# Force delete evicted pod
kubectl delete pod EVICTED_POD --grace-period=0 --force

# View evicted pods
kubectl get pods --field-selector=status.reason=Evicted
kubectl delete pods --field-selector=status.reason=Evicted
```

### Comparison: Priority vs QoS

| Aspect | Priority | QoS |
|--------|----------|-----|
| **Set By** | User (PriorityClass) | System (requests/limits) |
| **Scope** | Cluster-wide | Per-pod |
| **Affects** | Scheduler scheduling decisions | Eviction order |
| **When Active** | Always (unless priority=0) | During resource pressure |
| **Use Case** | Cluster-wide importance ranking | Fine-grained resource control |

---

### Priority vs Preemption vs Eviction

| Concept | Triggered By | Action | Result |
|---------|-------------|--------|--------|
| **Priority** | Pod creation | Affects queue position | Lower-priority pods scheduled last |
| **Preemption** | High-pri pod pending | Evicts low-pri pods | Makes space for high-pri pod |
| **Eviction** | Resource pressure | Removes pod from node | Frees resources for others |

| **API Server** | Gatekeeper | Validates priority, stores pod spec |
| **Scheduler** | Decision maker | Finds victims, initiates preemption |

## Conclusion

**Preemption & Eviction** ensure fair resource allocation in Kubernetes:
- **Preemption** = High-priority pods get resources by displacing low-priority pods
- **Eviction** = Pods removed when resources are constrained
- **Priority Classes** = Define workload importance
- **QoS Classes** = Determine eviction order when priorities are equal
- **Components** work together: API Server → Scheduler → Kubelet → Runtime

Master these concepts for production-grade Kubernetes operations! 🚀
