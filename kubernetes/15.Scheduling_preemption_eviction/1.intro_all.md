# Big Picture First

When a Pod is created, Kubernetes handles it in **3 possible stages**:

```text
1. Scheduling → Decide WHERE pod should run
2. Preemption → If no space, REMOVE lower priority pods to make space
3. Eviction → Remove running pods due to resource pressure or admin action
```

Think of a **hotel analogy**:

* **Scheduling** = receptionist assigns a room.
* **Preemption** = VIP guest arrives, receptionist asks lower-priority guest to leave.
* **Eviction** = hotel removes guests because of fire/water shortage/maintenance.

# PART 1: Scheduling (Detailed)

# What is Scheduling?

Scheduling is the process where **kube-scheduler** decides:

> “Which node is best for this Pod?”

When you create a pod:

```bash
kubectl apply -f pod.yaml
```

Pod is **not immediately sent to a node**.

First:

```bash
kubectl get pods
```

Output:

```text
myapp   0/1   Pending
```

Why Pending?

Because scheduler has not assigned a node yet.

---

# Internal Scheduling Workflow

```text
User creates Pod YAML
        ↓
API Server stores Pod object
        ↓
Scheduler watches API server
        ↓
Pod has no nodeName?
        ↓
Scheduler starts scheduling cycle
        ↓
1. Filter nodes
2. Score nodes
3. Select best node
4. Bind Pod to node
        ↓
Kubelet on node creates containers
```

---

# kube-scheduler Component

Control plane component:

```bash
kubectl get pods -n kube-system
```

You’ll see:

```text
kube-scheduler-master
```

Its job:

* Watch unscheduled pods
* Evaluate all nodes
* Pick best node
* Bind pod

It does **not create containers**.

Kubelet does that later.

---

# Scheduling Phases

## Phase 1: Filtering (Elimination)

Scheduler removes nodes that **cannot run** the pod.

This is called:

```text
Filter plugins
```

Old name:

```text
Predicates
```

---

## Filter checks

---

### 1. Resource fit

Checks if node has enough:

* CPU
* Memory
* Ephemeral storage
* GPU

Example:

Pod:

```yaml
resources:
  requests:
    cpu: "2"
    memory: "4Gi"
```

Node available:

```text
CPU = 1
Memory = 8Gi
```

Result:

Rejected because CPU insufficient.

---

### 2. NodeSelector check

Pod:

```yaml
nodeSelector:
  env: production
```

Node must have:

```bash
kubectl label node worker1 env=production
```

If label missing → node filtered out.

---

### 3. Node affinity check

Advanced label matching.

---

### 4. Taints/Tolerations check

If node has taint:

```bash
kubectl taint node worker1 dedicated=db:NoSchedule
```

Only tolerated pods can enter.

---

### 5. Port conflict check

If pod requests:

```yaml
hostPort: 8080
```

If another pod already uses 8080 on that node → reject.

---

### 6. Persistent Volume compatibility

Volume zone must match node zone.

---

### 7. Pod affinity/anti-affinity

Checks pod placement rules.

---

If 10 nodes exist and only 3 pass filters, scheduler continues.

---

# Phase 2: Scoring (Ranking)

Now Kubernetes asks:

> Which of these 3 nodes is BEST?

Each node gets points.

Example:

```text
worker1 → 85
worker2 → 70
worker3 → 92
```

Scheduler picks:

```text
worker3
```

---

# Scoring Factors

---

## Least allocated

Prefer node with more free resources.

Example:

```text
worker1 CPU used 80%
worker2 CPU used 20%
```

Prefer:

```text
worker2
```

---

## Balanced allocation

Avoid node with:

```text
CPU 90%
Memory 10%
```

Prefer balanced usage.

---

## Image locality

If node already has Docker image:

```text
nginx:latest
```

Scheduling is faster.

Gets higher score.

---

## Affinity preference

Preferred rules add score.

---

## Topology spread

Distribute pods evenly across nodes/zones.

---

# Types of Scheduling Constraints

---

# 1. nodeName (Manual scheduling)

Bypass scheduler completely.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: manual
spec:
  nodeName: worker1
  containers:
  - name: nginx
    image: nginx
```

Pod directly assigned.

Scheduler skipped.

Use rarely.

---

# 2. nodeSelector (Hard exact match)

Simplest method.

Node label:

```bash
kubectl label node worker1 disktype=ssd
```

Pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: db
spec:
  nodeSelector:
    disktype: ssd
  containers:
  - name: mysql
    image: mysql
```

Meaning:

> Only run on SSD node.

If no node matches:

```text
Pending forever
```

---

# 3. Node Affinity

More powerful than nodeSelector.

Inside:

```yaml
affinity:
  nodeAffinity:
```

---

## A. requiredDuringSchedulingIgnoredDuringExecution

Hard rule.

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: zone
          operator: In
          values:
          - east
```

Meaning:

Must run in zone=east.

---

Why “IgnoredDuringExecution”?

If node label changes later:

Pod stays.

Scheduler ignores after scheduling.

---

## B. preferredDuringSchedulingIgnoredDuringExecution

Soft rule.

```yaml
affinity:
  nodeAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 50
      preference:
        matchExpressions:
        - key: cpu
          operator: In
          values:
          - high
```

Try preferred node.

If unavailable, still schedule elsewhere.

---

## Operators

### In

```yaml
operator: In
values: [prod]
```

---

### NotIn

Exclude nodes.

---

### Exists

Only key needed.

```yaml
operator: Exists
```

---

### DoesNotExist

Node must not have label.

---

### Gt / Lt

Numeric comparison.

---

# 4. Pod Affinity

Place pod close to another pod.

Example:

Web pod near cache pod.

```yaml
affinity:
  podAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app: redis
      topologyKey: kubernetes.io/hostname
```

Meaning:

> Schedule this pod on same node as Redis.

Benefits:

* low latency
* faster communication

---

# 5. Pod Anti-Affinity

Opposite.

Avoid same node.

Example:

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app: nginx
      topologyKey: kubernetes.io/hostname
```

Meaning:

Do not place nginx replicas together.

Use for HA.

---

# 6. Taints and Tolerations

Node says:

> Keep away unless allowed.

Node taint:

```bash
kubectl taint node worker1 gpu=true:NoSchedule
```

Pod:

```yaml
tolerations:
- key: "gpu"
  operator: "Equal"
  value: "true"
  effect: "NoSchedule"
```

---

## Taint types

---

### NoSchedule

Blocks new pods.

Existing pods stay.

---

### PreferNoSchedule

Soft block.

Avoid if possible.

---

### NoExecute

Blocks new pods **and evicts existing pods**.

---

# 7. Topology Spread Constraints

Distribute pods evenly.

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: web
```

Meaning:

Keep pods balanced across nodes.

Example:

```text
Node1 = 2 pods
Node2 = 2 pods
Node3 = 2 pods
```

# PART 2: Preemption (Deep)

---

# What is Preemption?

If important pod cannot schedule:

Scheduler asks:

> Can I remove lower-priority pods?

That removal is preemption.

---

Example:

Node full.

Running:

```text
analytics pod priority 100
logging pod priority 50
```

New pod arrives:

```text
payment pod priority 1000
```

Scheduler kills:

```text
logging pod
```

Then schedules:

```text
payment pod
```

---

# PriorityClass

Required for preemption.

Create:

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: critical-priority
value: 100000
globalDefault: false
description: "Critical workloads"
```

---

Use in pod:

```yaml
spec:
  priorityClassName: critical-priority
```

---

# Preemption Workflow

```text
Pod pending
   ↓
No node fits
   ↓
Scheduler checks priorities
   ↓
Find removable lower-priority pods
   ↓
Marks them for termination
   ↓
Waits for deletion
   ↓
Schedules high-priority pod
```

---

# Victim Selection Logic

Scheduler chooses pods to remove based on:

* lower priority
* minimal disruption
* respect PDB if possible
* enough resources freed

---

# Non-preempting Priority

Important but should not evict others.

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: important
value: 10000
preemptionPolicy: Never
```

Useful for:

* batch jobs
* non-critical analytics

# PART 3: Eviction (Deep)

Eviction = pod removal after it is already running.

---

# Who triggers eviction?

Could be:

* kubelet
* API server
* node controller
* taint manager
* admin

---

# Types of Eviction

---

# 1. Resource Pressure Eviction

Most common.

Node running out of resources.

Examples:

* Memory
* Disk
* Inodes
* PID

Check:

```bash
kubectl describe node worker1
```

Possible output:

```text
MemoryPressure=True
DiskPressure=True
PIDPressure=True
```

---

## Memory eviction

Node RAM low.

Kubelet evicts pods.

---

## Disk eviction

Disk full.

Example:

```text
/var/lib/containerd
```

full.

Pods removed.

---

## PID eviction

Too many processes.

---

# QoS Classes (Very Important)

Eviction order depends on QoS.

---

## 1. BestEffort

No requests or limits.

```yaml
containers:
- name: app
  image: nginx
```

Lowest protection.

Evicted first.

---

## 2. Burstable

Requests set, limits optional/different.

```yaml
resources:
  requests:
    memory: "256Mi"
  limits:
    memory: "1Gi"
```

Medium protection.

---

## 3. Guaranteed

Requests = limits.

```yaml
resources:
  requests:
    cpu: "1"
    memory: "1Gi"
  limits:
    cpu: "1"
    memory: "1Gi"
```

Highest protection.

Evicted last.

---

Eviction order:

```text
BestEffort → Burstable → Guaranteed
```

---

# 2. API Eviction

Graceful removal via Eviction API.

Example:

```bash
kubectl drain worker1 --ignore-daemonsets
```

This triggers evictions.

---

Why not delete?

Delete:

```bash
kubectl delete pod x
```

Immediate.

Eviction:

* graceful
* respects PDB

---

# 3. Taint-Based Eviction

Node becomes unhealthy.

Controller adds taint:

```text
node.kubernetes.io/not-ready:NoExecute
```

Pods without toleration removed.

Pod toleration:

```yaml
tolerations:
- key: node.kubernetes.io/not-ready
  operator: Exists
  effect: NoExecute
  tolerationSeconds: 300
```

Meaning:

Stay 5 minutes before eviction.

---

# 4. PodDisruptionBudget (PDB) Controlled Eviction

Protects against voluntary disruptions.

Example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: web
```

Meaning:

At least 2 pods must stay.

If only 2 alive:

Eviction denied.

---

# Full Relationship

```text
Pod created
   ↓
Scheduling chooses node
   ↓
Node becomes full?
   ↓
Eviction may remove pod
   ↓
High-priority pod arrives?
   ↓
Preemption may remove other pods
```

# Interview-Level Differences

| Feature             | Scheduling   | Preemption                      | Eviction            |
| ------------------- | ------------ | ------------------------------- | ------------------- |
| Happens when        | Pod creation | Pod pending due to no resources | Pod already running |
| Trigger             | Scheduler    | Scheduler                       | Kubelet/API         |
| Removes pods?       | No           | Yes                             | Yes                 |
| Uses PriorityClass? | Optional     | Required                        | No                  |
| Uses QoS?           | No           | No                              | Yes                 |
