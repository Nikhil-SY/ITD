# PodDisruptionBudget (PDB) in Kubernetes — Detailed Explanation

In Kubernetes, **PodDisruptionBudget (PDB)** protects your application from **too many Pods being disrupted at the same time** during **voluntary disruptions**.

Think of it as:

**"Always keep at least N pods running."**

or

**"At most N pods can be unavailable."**

---

# Why PDB is needed

Imagine you have a Deployment:

```text
payment-service → 3 replicas
```

Pods:

```text
payment-service-1
payment-service-2
payment-service-3
```

Now cluster admin runs:

```bash
kubectl drain worker-node-1
```

During node maintenance, Kubernetes may evict pods.

Without PDB:

```text
Pod1 evicted
Pod2 evicted
```

Only 1 pod left → service may go down.

With PDB:

Kubernetes checks the budget and says:

```text
Only 1 pod can be disrupted now.
```

It blocks further eviction until replacement pod becomes healthy.

---

# What PDB protects against

### Voluntary disruptions (YES)

PDB works for planned actions like:

* Node draining

  ```bash
  kubectl drain node1
  ```
* Cluster upgrades
* Autoscaler removing nodes
* Manual pod eviction
* Some rolling updates (depending on controller)

---

### Involuntary disruptions (NO)

PDB cannot protect against:

* Node crash
* Pod crash
* OOMKilled
* Hardware failure
* Network outage

PDB only controls **evictions**, not failures.

---

# How PDB works

Two ways to define budget:

## 1. `minAvailable`

Minimum number of pods that **must stay available**.

Example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: payment
```

Meaning:

```text
Total pods = 3
At least 2 must stay healthy
Only 1 can be evicted
```

---

## 2. `maxUnavailable`

Maximum number of pods that can be unavailable.

Example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-pdb
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: payment
```

Meaning:

```text
Only 1 pod can be down at a time
```

---

# Example walkthrough

## Step 1: Create Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx
```

Pods:

```text
web-1
web-2
web-3
```

---

## Step 2: Create PDB

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: web
```

Apply:

```bash
kubectl apply -f pdb.yaml
```

---

## Step 3: Drain node

```bash
kubectl drain worker-node-1
```

Suppose node has:

```text
web-1
web-2
```

Kubernetes tries eviction.

Allowed:

```text
Evict web-1
```

Blocked:

```text
Cannot evict web-2
```

Because:

```text
Need minimum 2 available
```

Drain waits until replacement pod becomes ready.

---

# PDB status commands

Check:

```bash
kubectl get pdb
```

Example output:

```text
NAME      MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
web-pdb   2               N/A               1                     2d
```

Important field:

### `ALLOWED DISRUPTIONS`

```text
1
```

Means:

```text
One pod may be evicted now
```

Describe:

```bash
kubectl describe pdb web-pdb
```

# Advantages of PDB

## 1. Prevents downtime

Without PDB:

```text
All pods might be drained
Application down
```

With PDB:

```text
Minimum pods remain running
```

Example:

Payment API remains available during node upgrade.

---

## 2. Safe cluster maintenance

Admins can run:

```bash
kubectl drain
```

without accidentally breaking applications.

---

## 3. Works with Cluster Autoscaler

If autoscaler wants to remove a node:

PDB may stop removal if it would violate availability.

---

## 4. Protects critical applications

Useful for:

* Databases
* APIs
* Stateful apps
* Payment systems
* Authentication services

---

## 5. Enables high availability

PDB enforces HA policy automatically.

Example:

```text
Always keep 3 search pods alive
```

---

# minAvailable vs maxUnavailable

## Use `minAvailable`

When you know required healthy pods.

Example:

```yaml
minAvailable: 2
```

Means:

```text
Need at least 2 alive
```

---

## Use `maxUnavailable`

When you know acceptable disruption.

Example:

```yaml
maxUnavailable: 1
```

Means:

```text
Only 1 may go down
```

---

# Percentage support

Can use percentages.

Example:

```yaml
maxUnavailable: 30%
```

For 10 pods:

```text
3 pods may be disrupted
```

---

# Important limitations

## 1. Does not stop crashes

Node failure:

```text
Node dies → pods lost
```

PDB cannot help.

---

## 2. Bad configuration can block maintenance

Example:

```yaml
replicas: 1
minAvailable: 1
```

Drain impossible.

Because:

```text
Cannot evict the only pod
```

---

## 3. Needs multiple replicas

Single replica apps usually cannot benefit.

---

# Real-world example

### Critical auth service

Deployment:

```text
auth-service replicas = 5
```

PDB:

```yaml
minAvailable: 4
```

During cluster upgrade:

Only one pod can be disrupted.

Users can still log in.

# Interview-style answer

**Q: What is PodDisruptionBudget in Kubernetes?**

**Answer:**
**PodDisruptionBudget (PDB)** in Kubernetes limits how many Pods can be voluntarily disrupted at the same time during operations like node draining or upgrades. It helps maintain application availability by ensuring a minimum number of Pods remain running. It can be configured using **`minAvailable`** or **`maxUnavailable`**, and is commonly used to protect critical production workloads from downtime.
