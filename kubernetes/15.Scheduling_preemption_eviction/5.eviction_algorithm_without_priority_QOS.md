# Kubernetes Eviction WITHOUT Priority & QoS: Not FIFO, Not LIFO!

---

## The Question

**"If no priority and QoS eviction happens in LIFO?"**

**Answer: NO!**

```
❌ WRONG: LIFO (Last pod created = First pod evicted)
❌ WRONG: FIFO (First pod created = First pod evicted)
✅ CORRECT: "BEST PRESERVATION" algorithm
```

---

## What Happens During Eviction? (Step-by-Step)

When a node runs out of resources (memory, disk, CPU), the Kubelet initiates **eviction**.

### Eviction Triggering (Not Creation-Order Based)

```
Node Resource Pressure Detected
         ↓
Kubelet triggers eviction
         ↓
NOT based on pod creation time!
         ↓
Based on: Resource usage vs. requests
          Pod criticality
          Pod age and usage patterns
```

---

## The ACTUAL Eviction Algorithm

### Step 1: Categorize Pods by QoS Class

```
All running pods on node:
├─ BestEffort Pods (no requests/limits)
│  └─ QoS = BestEffort
│
├─ Burstable Pods (requests < limits)
│  └─ QoS = Burstable
│
└─ Guaranteed Pods (requests = limits)
   └─ QoS = Guaranteed
```

---

### Step 2: Sort by QoS Priority (HARD RULE)

```
Eviction Priority by QoS:
1️⃣ BestEffort pods    → Evicted FIRST (no protection)
2️⃣ Burstable pods     → Evicted SECOND (medium protection)
3️⃣ Guaranteed pods    → Evicted LAST (maximum protection)

^ THIS IS ALWAYS THE ORDER
^ REGARDLESS OF CREATION TIME
```

---

### Step 3: Within Same QoS, Use Secondary Factors

```
If multiple pods have SAME QoS class:
├─ Factor 1: Pod Priority (if set)
│  ├─ If priority classes exist: Use priority value
│  └─ If NO priority classes: All have priority 0 (equal)
│
├─ Factor 2: Resource Usage vs. Request
│  ├─ Pod using MORE than requested → Higher chance to evict
│  ├─ Pod using LESS than requested → Lower chance to evict
│  └─ Why? Pod is "misbehaving" by over-consuming
│
├─ Factor 3: Pod Age (tie-breaker)
│  ├─ Older pods → Lower priority to evict
│  ├─ Younger pods → Higher priority to evict
│  └─ Why? Spare longer-running workloads
│
└─ Factor 4: Pod Restart Status
   ├─ Never restarted → Lower priority to evict
   ├─ Restarted many times → Higher priority to evict
   └─ Why? Avoid flaky pods wasting resources
```

## Detailed Example: Eviction with NO Priority & NO QoS

### Setup

```
Node: 4GB Memory, Currently Using 3.8GB

Pod List (in creation order):
┌─────────────────────────────────────────────────────────────┐
│ Creation │ Name             │ QoS        │ Memory      │ Age │
│ Order    │                  │            │ Request     │     │
├──────────┼──────────────────┼────────────┼─────────────┼─────┤
│ 1st      │ Pod-A            │ BestEffort │ NONE        │ 5h  │
│ 2nd      │ Pod-B            │ Guaranteed │ 1Gi         │ 4h  │
│ 3rd      │ Pod-C            │ BestEffort │ NONE        │ 2h  │
│ 4th      │ Pod-D            │ Burstable  │ 0.5Gi       │ 1h  │
│ 5th      │ Pod-E            │ BestEffort │ NONE        │ 30m │
└─────────────────────────────────────────────────────────────┘

Memory Allocation:
├─ Pod-A (BestEffort): ~800Mi
├─ Pod-B (Guaranteed): 1Gi (requested)
├─ Pod-C (BestEffort): ~900Mi
├─ Pod-D (Burstable): 500Mi (requested), using ~700Mi (over request!)
├─ Pod-E (BestEffort): ~600Mi
└─ Total: 3.8Gi / 4Gi available

Need to free: ~200Mi to prevent node crash
```

### Eviction Decision Process

```
STEP 1: Filter by QoS Priority
┌─────────────────────────────────────────────────────────────┐
│ Rank Pods by QoS (HARD RULE - never breaks this order):    │
│                                                             │
│ TIER 1 - BestEffort (evict these FIRST):                   │
│ ├─ Pod-A (5h old, 800Mi)                                   │
│ ├─ Pod-C (2h old, 900Mi)                                   │
│ └─ Pod-E (30m old, 600Mi) ← Youngest                       │
│                                                             │
│ TIER 2 - Burstable (evict these SECOND):                   │
│ └─ Pod-D (1h old, USING 700Mi vs 500Mi REQUEST!)          │
│     ├─ Over-consuming! (700 > 500)                        │
│     └─ Most likely to evict in this tier                  │
│                                                             │
│ TIER 3 - Guaranteed (evict these LAST):                    │
│ └─ Pod-B (4h old, using exactly 1Gi)                       │
│     └─ Protected! Only evict if desperate                  │
└─────────────────────────────────────────────────────────────┘

✓ RESULT: Pod-A, Pod-C, Pod-E are candidates for eviction
          (NOT Pod-E just because it's newest)
          (NOT Pod-A just because it's oldest)
```

---

```
STEP 2: Select Best Candidate from BestEffort Tier
┌─────────────────────────────────────────────────────────────┐
│ BestEffort candidates:                                      │
│ ├─ Pod-A (5h old, 800Mi) - OLDER pod                       │
│ ├─ Pod-C (2h old, 900Mi) - MEDIUM pod                      │
│ └─ Pod-E (30m old, 600Mi) - NEWEST pod, uses 600Mi         │
│                                                             │
│ Secondary Factors (within same QoS):                        │
│                                                             │
│ Factor 1: Resource Usage vs Request                         │
│ ├─ Pod-A: No request (BestEffort) → No over-consumption    │
│ ├─ Pod-C: No request (BestEffort) → No over-consumption    │
│ └─ Pod-E: No request (BestEffort) → No over-consumption    │
│ ^ All equal on this factor                                 │
│                                                             │
│ Factor 2: Pod Age (tie-breaker)                            │
│ ├─ Pod-A: 5h old → Prefer to KEEP (older = more stable)   │
│ ├─ Pod-C: 2h old → Medium priority                        │
│ └─ Pod-E: 30m old → EVICT FIRST (newest)                  │
│           ^ Lower stability, less established              │
│                                                             │
│ WINNER: Pod-E ← Evicted FIRST (YOUNGEST, not OLDEST!)     │
└─────────────────────────────────────────────────────────────┘

✓ RESULT: Pod-E is evicted
```

---

```
STEP 3: After Pod-E Evicted
┌─────────────────────────────────────────────────────────────┐
│ Current State:                                              │
│ ├─ Pod-A (BestEffort): 800Mi                               │
│ ├─ Pod-B (Guaranteed): 1Gi                                 │
│ ├─ Pod-C (BestEffort): 900Mi                               │
│ ├─ Pod-D (Burstable): 700Mi (using > 500Mi request)       │
│ └─ Pod-E: TERMINATED ✓                                     │
│                                                             │
│ Memory freed: 600Mi                                        │
│ Memory pressure: RESOLVED (need was 200Mi, freed 600Mi)    │
│                                                             │
│ Remaining BestEffort: Pod-A, Pod-C                         │
│ Status: NOT evicted (memory pressure resolved)             │
└─────────────────────────────────────────────────────────────┘

✓ RESULT: Eviction stops here (no more pressure)
          NOT LIFO (didn't evict Pod-D which was 4th/newest)
          NOT FIFO (didn't evict Pod-A which was 1st/oldest)
          BEST-PRESERVATION (evicted newest BestEffort pod)
```

---

### If More Memory Needed

```
STEP 4: If Still Pressure (need more than 600Mi free)
┌─────────────────────────────────────────────────────────────┐
│ Remaining BestEffort candidates:                            │
│ ├─ Pod-A (5h old, 800Mi) ← OLDER                          │
│ └─ Pod-C (2h old, 900Mi) ← NEWER                          │
│                                                             │
│ Factor: Pod Age                                            │
│ ├─ Pod-A: 5h old → Prefer to KEEP (more stable)           │
│ └─ Pod-C: 2h old → EVICT NEXT (younger)                   │
│                                                             │
│ WINNER: Pod-C ← Evicted SECOND (NOT Pod-A the oldest!)    │
└─────────────────────────────────────────────────────────────┘
```

---

```
STEP 5: If STILL Pressure (need even more)
┌─────────────────────────────────────────────────────────────┐
│ Last BestEffort remaining:                                 │
│ └─ Pod-A (5h old, 800Mi) ← Only BestEffort left           │
│                                                             │
│ WINNER: Pod-A ← Evicted THIRD (THE OLDEST!)               │
│                                                             │
│ After Pod-A evicted:                                       │
│ Freed: 800Mi more                                          │
│                                                             │
│ Total freed: 600 + 900 + 800 = 2.3Gi                      │
│ All BestEffort pods gone!                                 │
│                                                             │
│ If STILL need more:                                        │
│ └─ Pod-D (Burstable, over-consuming) ← Next target         │
│    └─ NOT Pod-B (Guaranteed) ← Most protected              │
└─────────────────────────────────────────────────────────────┘
```

---

### Final Eviction Order

```
ACTUAL EVICTION SEQUENCE:
1️⃣ Pod-E (30m old) ← YOUNGEST BestEffort, evicted FIRST
2️⃣ Pod-C (2h old) ← MIDDLE age BestEffort, evicted SECOND
3️⃣ Pod-A (5h old) ← OLDEST BestEffort, evicted THIRD
4️⃣ Pod-D (1h old) ← Burstable (if still needed)
5️⃣ Pod-B (4h old) ← Guaranteed (only if critical)

ANALYSIS:
├─ Creation order: A(1st), B(2nd), C(3rd), D(4th), E(5th)
├─ Eviction order: E, C, A, D, B
│
├─ Is it LIFO? NO (LIFO would be E, D, C, B, A)
├─ Is it FIFO? NO (FIFO would be A, B, C, D, E)
│
└─ What is it? QoS-based with age as tie-breaker
            BestEffort evicted by AGE (youngest first)
            Then Burstable, then Guaranteed
```

### Scenario 1: Only QoS (No Priority, No Priority Classes)

```
Eviction Order Decision:
1. QoS Class (FIRST) ← Hard rule
   ├─ All BestEffort first
   ├─ All Burstable second
   └─ All Guaranteed last

2. Within same QoS (SECOND):
   ├─ Usage vs Request (pod over-consuming?)
   ├─ Pod Age (newer pods evicted first)
   └─ Other factors
```

---

### Scenario 2: With Priority Classes

```
Eviction Order Decision:
1. QoS Class (FIRST) ← Hard rule
   ├─ All BestEffort first
   ├─ All Burstable second
   └─ All Guaranteed last

2. Priority within same QoS (SECOND)
   ├─ Lower priority pods evicted first
   ├─ Higher priority pods protected
   └─ Among same priority: age/usage factors

Example:
├─ BestEffort Low Priority: Evicted first
├─ BestEffort High Priority: Evicted later
├─ Burstable Low Priority: Evicted after all BestEffort
└─ And so on...
```

### Setup

```
Database Node: 16GB Memory, 14GB used

Running Pods:
┌─────────────────────────────────────────────────────────────┐
│ Name           │ QoS        │ Memory   │ Created    │ Age    │
│                │            │ Request  │            │        │
├────────────────┼────────────┼──────────┼────────────┼────────┤
│ db-primary     │ Guaranteed │ 8Gi      │ 6 months   │ 6 mo   │
│ cache-service  │ Burstable  │ 2Gi      │ 3 months   │ 3 mo   │
│ log-processor  │ BestEffort │ None     │ 2 weeks    │ 2 wks  │
│ monitoring     │ BestEffort │ None     │ 1 week     │ 1 wk   │
│ temp-tool      │ BestEffort │ None     │ 30 min     │ 30 min │
└─────────────────────────────────────────────────────────────┘

Memory Usage:
├─ db-primary: 8Gi (exactly as requested)
├─ cache-service: 3Gi (uses more than 2Gi request - over!)
├─ log-processor: 1.5Gi
├─ monitoring: 0.8Gi
├─ temp-tool: 0.7Gi
└─ Total: 14Gi / 16Gi (2Gi available)

New pod needs 3Gi
└─ ERROR: Cannot fit, need to evict 2Gi
```

---

### Eviction Decision

```
DECISION PROCESS:

STEP 1: By QoS (Non-negotiable)
├─ Must evict BestEffort pods first!
└─ Candidates: log-processor, monitoring, temp-tool

STEP 2: Among BestEffort pods, by age
├─ temp-tool (30 min old) ← YOUNGEST
│  └─ Evict FIRST despite being created LAST!
│
├─ monitoring (1 week old) ← MIDDLE
│  └─ Evict SECOND
│
└─ log-processor (2 weeks old) ← OLDEST
   └─ Evict THIRD if needed

STEP 3: If still need more (unlikely)
├─ cache-service (Burstable, over-consuming)
│  └─ Using 3Gi > 2Gi request
│  └─ Evict FOURTH
│
└─ db-primary: NEVER (Guaranteed, critical)
```

---

### Result

```
Expected if LIFO:
├─ Evict temp-tool (30 min, newest) ✓ (matches LIFO)
├─ Evict monitoring (1 week) ✓ (matches LIFO)
└─ Evict log-processor (2 weeks, oldest) ✓ (matches LIFO)

^ In this case, LIFO MATCHES because all are BestEffort!

BUT: If different QoS:
├─ What if temp-tool was Burstable? → Would NOT be evicted first
├─ What if log-processor was Guaranteed? → Would never be evicted
└─ LIFO assumption breaks!

ACTUAL ALGORITHM:
1. Evict BestEffort before Burstable before Guaranteed
2. Within same QoS, prefer newer/younger pods
3. Creation order is NEVER the primary factor!
```

## When LIFO LOOKS CORRECT (But It's Not)

### Coincidence Case

```
ALL pods have SAME QoS class (e.g., all BestEffort)
AND
ALL pods have SAME age-related characteristics
└─ In this rare case, newest pod might be evicted first
└─ Makes LIFO look correct!

But this is coincidence, not algorithm!

Real algorithm:
├─ QoS is PRIMARY factor (not creation order)
├─ Age is SECONDARY factor (not creation order)
├─ Creation order is NOT a factor
```

---

### Why LIFO Seems Right But Is Wrong

```
Example that BREAKS LIFO:

Creation Order: Pod-A, Pod-B, Pod-C

Case 1: All BestEffort QoS (LIFO appears correct)
├─ Pod-C (30 min old) → Evicted 1st ✓ (newest)
├─ Pod-B (2h old) → Evicted 2nd
└─ Pod-A (5h old) → Evicted 3rd (oldest)
^ Appears to be LIFO!

Case 2: Different QoS (LIFO fails)
├─ Pod-C: BestEffort (30 min old)
├─ Pod-B: Guaranteed (2h old)
└─ Pod-A: BestEffort (5h old)

Actual eviction order:
├─ Pod-C (BestEffort) → Evicted 1st ✓
├─ Pod-A (BestEffort) → Evicted 2nd
└─ Pod-B (Guaranteed) → Evicted 3rd
    
✗ NOT LIFO! (Pod-B created 2nd but evicted LAST)
✗ Pod-A created FIRST but evicted SECOND!

This contradicts LIFO which would predict:
└─ Pod-C → Pod-B → Pod-A
```

## Kubelet Eviction Thresholds

### Memory Pressure Example

```
Kubelet Configuration:
├─ evictionHard:
│  └─ memory.available < 100Mi
│     (If available memory drops below 100Mi, evict)
│
└─ evictionSoft:
   ├─ memory.available < 500Mi
   │  └─ But with grace period
   └─ evictionMaxPodGracePeriod: 30s

When Memory Drops Below Threshold:
1. Kubelet detects pressure
2. Initiates graceful termination (30s grace period)
3. Uses eviction priority (QoS-based)
4. Evicts lowest QoS first
5. Within same QoS: uses secondary factors (age, etc.)
6. Repeats until memory pressure resolved
```

## Summary: NOT FIFO, NOT LIFO, Something Else!

### The Truth Table

| Eviction Scenario | FIFO? | LIFO? | Actual Algorithm |
|-------------------|-------|-------|------------------|
| **No Priority, No QoS specified** | ❌ NO | ❌ NO | QoS-based (all BestEffort) + Age |

| **With Priority classes** | ❌ NO | ❌ NO | QoS-tier first, then Priority, then secondary |
| **Same QoS, same priority** | ❌ NO | ✅ MAYBE | Age (newer pods first) |

### Real-World Implications

```
Misconception 1: "If no priority, eviction is FIFO"
Reality: ❌ WRONG
         Eviction is QoS-based
         Within QoS, it's by usage and age
         Creation order doesn't matter

Misconception 2: "If no priority, eviction is LIFO"
Reality: ❌ WRONG
         LIFO might match when all pods are same QoS
         But breaks when QoS varies
         Only works by coincidence

Misconception 3: "Oldest pod is safest (won't be evicted)"
Reality: ❌ WRONG
         QoS class matters MORE than age
         BestEffort 5-year-old pod
         > Guaranteed 5-minute-old pod
         (Guaranteed pod never evicted if BestEffort available)

Misconception 4: "Eviction respects creation order"
Reality: ❌ WRONG
         QoS is primary
         Age is secondary
         Creation order is not a factor
```

## Best Practices to Avoid Eviction Issues

### Practice 1: Always Use Resource Requests/Limits

```yaml
✅ GOOD:
spec:
  containers:
  - name: app
    resources:
      requests:
        memory: "512Mi"
        cpu: "250m"
      limits:
        memory: "1Gi"
        cpu: "500m"
# QoS = Guaranteed (most protected)

❌ BAD:
spec:
  containers:
  - name: app
    # No resources
# QoS = BestEffort (evicted first!)
```

---

### Practice 2: Match Requests to Actual Usage

```yaml
✅ GOOD:
resources:
  requests:
    memory: "512Mi"  # Actual typical usage
  limits:
    memory: "1Gi"    # 2x request for spikes
# Pod won't be evicted for over-consumption

❌ BAD:
resources:
  requests:
    memory: "100Mi"  # Underestimated!
  limits:
    memory: "1Gi"    # Pod uses 800Mi typically
# Pod will be marked as over-consuming
# Higher eviction priority!
```

---

### Practice 3: Set Priority Classes for Critical Workloads

```yaml
✅ GOOD:
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: database
value: 1000
---
apiVersion: v1
kind: Pod
metadata:
  name: postgres
spec:
  priorityClassName: database
  containers:
  - name: db
    resources:
      requests:
        memory: "4Gi"
      limits:
        memory: "8Gi"
# Even if Burstable, priority protects it

❌ BAD:
apiVersion: v1
kind: Pod
metadata:
  name: postgres
spec:
  # No priority!
  containers:
  - name: db
    resources:
      requests:
        memory: "4Gi"
      limits:
        memory: "8Gi"
# At mercy of eviction if resource pressure
```

---

### Practice 4: Use PodDisruptionBudget

```yaml
✅ GOOD:
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: database-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: database
---
apiVersion: v1
kind: Pod
metadata:
  name: postgres-primary
  labels:
    app: database
spec:
  priorityClassName: database
  containers:
  - name: db
    resources:
      requests:
        memory: "4Gi"
      limits:
        memory: "8Gi"
# PDB + Priority + Guaranteed = Maximum protection
```

## Final Comparison: Creation Order vs Eviction Order

```
Scenario: 4 BestEffort pods (no priority, no requests/limits)
Created in order: Pod-A, Pod-B, Pod-C, Pod-D

FIFO Prediction:  Evict A → B → C → D (by creation order)
LIFO Prediction:  Evict D → C → B → A (reverse creation order)

ACTUAL Eviction:  Depends on AGE at time of pressure
                  If all created 5 min apart:
                  └─ Evict D → C → B → A (youngest first)
                     ^ Looks like LIFO but it's not!
                     ^ It's "youngest pod first" which happens
                       to match LIFO in this timing

                  But if created hours apart then pressure happens:
                  └─ Evict D → C → B → A (by age at eviction time)
                     ^ Still "youngest first"
                     ^ Still looks like LIFO

                  BUT if different ages or QoS:
                  Pod-A: BestEffort (5h old)
                  Pod-B: Guaranteed (30 min old)
                  Pod-C: BestEffort (2h old)
                  Pod-D: Burstable (1h old)
                  
                  Actual: A → C → D → B
                  (BestEffort by age, then Burstable, then Guaranteed)
                  ^ NEITHER FIFO NOR LIFO!
```

## Conclusion

### The Answer to "Is Eviction LIFO?"

**No. Eviction is NOT LIFO.**

### The Real Algorithm

```
Priority 1: QoS Class (ALWAYS first)
            BestEffort → Burstable → Guaranteed

Priority 2: Within Same QoS
            Priority Value (if set)
            → Usage vs Request
            → Pod Age (younger first)
            → Other factors

Priority 3: Creation Order (NEVER a factor)
            ❌ Not used in decision
            ❌ Not even considered
            ❌ Completely irrelevant
```

### Why LIFO Seems Right Sometimes

```
When all pods have:
├─ Same QoS class (all BestEffort)
└─ Close creation times

Then eviction order happens to match LIFO
└─ But this is COINCIDENCE
└─ Not because of LIFO algorithm
└─ It's because younger pods are evicted first
```

# No — for **Burstable**, both CPU and memory do **not** need to be set.

To get **Burstable QoS** in Kubernetes:

**At least one container in the Pod must have *any* `request` or `limit` set (CPU or memory),**
but the Pod must **not qualify for Guaranteed**.

That means **even one of these is enough**:

* only `cpu request`
* only `memory request`
* only `cpu limit`
* only `memory limit`
* any combination where `request != limit`

# Examples of **Burstable**

## Example 1: Only memory request set ✅

```yaml
resources:
  requests:
    memory: "256Mi"
```

**QoS:** `Burstable`

---

## Example 2: Only CPU request set ✅

```yaml
resources:
  requests:
    cpu: "200m"
```

**QoS:** `Burstable`

---

## Example 3: Only memory limit set ✅

```yaml
resources:
  limits:
    memory: "512Mi"
```

**QoS:** `Burstable`

---

## Example 4: CPU set, memory not set ✅

```yaml
resources:
  requests:
    cpu: "250m"
  limits:
    cpu: "500m"
```

**QoS:** `Burstable`

---

## Example 5: Both set but unequal ✅

```yaml
resources:
  requests:
    cpu: "200m"
    memory: "256Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"
```

**QoS:** `Burstable`

---

# When does it become **Guaranteed**?

For **Guaranteed**, **every container** must have:

* **CPU request**
* **CPU limit**
* **Memory request**
* **Memory limit**

And they must match exactly:

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"
```

**QoS:** `Guaranteed`

---

# Quick rule to remember

### **BestEffort**

```yaml
resources: {}
```

No requests, no limits.

### **Burstable**

```yaml
Any request or limit exists
```

### **Guaranteed**

```yaml
CPU + memory both set, and request == limit
```

---

## Interview-style answer

**Q: Do both CPU and memory need to be set for Burstable QoS?**

**Answer:**
No. For **Burstable** QoS in Kubernetes, it is enough to set **any one** resource request or limit (CPU or memory). Both CPU and memory are **not required**. A Pod becomes **Guaranteed** only when both CPU and memory requests and limits are set and are equal for every container.
