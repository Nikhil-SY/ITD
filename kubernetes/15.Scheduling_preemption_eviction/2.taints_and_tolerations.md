## Introduction

In Kubernetes, you need fine-grained control over which pods run on which nodes. Imagine a restaurant with different sections: the chef's special section shouldn't allow just any customer, and a VIP section should only seat VIP members.

**Taints & Tolerations** work together like this:
- **Taint** = A label that says "only pods with special permission can run here"
- **Toleration** = A permission that says "I'm allowed to run on nodes with this taint"

**Cordon & Drain** are tools to safely manage node maintenance:
- **Cordon** = Mark a node as "off-limits" for new pods (but existing pods stay)
- **Drain** = Evict all pods and prepare a node for maintenance

---

## Taints: What, Why, How

### What Are Taints?

A **taint** is a property of a Kubernetes node that repels pods unless those pods have matching tolerations. Think of it as a "Do Not Disturb" sign on a node.

**Structure of a Taint:**
```
key=value:effect
```

- **key**: Name identifier (e.g., `gpu`, `environment`, `dedicated`)
- **value**: Optional value (e.g., `true`, `production`, `nvidia`)
- **effect**: What happens to pods without tolerance
  - `NoSchedule`: New pods won't be scheduled (existing pods unaffected)
  - `PreferNoSchedule`: New pods avoid this node (soft preference)
  - `NoExecute`: New AND existing pods are evicted if no toleration

---

### Why Use Taints?

| Scenario | Reason |
|----------|--------|
| **Dedicated Hardware** | Reserve specific nodes for GPU workloads, expensive resources |
| **Environment Isolation** | Keep staging pods off production nodes |
| **Cost Control** | Prevent regular workloads from running on expensive spot instances |
| **Compliance** | Ensure sensitive data only runs on secure nodes |
| **Node Maintenance** | Prevent new workloads during updates or repairs |

---

### How Taints Work: Step-by-Step

```
User creates Node with Taint
         ↓
Scheduler receives Pod request
         ↓
Check: Does Pod have matching Toleration?
    ├─ NO  → Scheduler rejects Pod (Pod stays Pending)
    └─ YES → Pod scheduled and runs normally
```

## Tolerations: What, Why, How

### What Are Tolerations?

A **toleration** is a Pod-level setting that allows it to be scheduled on nodes with taints. It's the "passport" that lets a pod through the tainted node's security checkpoint.

**Structure of a Toleration (in Pod spec):**
```yaml
tolerations:
- key: gpu
  operator: Equal
  value: "true"
  effect: NoSchedule
```

---

### Why Use Tolerations?

- **Selective Scheduling**: Allow specific pods on restricted nodes
- **Multi-tenant Clusters**: Different teams get their own nodes
- **Resource Optimization**: Use expensive nodes only for workloads that need them
- **Flexibility**: Move workloads between nodes by adjusting tolerations

---

### How Tolerations Work

A toleration matches a taint when:
1. Keys match (`gpu` = `gpu`)
2. Values match if operator is `Equal` (`true` = `true`)
3. Effect matches (`NoSchedule` = `NoSchedule`)

## Practical Examples: Taints & Tolerations

### Example 1: GPU Node (NoSchedule Effect)

**Scenario**: You have a GPU node. Only ML workloads should use it; regular apps shouldn't.

#### Step 1: Taint the GPU Node

```bash
# Taint node-gpu with gpu=true, effect NoSchedule
kubectl taint nodes node-gpu gpu=true:NoSchedule

# Verify taint was applied
kubectl describe node node-gpu
```

**Output:**
```
Name:               node-gpu
...
Taints:             gpu=true:NoSchedule
```

#### Step 2: Create a Regular Pod (Will Be Rejected)

```yaml
# regular-app.yaml
apiVersion: v1
kind: Pod
metadata:
  name: regular-app
spec:
  containers:
  - name: nginx
    image: nginx:latest
```

```bash
kubectl apply -f regular-app.yaml
kubectl get pods
```

**Result:**
```
NAME           READY   STATUS    RESTARTS   AGE
regular-app    0/1     Pending   0          10s
```

The pod is stuck in `Pending` because it has no toleration for the `gpu=true:NoSchedule` taint.

#### Step 3: Create a GPU Pod with Toleration

```yaml
# gpu-app.yaml
apiVersion: v1
kind: Pod
metadata:
  name: gpu-app
spec:
  containers:
  - name: ml-training
    image: tensorflow:latest
    resources:
      limits:
        nvidia.com/gpu: 1
  
  # Add toleration matching the taint
  tolerations:
  - key: gpu
    operator: Equal
    value: "true"
    effect: NoSchedule
```

```bash
kubectl apply -f gpu-app.yaml
kubectl get pods
```

**Result:**
```
NAME           READY   STATUS    RESTARTS   AGE
gpu-app        1/1     Running   0          5s
regular-app    0/1     Pending   0          15s
```

✅ `gpu-app` runs because it has the matching toleration
❌ `regular-app` stays pending because it has no toleration

---

### Example 2: Environment Isolation (Multiple Taints)

**Scenario**: Production nodes should only run production pods; staging pods should not use them.

#### Step 1: Taint Production Nodes

```bash
# Taint all production nodes
kubectl taint nodes prod-node-1 prod-node-2 environment=production:NoSchedule

# Verify
kubectl describe node prod-node-1 | grep Taints
```

**Output:**
```
Taints:             environment=production:NoSchedule
```

#### Step 2: Deploy Production Pod

```yaml
# production-app.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: prod-api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
      - name: api-server
        image: api-server:v1.0
      
      # Toleration for production nodes
      tolerations:
      - key: environment
        operator: Equal
        value: production
        effect: NoSchedule
      
      # Node affinity to prefer production nodes
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: environment
                operator: In
                values:
                - production
```

```bash
kubectl apply -f production-app.yaml
kubectl get pods -o wide
```

**Result:**
```
NAME                     READY   NODE         STATUS
prod-api-abc123...       1/1     prod-node-1  Running
prod-api-def456...       1/1     prod-node-2  Running
```

#### Step 3: Try to Deploy Staging Pod (Will Be Rejected)

```yaml
# staging-app.yaml
apiVersion: v1
kind: Pod
metadata:
  name: staging-app
spec:
  containers:
  - name: nginx
    image: nginx:latest
  # No toleration - will be rejected from production nodes
```

```bash
kubectl apply -f staging-app.yaml
kubectl get pods
```

**Result:**
```
NAME           READY   STATUS    RESTARTS   AGE
staging-app    0/1     Pending   0          5s
```

### Example 3: PreferNoSchedule (Soft Preference)

**Scenario**: Prefer not to use expensive spot instances, but it's okay if needed.

#### Step 1: Taint Spot Instance Nodes

```bash
# Use PreferNoSchedule - softer than NoSchedule
kubectl taint nodes spot-node-1 instance-type=spot:PreferNoSchedule

# Verify
kubectl describe node spot-node-1 | grep Taints
```

**Output:**
```
Taints:             instance-type=spot:PreferNoSchedule
```

#### Step 2: Deploy Pod Without Toleration

```yaml
# regular-app.yaml
apiVersion: v1
kind: Pod
metadata:
  name: regular-app
spec:
  containers:
  - name: app
    image: app:latest
```

```bash
kubectl apply -f regular-app.yaml
kubectl get pods -o wide
```

**Result:**
```
NAME          READY   NODE         STATUS
regular-app   1/1     normal-node  Running
```

✅ The pod runs on `normal-node` because it prefers to avoid `spot-node-1`, but if only spot nodes were available, it would still be scheduled there.

---

### Example 4: NoExecute (Evicts Existing Pods)

**Scenario**: A node is going down for maintenance. Evict all running pods.

#### Step 1: Taint Node with NoExecute

```bash
# This will evict ALL existing pods without toleration
kubectl taint nodes node-to-maintain maintenance=true:NoExecute

# Check pod status
kubectl get pods -o wide
```

**Result:**
```
NAME                     READY   STATUS    RESTARTS   AGE
pod-with-toleration      1/1     Running   0          2m (moved to another node)
pod-without-toleration   0/1     Unknown   0          5m (being evicted)
```

#### Step 2: Add Toleration with Graceful Eviction Timeout

```yaml
# maintenance-tolerant-app.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: maintenance-safe-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: safe-app
  template:
    metadata:
      labels:
        app: safe-app
    spec:
      containers:
      - name: app
        image: app:latest
      
      # Tolerate maintenance taint with 5-minute eviction grace period
      tolerations:
      - key: maintenance
        operator: Equal
        value: "true"
        effect: NoExecute
        tolerationSeconds: 300  # 5 minutes grace period
```

```bash
kubectl apply -f maintenance-tolerant-app.yaml
```

**Result:**
```
Pods with this toleration will gracefully shut down over 5 minutes,
allowing time for connections to drain and data to be saved.
```

## Cordon & Uncordon

### What is Cordon?

**Cordon** marks a node as unschedulable for NEW pods. Existing pods keep running normally.

```
Before Cordon                After Cordon
┌──────────────┐            ┌──────────────┐
│   Node-A     │            │   Node-A     │
│ (3 pods)     │   cordon   │ (3 pods)     │
│ ✓ Running    │ --------→  │ ✓ Running    │
│ ✓ Accepting  │            │ ✗ Blocked    │
└──────────────┘            └──────────────┘
```

### Why Use Cordon?

| Scenario | Reason |
|----------|--------|
| **Pre-maintenance** | Stop new pods before draining existing ones |
| **Testing** | Block new workloads while testing node stability |
| **Manual Inspection** | Investigate issues without new pods interfering |
| **Planned Downtime** | Graceful transition before shutdown |

---

### How to Use Cordon

#### Cordon a Node

```bash
# Mark node as unschedulable
kubectl cordon node-a

# Verify
kubectl get nodes
```

**Output:**
```
NAME      STATUS                     ROLES    AGE
node-a    NotReady,SchedulingDisabled 0       10d
node-b    Ready                      master   10d
node-c    Ready                      worker   8d
```

Notice the `SchedulingDisabled` status.

#### Try to Schedule a Pod on Cordoned Node

```yaml
# new-app.yaml
apiVersion: v1
kind: Pod
metadata:
  name: new-app
spec:
  containers:
  - name: nginx
    image: nginx:latest
  nodeSelector:
    kubernetes.io/hostname: node-a
```

```bash
kubectl apply -f new-app.yaml
kubectl describe pod new-app
```

**Output:**
```
Events:
  Type     Reason             AGE     Message
  ----     ------             ---     -------
  Warning  FailedScheduling   10s     0/3 nodes are available:
                                      1 node(s) had taints that the pod didn't tolerate,
                                      1 node(s) were unschedulable
```

❌ Pod cannot be scheduled even if we force the node selector.

#### Existing Pods Keep Running

```bash
# Pods already on node-a continue to run
kubectl get pods -o wide | grep node-a
```

**Output:**
```
NAME                STATUS    NODE
existing-app        Running   node-a
```

✅ Existing pods are unaffected.

---

### How to Uncordon a Node

```bash
# Remove the cordon - node is schedulable again
kubectl uncordon node-a

# Verify
kubectl get nodes
```

**Output:**
```
NAME      STATUS   ROLES    AGE
node-a    Ready    worker   10d
node-b    Ready    master   10d
node-c    Ready    worker   8d
```

Status changes back to `Ready`.

## Drain

### What is Drain?

**Drain** safely evicts ALL pods from a node and marks it as unschedulable. It's the clean way to prepare a node for maintenance.

```
Before Drain              During Drain              After Drain
┌──────────────┐         ┌──────────────┐         ┌──────────────┐
│   Node-A     │         │   Node-A     │         │   Node-A     │
│ (5 pods)     │ drain   │ (3 pods)     │ moving  │ (0 pods)     │
│ ✓ Running    │------→  │ (2 evicted)  │------→  │ ✗ Blocked    │
│ ✓ Accepting  │         │ → Node-B     │         │ ✗ Cordoned   │
└──────────────┘         └──────────────┘         └──────────────┘
                              ↓
                         ┌──────────────┐
                         │   Node-B     │
                         │ (7 pods now) │
                         └──────────────┘
```

### Why Use Drain?

| Scenario | Reason |
|----------|--------|
| **Node Maintenance** | Kernel updates, hardware repairs |
| **Cluster Upgrades** | Upgrade node OS or kubelet safely |
| **Decommissioning** | Remove a node from the cluster |
| **Scale-down** | Safely reduce cluster size |

---

### How Drain Works

1. **Cordon** the node (no new pods)
2. **Evict** all pods gracefully
3. **Wait** for replacement pods on other nodes
4. **Delete** pod objects from cordoned node

---

### Drain in Action

#### Step 1: See Current State

```bash
# Check node and pods
kubectl get nodes
kubectl get pods -o wide
```

**Output:**
```
NODES:
NAME      STATUS   ROLES    AGE
node-a    Ready    worker   10d
node-b    Ready    worker   8d

PODS:
NAME                    READY   NODE    STATUS
app-1-abc123...         1/1     node-a  Running
app-2-def456...         1/1     node-a  Running
app-3-ghi789...         1/1     node-b  Running
```

#### Step 2: Drain the Node

```bash
# Evict all pods from node-a
kubectl drain node-a --ignore-daemonsets --delete-emptydir-data

# Note:
# --ignore-daemonsets: Don't try to evict DaemonSet pods (they're supposed to run on all nodes)
# --delete-emptydir-data: Allow eviction of pods using emptyDir volumes
```

**Output:**
```
node/node-a cordoned
pod/app-1-abc123... evicted
pod/app-2-def456... evicted
node/node-a drained
```

#### Step 3: Check Node Status

```bash
kubectl get nodes
kubectl get pods -o wide
```

**Output:**
```
NODES:
NAME      STATUS                     ROLES    AGE
node-a    NotReady,SchedulingDisabled worker   10d
node-b    Ready                      worker   8d

PODS:
NAME                    READY   NODE    STATUS
app-1-xyz987...         1/1     node-b  Running (new replica)
app-2-qwe654...         1/1     node-b  Running (new replica)
app-3-ghi789...         1/1     node-b  Running (unchanged)
```

✅ Pods evicted from node-a
✅ New replicas created on node-b
✅ node-a is cordoned (unschedulable)

---

#### Step 4: Do Maintenance

```bash
# Now you can safely:
# - Update OS
# - Install patches
# - Replace hardware
# - Restart kubelet
```

---

#### Step 5: Uncordon the Node

```bash
# Once maintenance is done, make node schedulable again
kubectl uncordon node-a

# Verify
kubectl get nodes
```

**Output:**
```
NAME      STATUS   ROLES    AGE
node-a    Ready    worker   10d
node-b    Ready    worker   8d
```

✅ Node is back online and ready for workloads.

---

### Drain Flags & Options

| Flag | Description |
|------|-------------|
| `--ignore-daemonsets` | Ignore DaemonSet pods (required in most cases) |
| `--delete-emptydir-data` | Allow eviction of pods using emptyDir volumes |
| `--grace-period=30` | Grace period for graceful termination (seconds) |
| `--force` | Force delete pods that don't evict cleanly |
| `--dry-run=client` | Preview what will be evicted without actually draining |
| `--pod-selector=app=web` | Only drain pods matching this selector |
| `--timeout=5m` | Maximum time to wait for eviction |

---

#### Dry-Run: Preview Drain Action

```bash
# See what will be evicted without actually doing it
kubectl drain node-a --ignore-daemonsets --dry-run=client
```

**Output:**
```
node/node-a would be cordoned
pod/app-1-abc123... would be evicted
pod/app-2-def456... would be evicted
node/node-a would be drained
```

---

#### Force Drain (For Stuck Pods)

```bash
# Force evict pods that won't drain cleanly
kubectl drain node-a --ignore-daemonsets --delete-emptydir-data --force

# Or with timeout
kubectl drain node-a --ignore-daemonsets --force --timeout=2m
```

## Real-World Scenarios

### Scenario 1: GPU Cluster with Cost Optimization

**Problem**: We have expensive GPU nodes and regular CPU nodes. We want to:
1. Use GPU only for ML workloads
2. Prevent regular apps from wasting GPU resources
3. Allow emergency scheduling if needed

**Solution**:

```bash
# Step 1: Taint GPU nodes
kubectl taint nodes gpu-node-1 gpu-node-2 workload=gpu:NoSchedule

# Step 2: Create ML deployment with toleration
cat <<EOF | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ml-training
spec:
  replicas: 2
  selector:
    matchLabels:
      app: ml
  template:
    metadata:
      labels:
        app: ml
    spec:
      containers:
      - name: pytorch
        image: pytorch/pytorch:latest
        resources:
          limits:
            nvidia.com/gpu: 1
      
      tolerations:
      - key: workload
        operator: Equal
        value: gpu
        effect: NoSchedule
      
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: node-type
                operator: In
                values:
                - gpu
EOF

# Step 3: Verify only ML pods use GPU nodes
kubectl get pods -o wide
```

---

### Scenario 2: Multi-tenant Production Cluster

**Problem**: We have multiple teams (web, data, infra) sharing a cluster. We want isolation and resource protection.

**Solution**:

```bash
# Step 1: Taint team nodes
kubectl taint nodes team-web-1 team-web-2 team=web:NoSchedule
kubectl taint nodes team-data-1 team-data-2 team=data:NoSchedule
kubectl taint nodes team-infra-1 team-infra-2 team=infra:NoSchedule

# Step 2: Deploy web team app with namespace isolation
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Namespace
metadata:
  name: team-web
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-api
  namespace: team-web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web-api
  template:
    metadata:
      labels:
        app: web-api
    spec:
      containers:
      - name: api
        image: web-api:v1.0
      
      tolerations:
      - key: team
        operator: Equal
        value: web
        effect: NoSchedule
      
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: team
                operator: In
                values:
                - web
EOF

# Step 3: Repeat for data and infra teams
# (Similar pattern with different namespaces and toleration values)
```

---

### Scenario 3: Planned Cluster Upgrade

**Problem**: We need to upgrade nodes from Kubernetes v1.24 to v1.25 without downtime.

**Solution**:

```bash
# Step 1: Preview what will be drained
kubectl drain node-a --ignore-daemonsets --dry-run=client
# Review the output

# Step 2: Drain node-a (evict all pods)
kubectl drain node-a --ignore-daemonsets --delete-emptydir-data

# Step 3: Perform maintenance (SSH to node)
ssh node-a
sudo apt-get update
sudo apt-get install -y kubelet=1.25.0-00 kubeadm=1.25.0-00
sudo systemctl restart kubelet
exit

# Step 4: Verify node is healthy
kubectl get node node-a
# Wait until STATUS is Ready

# Step 5: Uncordon node
kubectl uncordon node-a

# Step 6: Verify pods are rescheduled
kubectl get pods -o wide | grep node-a

# Step 7: Repeat for other nodes
kubectl drain node-b --ignore-daemonsets --delete-emptydir-data
# ... maintenance on node-b ...
kubectl uncordon node-b
```

---

### Scenario 4: Emergency Maintenance - NoExecute Taint

**Problem**: A node has a failing disk. We need to evict running pods before it fails completely.

**Solution**:

```bash
# Step 1: Apply NoExecute taint to immediately evict all pods
kubectl taint nodes node-with-failing-disk node-issue=disk-failure:NoExecute

# Step 2: Watch pods move to other nodes
kubectl get pods -o wide --watch

# Step 3: Check node is empty
kubectl describe node node-with-failing-disk
# Look for "Pods:" section - should be empty or only system pods

# Step 4: Perform repair
ssh node-with-failing-disk
# Replace failing disk, run diagnostics, etc.

# Step 5: Remove the taint once fixed
kubectl taint nodes node-with-failing-disk node-issue=disk-failure:NoExecute-
# (Note the minus sign at the end to remove)

# Step 6: Node accepts new pods again
kubectl uncordon node-with-failing-disk
```

## Quick Reference

### Taints Commands

```bash
# Add a taint
kubectl taint nodes NODE_NAME key=value:effect

# Example: NoSchedule taint
kubectl taint nodes node-1 gpu=true:NoSchedule

# Example: PreferNoSchedule taint
kubectl taint nodes node-1 spot=true:PreferNoSchedule

# Example: NoExecute taint
kubectl taint nodes node-1 maintenance=true:NoExecute

# Remove a taint (add minus sign at end)
kubectl taint nodes NODE_NAME key=value:effect-
kubectl taint nodes node-1 gpu=true:NoSchedule-

# View taints on a node
kubectl describe node NODE_NAME | grep Taints

# List all taints in cluster
kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
```

---

### Toleration YAML Template

```yaml
tolerations:
- key: gpu                           # Must match taint key
  operator: Equal                    # Equal or Exists
  value: "true"                      # Must match taint value (if using Equal)
  effect: NoSchedule                 # NoSchedule, PreferNoSchedule, NoExecute
  tolerationSeconds: 300             # Grace period for NoExecute (seconds)
```

---

### Cordon/Uncordon Commands

```bash
# Cordon a node (block new pods)
kubectl cordon NODE_NAME

# Uncordon a node (allow new pods)
kubectl uncordon NODE_NAME

# Check if node is cordoned
kubectl get nodes
# Look for "SchedulingDisabled" in STATUS column
```

---

### Drain Commands

```bash
# Dry-run: preview what will be drained
kubectl drain NODE_NAME --ignore-daemonsets --dry-run=client

# Actually drain the node
kubectl drain NODE_NAME --ignore-daemonsets --delete-emptydir-data

# Drain with grace period
kubectl drain NODE_NAME --ignore-daemonsets --grace-period=30

# Force drain (for stubborn pods)
kubectl drain NODE_NAME --ignore-daemonsets --force --timeout=2m

# Drain only specific pods
kubectl drain NODE_NAME --pod-selector=app=web

# After maintenance, uncordon
kubectl uncordon NODE_NAME
```

---

### Taint Effects Comparison

| Effect | New Pods | Existing Pods | Use Case |
|--------|----------|---------------|----------|
| **NoSchedule** | ❌ Blocked | ✅ Run | Reserve nodes, prevent scheduling |
| **PreferNoSchedule** | ⚠️ Avoid | ✅ Run | Soft preference, use if needed |
| **NoExecute** | ❌ Blocked | ❌ Evicted | Emergency maintenance, node failure |

---

### Toleration Operators

| Operator | Meaning | Requires Value? |
|----------|---------|-----------------|
| **Equal** | Key=Value must match exactly | Yes |
| **Exists** | Key exists (any/no value) | No |

**Equal Example:**
```yaml
tolerations:
- key: gpu
  operator: Equal
  value: "true"
  effect: NoSchedule
```

**Exists Example:**
```yaml
tolerations:
- key: gpu
  operator: Exists  # Any gpu key, any value
  effect: NoSchedule
```

## Summary Table

| Concept | What | Why | When |
|---------|------|-----|------|
| **Taint** | Node label that repels pods | Reserve/isolate nodes | Setup phase |
| **Toleration** | Pod permission to run on tainted nodes | Allow specific pods on tainted nodes | Pod definition |
| **Cordon** | Block new pods (soft) | Prepare for maintenance | Before maintenance |
| **Uncordon** | Allow new pods | Resume normal operation | After maintenance |
| **Drain** | Evict all pods + cordon (hard) | Clean maintenance | Major upgrades |

## Troubleshooting

### Pod Stuck in Pending After Taint Added

```bash
# Check why pod is pending
kubectl describe pod POD_NAME

# Look for "Taint Toleration" in Events section

# Solution: Add matching toleration to pod spec
# or remove taint: kubectl taint nodes NODE_NAME key=value:effect-
```

---

### Node Not Draining - Pods Won't Evict

```bash
# Check which pods are blocking drain
kubectl drain NODE_NAME --ignore-daemonsets --dry-run=client

# Force drain with timeout
kubectl drain NODE_NAME --ignore-daemonsets --force --timeout=1m

# Or delete problematic pod directly
kubectl delete pod POD_NAME --grace-period=0 --force
```

### Check Current Taints and Tolerations

```bash
# View all taints
kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints

# View pod tolerations
kubectl get pod POD_NAME -o yaml | grep -A 10 tolerations

# Or describe
kubectl describe pod POD_NAME | grep -A 10 Tolerations
```

## Conclusion

- **Taints & Tolerations** = Fine-grained pod scheduling control
- **Cordon** = Soft node isolation (existing pods stay)
- **Uncordon** = Resume normal operation
- **Drain** = Hard node isolation (all pods evicted)
