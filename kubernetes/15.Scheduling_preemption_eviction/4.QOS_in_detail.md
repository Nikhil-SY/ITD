# Kubernetes QoS (Quality of Service) — Detailed Explanation

In Kubernetes, **QoS (Quality of Service)** determines **how the kubelet prioritizes Pods during resource pressure**, especially for **eviction** when a node runs low on **memory**, **CPU**, or **ephemeral storage**.

**Important:**
QoS **does not affect scheduling** (where a Pod is placed).
It mainly affects **eviction order**.

---

# Why QoS exists

Imagine a node with **8 GiB RAM**.

Three Pods are running:

* Pod A → no resource limits
* Pod B → requests 1Gi, limit 2Gi
* Pod C → requests 2Gi, limit 2Gi

Node memory becomes full.

Which Pod should Kubernetes kill first?

QoS helps answer that.

Eviction preference:

```text
BestEffort   → evicted first
Burstable    → evicted next
Guaranteed   → evicted last
```

---

# How Kubernetes decides QoS class

QoS is calculated **per Pod**, based on **all containers’ `resources.requests` and `resources.limits`**.

Check QoS:

```bash
kubectl get pod <pod-name> -o jsonpath='{.status.qosClass}'
```

Possible values:

1. **BestEffort**
2. **Burstable**
3. **Guaranteed**

---

# 1. BestEffort QoS

## Definition

Pod has **no CPU or memory requests or limits** for **any container**.

Example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: besteffort-pod
spec:
  containers:
  - name: app
    image: nginx
```

No resources section at all.

---

## Behavior

### CPU

Can use any available CPU.

No guaranteed CPU.

May be throttled heavily.

### Memory

Can consume memory until node pressure happens.

First candidate for eviction.

---

## When to use

Good for:

* Testing
* Temporary jobs
* Debug Pods
* Non-critical workloads

Avoid for:

* Production apps
* Databases
* APIs

---

## Example scenario

Node memory full:

```text
Pod A (BestEffort)
Pod B (Burstable)
Pod C (Guaranteed)
```

Kubernetes evicts:

```text
Pod A first
```

---

# 2. Burstable QoS

## Definition

Pod has **at least one request or limit**, but **requests and limits are not equal for all CPU/memory**.

Most common QoS.

Example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: burstable-pod
spec:
  containers:
  - name: app
    image: nginx
    resources:
      requests:
        cpu: "200m"
        memory: "256Mi"
      limits:
        cpu: "500m"
        memory: "512Mi"
```

---

## Why Burstable?

Guaranteed:

```text
Needs at least 256Mi
```

Can burst up to:

```text
512Mi
```

Hence **Burstable**.

---

## Behavior

### CPU

Guaranteed minimum:

```text
200m
```

Can use up to:

```text
500m
```

If CPU busy, gets at least request.

---

### Memory

Guaranteed:

```text
256Mi
```

Can consume:

```text
512Mi
```

If exceeds limit:

```text
OOMKilled
```

---

## Eviction rule

Among Burstable Pods:

Pod using more than request is more likely evicted.

Example:

```text
Pod1 request=256Mi using 300Mi
Pod2 request=256Mi using 700Mi
```

Pod2 likely evicted first.

---

## When to use

Best for:

* Web applications
* APIs
* Microservices
* Most production workloads

Most common choice.

---

# 3. Guaranteed QoS

## Definition

For **every container**:

```text
request == limit
```

for both:

* CPU
* Memory

Example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: guaranteed-pod
spec:
  containers:
  - name: app
    image: nginx
    resources:
      requests:
        cpu: "500m"
        memory: "512Mi"
      limits:
        cpu: "500m"
        memory: "512Mi"
```

---

## Requirements

Both CPU and memory must be set.

And must be equal.

Wrong example:

```yaml
requests:
  cpu: "500m"
  memory: "512Mi"
limits:
  cpu: "500m"
  memory: "1Gi"
```

This becomes **Burstable**, not Guaranteed.

---

## Behavior

Strongest protection.

Last to be evicted.

Ideal for critical workloads.

---

## CPU behavior

Guaranteed dedicated CPU share.

---

## Memory behavior

Guaranteed memory reservation.

Still can be killed only if exceeding limit or extreme node failure.

---

## When to use

Best for:

* Databases
* Critical services
* Stateful apps
* Payment systems
* Core infrastructure

---

# Comparison Table

| Feature         | BestEffort | Burstable       | Guaranteed    |
| --------------- | ---------- | --------------- | ------------- |
| Requests set    | No         | Yes             | Yes           |
| Limits set      | No         | Optional        | Yes           |
| Request = Limit | No         | Not necessarily | Yes           |
| Eviction risk   | Highest    | Medium          | Lowest        |
| Production use  | Rare       | Most common     | Critical apps |

# Important interview point

QoS is **Pod-level**, but calculated from **all containers**.

Example:

Container 1:

```yaml
request=limit
```

Container 2:

```yaml
no resources
```

Entire Pod becomes:

```text
Burstable
```

Not Guaranteed.

# Interview-style answer

**Q: What is Kubernetes QoS?**

**Answer:**
QoS (Quality of Service) in Kubernetes determines Pod eviction priority during node resource pressure. Kubernetes assigns one of three classes:

* **BestEffort** → no requests/limits, evicted first
* **Burstable** → requests/limits set but not equal, medium priority
* **Guaranteed** → requests equal limits for CPU and memory, evicted last

QoS helps Kubernetes protect critical workloads when resources are scarce.
