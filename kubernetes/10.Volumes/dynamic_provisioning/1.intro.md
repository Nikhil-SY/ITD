# Dynamic Provisioning in Kubernetes (Detailed)

Dynamic Provisioning solves a major storage problem in Kubernetes: **automatic creation of storage when a pod requests it.**

Without dynamic provisioning, admins must manually create **PersistentVolumes (PV)** first.

With dynamic provisioning, Kubernetes creates the storage **automatically** when a **PersistentVolumeClaim (PVC)** is created.

---

# 1. Why Dynamic Provisioning is Needed

## Problem with Static Provisioning

Traditional way:

```text
Admin creates disk manually
        ↓
Creates PersistentVolume (PV)
        ↓
Developer creates PVC
        ↓
PVC binds to PV
```

Example:

Developer wants **10Gi storage**.

Admin must:

* Create EBS disk in AWS
* Create PV YAML
* Apply PV

Then PVC can use it.

Problems:

* Manual effort
* Slow
* Admin bottleneck
* Hard to scale
* Wastage (unused PVs)

---

# 2. Dynamic Provisioning Concept

Instead of manually creating PV:

```text
Developer creates PVC
        ↓
PVC references StorageClass
        ↓
Kubernetes talks to storage provider
        ↓
Creates disk automatically
        ↓
Creates PV automatically
        ↓
PVC gets bound
        ↓
Pod uses storage
```

Admin only needs to define **StorageClass** once.

---

# 3. Core Components Involved

Dynamic provisioning involves these:

### 1. Pod

Application needing storage.

---

### 2. PVC (PersistentVolumeClaim)

Storage request.

Example:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
  storageClassName: gp2
```

PVC says:

> "I need 5Gi storage using gp2 storage class"

---

### 3. StorageClass (Most Important)

Defines **how storage should be created**.

Example:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp2
provisioner: kubernetes.io/aws-ebs
parameters:
  type: gp2
```

StorageClass tells Kubernetes:

* Which storage backend to use
* Disk type
* Performance options
* Reclaim policy
* Binding behavior

Think:

```text
PVC = What I need
StorageClass = How to create it
PV = Actual created storage
```

---

### 4. Provisioner

Component that creates storage.

Examples:

* AWS EBS provisioner
* Azure Disk provisioner
* GCE PD provisioner
* CSI drivers

Provisioner talks to cloud API.

Example:

```text
Create 10Gi EBS volume
Attach to node
Return volume ID
```

---

### 5. PersistentVolume (PV)

Created automatically.

You usually don’t create this manually in dynamic provisioning.

---

# 4. Complete Flow (Step by Step)

## Step 1: Admin creates StorageClass

Example:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-storage
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
allowVolumeExpansion: true
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
```

---

## Step 2: Developer creates PVC

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-pvc
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: fast-storage
  resources:
    requests:
      storage: 20Gi
```

---

## Step 3: PVC stays Pending briefly

Check:

```bash
kubectl get pvc
```

Output:

```text
mysql-pvc   Pending
```

---

## Step 4: Kubernetes sees StorageClass

It checks:

```text
storageClassName = fast-storage
```

Finds matching StorageClass.

---

## Step 5: Provisioner creates disk

For AWS:

```text
Create EBS volume of 20Gi
Type = gp3
```

Cloud API call happens.

---

## Step 6: Kubernetes auto creates PV

Example auto-generated PV:

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pvc-abc123
spec:
  capacity:
    storage: 20Gi
```

---

## Step 7: PVC binds to PV

Status becomes:

```bash
kubectl get pvc
```

```text
mysql-pvc   Bound
```

---

## Step 8: Pod mounts PVC

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mysql
spec:
  containers:
  - name: mysql
    image: mysql
    volumeMounts:
    - mountPath: /var/lib/mysql
      name: mysql-storage

  volumes:
  - name: mysql-storage
    persistentVolumeClaim:
      claimName: mysql-pvc
```

# 5. StorageClass Explained Deeply

---

## provisioner

Defines plugin that creates storage.

Examples:

```yaml
provisioner: ebs.csi.aws.com
```

AWS EBS CSI driver.

---

## parameters

Provider-specific settings.

AWS example:

```yaml
parameters:
  type: gp3
  fsType: ext4
```

Azure:

```yaml
parameters:
  skuName: Premium_LRS
```

---

## reclaimPolicy

What happens after PVC deletion.

### Delete

```yaml
reclaimPolicy: Delete
```

Deletes:

* PVC
* PV
* Cloud disk

Good for temporary workloads.

---

### Retain

```yaml
reclaimPolicy: Retain
```

Keeps disk.

Useful for databases.

---

## allowVolumeExpansion

Allows resizing.

```yaml
allowVolumeExpansion: true
```

Later:

```yaml
storage: 50Gi
```

Disk expands automatically.

---

## volumeBindingMode

Very important.

### Immediate

Storage created immediately.

```yaml
volumeBindingMode: Immediate
```

Problem:

Could create disk in wrong availability zone.

---

### WaitForFirstConsumer

Best practice.

```yaml
volumeBindingMode: WaitForFirstConsumer
```

Storage created only when pod is scheduled.

Benefits:

* Correct zone
* Better placement

---

# 6. CSI Drivers (Modern Standard)

Older:

```text
kubernetes.io/aws-ebs
```

Deprecated.

Modern:

```text
ebs.csi.aws.com
```

CSI = **Container Storage Interface**

Benefits:

* Standardized
* External plugins
* Easier upgrades
* Rich features

Examples:

* AWS EBS CSI
* Azure Disk CSI
* GCE CSI
* NFS CSI
* Ceph CSI

# 7. Full Example (End to End)

## StorageClass

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ebs
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
allowVolumeExpansion: true
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
```

---

## PVC

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: fast-ebs
  resources:
    requests:
      storage: 10Gi
```

---

## Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: demo
  template:
    metadata:
      labels:
        app: demo
    spec:
      containers:
      - name: app
        image: nginx
        volumeMounts:
        - mountPath: /data
          name: storage
      volumes:
      - name: storage
        persistentVolumeClaim:
          claimName: app-data
```

# 9. Common Issues

## PVC Pending

Reasons:

* StorageClass missing
* Wrong storageClassName
* CSI driver not installed
* Cloud permission issue

---

## No default StorageClass

Check:

```bash
kubectl get storageclass
```

Look for:

```text
(default)
```

---

## Zone mismatch

Use:

```yaml
volumeBindingMode: WaitForFirstConsumer
```

---

## Access mode unsupported

Example:

```yaml
ReadWriteMany
```

AWS EBS doesn't support RWX.

---

# 10. Static vs Dynamic Provisioning

| Feature           | Static  | Dynamic   |
| ----------------- | ------- | --------- |
| PV creation       | Manual  | Automatic |
| Admin effort      | High    | Low       |
| Speed             | Slow    | Fast      |
| Scalability       | Poor    | Excellent |
| Cloud integration | Limited | Excellent |

---

# Interview One-Liner

**Dynamic provisioning in Kubernetes automatically creates and binds storage volumes through a StorageClass when a PVC is created, eliminating the need for manual PV creation.**

# Easy Memory Trick

```text
StorageClass = Blueprint
PVC = Request
Provisioner = Builder
PV = Actual Disk
Pod = User
```

Flow:

```text
Pod → PVC → StorageClass → Provisioner → PV → Mounted to Pod
```
