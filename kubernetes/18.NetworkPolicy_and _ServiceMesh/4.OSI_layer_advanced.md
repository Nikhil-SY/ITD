## 1. What is the OSI Model?

### The Problem It Solves

Imagine you want computers made by different companies, running different software, connected by different physical cables, to all communicate reliably. Before the OSI model, every vendor had their own proprietary networking stack — IBM's network couldn't talk to DEC's network.

In 1984, the **International Organization for Standardization (ISO)** published the **OSI Model** (Open Systems Interconnection) — a universal framework that breaks networking into 7 distinct layers. Each layer has a specific job and talks only to the layer directly above and below it.

### The Postal System Analogy

Think of sending a letter internationally:

```
You (sender) want to send a letter to someone in Japan.

What actually happens:
1. You WRITE the letter          ← Application (what you want to say)
2. You TRANSLATE to Japanese     ← Presentation (format/language)
3. You address the envelope      ← Session (conversation tracking)
4. Post office VERIFIES delivery ← Transport (reliable delivery)
5. Sorting center ROUTES it      ← Network (which country/city)
6. Mail truck CARRIES bags       ← Data Link (node to node)
7. Road/airplane MOVES it        ← Physical (actual medium)

At the destination, the process is REVERSED.
The recipient reads it in their language.
```

This is exactly how OSI works — each layer adds a "wrapper" going down, and unwraps it going up.

### Why Developers and DevOps Engineers Need to Know This

- When a Kubernetes pod can't reach another pod → which layer is broken?
- When a TLS handshake fails → which layer? (Layer 6)
- When a NetworkPolicy blocks traffic → which layer? (Layer 3/4)
- When you configure an Ingress controller → which layer? (Layer 7)
- Understanding BGP (used by Kubernetes CNI plugins) → Layer 3

### Data Units at Each Layer

Each layer has a specific name for the chunk of data it handles:

```
Layer 7 (Application)   → Data
Layer 6 (Presentation)  → Data

Layer 4 (Transport)     → Segment (TCP) or Datagram (UDP)
Layer 3 (Network)       → Packet
Layer 2 (Data Link)     → Frame
Layer 1 (Physical)      → Bits (0s and 1s)
```

## 3. Layer-by-Layer Deep Dive

---

### Layer 1 — Physical

#### What

The **physical layer** is the raw transmission medium — the actual hardware that carries electrical signals, light pulses, or radio waves. It deals in **bits** (0s and 1s).

It has absolutely no understanding of what the data means. It just converts bits to signals and signals to bits.

#### Why

Without a physical medium, there is no communication at all. This layer is the foundation everything else builds on.

#### How

```
Physical media types:

Copper wire (Ethernet)
  Bit 0 → Low voltage (~0V)
  Bit 1 → High voltage (~5V)
  ┌────┐    ┌────┐    ┌────┐
  │    │    │    │    │    │    = 1 0 1 0 1 1 ...
──┘    └────┘    └────┘    └──

Fiber optic cable
  Bit 0 → No light pulse
  Bit 1 → Light pulse (laser)
  Transmission speed: up to 100 Gbps over km distances

Wi-Fi (radio waves)
  Uses 2.4 GHz or 5 GHz radio frequency bands
  Encodes bits as variations in wave amplitude/frequency
```

#### Real Components

- Ethernet cables (Cat5e, Cat6, Cat7)
- Fiber optic cables (single-mode, multi-mode)
- Network Interface Cards (NICs) — the hardware in your laptop
- Wi-Fi antennas
- Repeaters and hubs

#### What Can Go Wrong (Troubleshooting)

```bash
# Check if physical NIC is detected
ip link show
# eth0: <NO-CARRIER>   ← Cable is unplugged (Layer 1 problem!)
# eth0: <BROADCAST>    ← Physical layer is working
```

### Layer 2 — Data Link

#### What

The data link layer handles **node-to-node** communication — moving data between two directly connected devices on the **same local network**. It uses **MAC addresses** (Media Access Control) for addressing.

Think of it as the delivery system within a single building — it knows which room (device) to deliver to, but only within the building.

#### Why

- Without Layer 2, you couldn't distinguish between multiple devices on the same wire
- It detects transmission errors (bit corruption)
- It controls who gets to transmit on a shared medium (CSMA/CD for Ethernet)

#### How — MAC Addresses

Every network interface has a globally unique **MAC address** burned in at the factory:

```
MAC Address format:  AA:BB:CC:DD:EE:FF
                     ──────────  ──────────
                     Manufacturer Device ID
                     (OUI)

Example: 
  00:1A:2B:3C:4D:5E
  00:1A:2B = Apple Inc. (OUI)
  3C:4D:5E = Unique device ID
```

MAC addresses are **flat** (no hierarchy, no routing) — they only work on the local network segment.

#### The Ethernet Frame

Layer 2 wraps data into a **frame**:

```
Ethernet Frame Structure:
┌──────────┬──────────┬──────┬─────────────────┬─────┐
│  Dest    │  Source  │ Type │    Payload       │ FCS │
│  MAC     │  MAC     │      │  (IP Packet)     │     │
│ (6 bytes)│ (6 bytes)│(2B)  │  (up to 1500B)  │(4B) │
└──────────┴──────────┴──────┴─────────────────┴─────┘

FCS = Frame Check Sequence (error detection — a checksum)
Type = 0x0800 for IPv4, 0x0806 for ARP, 0x86DD for IPv6
```

#### ARP — How Layer 2 Finds MAC Addresses

**ARP (Address Resolution Protocol)** bridges Layer 2 and Layer 3. When you know someone's IP address but not their MAC address, ARP finds it:

```
Computer A (IP: 192.168.1.10) wants to send to Computer B (IP: 192.168.1.20)
Computer A doesn't know B's MAC address yet.

Step 1: A broadcasts ARP Request to EVERYONE on the network:
  "Who has IP 192.168.1.20? Tell 192.168.1.10"
  Destination MAC: FF:FF:FF:FF:FF:FF (broadcast — everyone receives it)

Step 2: Only B responds with ARP Reply:
  "192.168.1.20 is at MAC AA:BB:CC:DD:EE:FF"

Step 3: A stores this in its ARP cache:
  192.168.1.20 → AA:BB:CC:DD:EE:FF (cached for ~20 minutes)

Step 4: A can now send frames directly to B's MAC address.
```

```bash
# View ARP cache on Linux
arp -n
# Address          HWtype  HWaddress           Flags
# 192.168.1.1      ether   a4:c3:f0:01:23:45   C
# 192.168.1.20     ether   00:1a:2b:3c:4d:5e   C
```

#### Layer 2 Devices

- **Switch** — learns which MAC addresses are on which port, forwards frames intelligently
- **Bridge** — connects two network segments

### Layer 3 — Network

#### What

The network layer handles **end-to-end** routing across multiple networks. It uses **IP addresses** for addressing and **routers** to forward packets between networks.

If Layer 2 is delivery within a building, Layer 3 is the postal system that routes mail between cities and countries.

#### Why

MAC addresses only work on the local network. When you access Google's servers across the internet, your packet crosses dozens of different networks, each with its own switches and MAC addresses. IP addresses provide a globally routable, hierarchical addressing system.

#### How — IP Addresses and Subnets

```
IPv4 Address: 192.168.1.100
  Written as 4 octets (8 bits each) in decimal
  Binary:     11000000.10101000.00000001.01100100

Subnet Mask: 255.255.255.0  (or /24 in CIDR notation)
  Binary:     11111111.11111111.11111111.00000000
              ─────────────────────────  ─────────
              Network portion (24 bits)  Host portion (8 bits)

This means:
  Network address: 192.168.1.0   (the network itself)
  Host range:      192.168.1.1 - 192.168.1.254 (254 usable hosts)
  Broadcast:       192.168.1.255 (sent to everyone on this network)
```

#### The IP Packet

```
IPv4 Packet Header:
┌──────┬──────┬──────────┬────────────────────────────────────┐
│ Ver  │ IHL  │   TTL    │  Protocol (6=TCP, 17=UDP, 1=ICMP)  │
├──────┴──────┴──────────┼────────────────────────────────────┤
│    Source IP Address   │   Destination IP Address           │
│    (4 bytes)           │   (4 bytes)                        │
├────────────────────────┴────────────────────────────────────┤
│                     Payload (TCP Segment)                    │
└─────────────────────────────────────────────────────────────┘

TTL (Time To Live):
  Each router that forwards the packet decrements TTL by 1
  When TTL = 0, the packet is discarded (prevents infinite loops)
  Typical starting value: 64 or 128
```

#### Routing — How Packets Find Their Way

A router has a **routing table** — a map of which direction to send packets:

```
Router's Routing Table:
┌──────────────────┬─────────────┬───────────────┬──────────┐
│ Destination      │ Subnet Mask │ Gateway       │ Interface│
├──────────────────┼─────────────┼───────────────┼──────────┤
│ 192.168.1.0      │ /24         │ (directly)    │ eth0     │
│ 10.0.0.0         │ /8          │ (directly)    │ eth1     │
│ 0.0.0.0          │ /0          │ 203.0.113.1   │ eth2     │  ← Default route
└──────────────────┴─────────────┴───────────────┴──────────┘

When a packet arrives for 8.8.8.8:
1. Check: 8.8.8.8 matches 192.168.1.0/24? No
2. Check: 8.8.8.8 matches 10.0.0.0/8? No
3. Check: 8.8.8.8 matches 0.0.0.0/0? YES (default — matches everything)
   → Forward to 203.0.113.1 (the internet gateway)
```

#### ICMP — The Diagnostic Protocol

```bash
# ICMP lives at Layer 3
ping 8.8.8.8
# Sends ICMP Echo Request → Google responds with ICMP Echo Reply

traceroute 8.8.8.8
# Sends packets with TTL=1, TTL=2, TTL=3...
# Each router that discards the packet sends back ICMP Time Exceeded
# This reveals every hop along the path
```

### Layer 4 — Transport

#### What

The transport layer manages **end-to-end communication between applications** (not just machines). It introduces **port numbers** to identify which application on a machine should receive the data.

If Layer 3 gets a packet to the right machine, Layer 4 gets it to the right **door** (application) on that machine.

#### Why

A machine runs many applications simultaneously — a web server, a database, an SSH server. Without ports, the OS wouldn't know whether an incoming packet is for the web server (port 80) or the SSH server (port 22).

#### Port Numbers

```
Port ranges:
  0 – 1023:     Well-known ports (require root to bind)
  1024 – 49151: Registered ports
  49152 – 65535: Dynamic/ephemeral ports (clients use these as source)

Common well-known ports:
  20, 21   → FTP
  22       → SSH
  25       → SMTP (email sending)
  53       → DNS
  80       → HTTP
  443      → HTTPS (HTTP over TLS)
  3306     → MySQL
  5432     → PostgreSQL
  6379     → Redis
  27017    → MongoDB

A connection is identified by a 4-tuple:
  (Source IP, Source Port, Destination IP, Destination Port)
  Example: (10.0.0.5, 54321, 93.184.216.34, 443)
```

#### TCP vs UDP

The two main transport protocols have very different philosophies:

```
TCP (Transmission Control Protocol)     UDP (User Datagram Protocol)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Connection-oriented                     Connectionless
3-way handshake before data             Fire and forget
Guaranteed delivery                     No delivery guarantee
Ordered packets                         Packets may arrive out of order
Error correction (retransmit)           No retransmission
Flow control & congestion control       No flow control
Slower (overhead for reliability)       Faster (less overhead)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Use cases:                              Use cases:
  Web (HTTP/HTTPS)                        Video streaming
  Email                                   Online gaming
  File transfer                           DNS queries
  Kubernetes API                          VoIP
  SSH                                     WebRTC
```

#### TCP Segment Structure

```
TCP Segment Header:
┌──────────────────────┬──────────────────────┐
│   Source Port        │   Destination Port   │
│   (16 bits)          │   (16 bits)          │
├──────────────────────┴──────────────────────┤
│         Sequence Number (32 bits)           │
├─────────────────────────────────────────────┤
│         Acknowledgment Number (32 bits)     │
├────────┬────────────────────────────────────┤
│ Offset │  Flags: SYN, ACK, FIN, RST, PSH   │
├────────┴────────────────────────────────────┤
│    Window Size    │   Checksum              │
├───────────────────┴─────────────────────────┤
│                  Payload                    │
└─────────────────────────────────────────────┘

Key flags:
  SYN = Synchronize (start connection)
  ACK = Acknowledge (I received your data)
  FIN = Finish (close connection gracefully)
  RST = Reset (forcefully terminate)
```

### Layer 5 — Session

#### What

The session layer manages **dialogues** between applications — establishing, maintaining, and terminating communication sessions. It adds control over when a session starts, when it pauses, and when it ends.

#### Why

Consider downloading a large file over an unreliable connection. If the connection drops midway, should you restart from the beginning? Session layer mechanisms allow **checkpointing** — resuming from where you left off.

#### Real-World Examples

```
Session layer in practice:

1. Remote Procedure Calls (RPC)
   A program calls a function on another machine.
   Session layer manages: start call → wait for response → end call

2. SQL Sessions
   You connect to a database:
     - Session starts (authentication)
     - Multiple queries/transactions happen
     - Session ends (disconnect)
   The session layer maintains the context across all those queries

3. NetBIOS Sessions (legacy Windows networking)

4. HTTP/2 and HTTP/3 streams
   Multiple requests multiplexed over one connection
   Each stream is a "session" within the connection
```

#### In Modern Networks

In practice, Layer 5-7 functionality is often implemented together in the same protocol (e.g., HTTP handles sessions via cookies, TLS handles security). The distinction is conceptual but useful for understanding where session state lives.

### Layer 6 — Presentation

#### What

The presentation layer is responsible for **translating data** between the format the application uses and the format the network uses. It handles:
- **Encoding** (how to represent characters: ASCII, UTF-8, Unicode)
- **Encryption/Decryption** (TLS/SSL lives here)
- **Compression** (gzip, deflate)
- **Serialization** (converting objects to bytes: JSON, XML, Protobuf)

#### Why

Two applications might store data differently. A file encoded in UTF-8 on Linux must be readable on a Windows machine that uses a different encoding. The presentation layer handles the translation.

#### Real-World Examples

```
Encoding:
  "Hello" in ASCII: 48 65 6C 6C 6F (hex)
  "Hello" in UTF-8: same as ASCII for basic Latin characters
  "नमस्ते" in UTF-8: E0 A4 A8 E0 A4 AE E0 A4 B8 ...

Compression:
  HTTP header: "Accept-Encoding: gzip, deflate"
  Server compresses response body before sending
  Browser decompresses it after receiving
  Layer 6 concern: both sides must agree on the compression format

Encryption (TLS):
  Client → Server: data encrypted with server's public key
  Server → Client: data encrypted with session key
  (Detailed breakdown in Section 6)

Serialization:
  Your Python object → JSON string → bytes over network → 
  JSON parsed → JavaScript object on the other end
```

### Layer 7 — Application

#### What

The application layer is what **users and applications interact with directly**. It defines the protocols and rules for how applications communicate — the actual language of the conversation.

This is the highest layer. It does not refer to the application itself (like Chrome or curl), but to the **protocol** the application uses.

#### Why

Different types of applications need different communication rules. A web browser fetching a page has different needs from an email client sending mail or a DNS resolver looking up a hostname. Layer 7 protocols define these specialized rules.

#### Key Protocols

```
HTTP / HTTPS
  Client → Server: GET /index.html HTTP/1.1\r\nHost: example.com\r\n\r\n
  Server → Client: HTTP/1.1 200 OK\r\nContent-Type: text/html\r\n\r\n<html>...

DNS (Domain Name System)
  Client: "What is the IP address for google.com?"
  Server: "google.com → 142.250.80.46"

SMTP (Email sending)
  Client: EHLO myserver.com
  Server: 250 Hello
  Client: MAIL FROM: <alice@example.com>
  Client: RCPT TO: <bob@example.com>
  Client: DATA
  Client: Subject: Hello\r\n\r\nHi Bob! .\r\n
  Server: 250 OK

SSH
  Client connects to port 22
  Key exchange, authentication, encrypted shell session
  
gRPC (used heavily in Kubernetes internals)
  Based on HTTP/2
  Uses Protocol Buffers (binary serialization)
  Kubernetes API server → kubelet communication uses gRPC
```

#### HTTP in Detail

```
HTTP Request structure:
┌─────────────────────────────────────────────────┐
│  GET /api/users/123 HTTP/1.1                    │  ← Request line
│  Host: api.example.com                          │  ← Headers
│  Authorization: Bearer eyJhbGci...             │
│  Accept: application/json                       │
│  Connection: keep-alive                         │
│                                                 │  ← Blank line
│  (no body for GET)                              │  ← Body
└─────────────────────────────────────────────────┘

HTTP Response structure:
┌─────────────────────────────────────────────────┐
│  HTTP/1.1 200 OK                                │  ← Status line
│  Content-Type: application/json                 │  ← Headers
│  Content-Length: 87                             │
│  Cache-Control: max-age=3600                    │
│                                                 │  ← Blank line
│  {"id": 123, "name": "Alice", "role": "admin"} │  ← Body
└─────────────────────────────────────────────────┘
```

## 4. Complete Traffic Flow Example — Browser to Web Server

### Scenario

You type `https://shop.example.com/products` into your browser. Let's trace every layer.

```
Your Machine                                    Web Server
IP: 192.168.1.100                               IP: 93.184.216.34
MAC: AA:BB:CC:DD:EE:FF                          MAC: 11:22:33:44:55:66
```

### Sending Side (Encapsulation — adding wrappers going DOWN the stack)

```
LAYER 7 — APPLICATION
  Browser creates HTTP request:
  ┌────────────────────────────────────────────────────────┐
  │ GET /products HTTP/1.1                                 │
  │ Host: shop.example.com                                 │
  │ Accept: text/html                                      │
  └────────────────────────────────────────────────────────┘

LAYER 6 — PRESENTATION
  TLS encrypts the HTTP data using the session key:
  ┌────────────────────────────────────────────────────────┐
  │ [TLS Record Header] [Encrypted HTTP data]              │
  │  Content-Type: Application  Length: 512                │
  └────────────────────────────────────────────────────────┘

LAYER 5 — SESSION
  TLS session is established (session ID tracked).
  Connection state is maintained.

LAYER 4 — TRANSPORT
  TCP adds source and destination ports + sequence tracking:
  ┌────────────────────────────────────────────────────────┐
  │ TCP Segment                                            │
  │  Src Port: 54321   Dst Port: 443                       │
  │  Seq: 1000   Ack: 0   Flags: PSH,ACK                  │
  │  [Encrypted HTTP data]                                 │
  └────────────────────────────────────────────────────────┘

LAYER 3 — NETWORK
  IP adds source and destination IP addresses:
  ┌────────────────────────────────────────────────────────┐
  │ IP Packet                                              │
  │  Src IP: 192.168.1.100   Dst IP: 93.184.216.34        │
  │  TTL: 64   Protocol: 6 (TCP)                          │
  │  [TCP Segment]                                         │
  └────────────────────────────────────────────────────────┘

LAYER 2 — DATA LINK
  Ethernet adds source and destination MAC addresses:
  (Note: destination MAC is your ROUTER's MAC, not the web server's,
   because the web server is on a different network)
  ┌────────────────────────────────────────────────────────┐
  │ Ethernet Frame                                         │
  │  Src MAC: AA:BB:CC:DD:EE:FF  (your laptop)            │
  │  Dst MAC: FF:GG:HH:II:JJ:KK  (your router/gateway)   │
  │  [IP Packet]                                           │
  │  FCS checksum                                          │
  └────────────────────────────────────────────────────────┘

LAYER 1 — PHYSICAL
  Frame converted to electrical signals and sent over the cable.
  01101000 01110100 01110100 01110000 ... (bits)
```

### Across the Network — MAC Address Replacement at Each Hop

This is a subtle but important detail most people miss:

```
Your Laptop ─────── Router A ─────── Router B ─────── Web Server
MAC: AA:BB          MAC: FF:GG       MAC: ZZ:YY       MAC: 11:22
IP:  192.168.1.100  IP:  203.0.113.1  IP: 198.51.100.1  IP: 93.184.216.34

Hop 1: Laptop → Router A
  Src MAC: AA:BB (laptop)     Dst MAC: FF:GG (Router A's LAN port)
  Src IP:  192.168.1.100      Dst IP:  93.184.216.34
  ← IP addresses NEVER change through the journey →
  ← MAC addresses change at EVERY hop            →

Hop 2: Router A → Router B
  Src MAC: (Router A's WAN port)   Dst MAC: (Router B's port)
  Src IP:  192.168.1.100           Dst IP:  93.184.216.34

Hop 3: Router B → Web Server
  Src MAC: (Router B's port)       Dst MAC: 11:22 (Web Server)
  Src IP:  192.168.1.100           Dst IP:  93.184.216.34
```

### Receiving Side (Decapsulation — removing wrappers going UP the stack)

```
LAYER 1: Physical signals received → converted to bits
LAYER 2: Bits assembled into frame → MAC address checked → frame accepted
         → Ethernet header stripped → IP packet extracted
LAYER 3: IP packet checked → Dst IP matches → IP header stripped
         → TCP segment extracted
LAYER 4: Port 443 → send to TLS/HTTPS handler
         → TCP segment reassembled (may arrive out of order)
LAYER 5: Session ID looked up → existing TLS session found
LAYER 6: TLS decrypts payload using session key → HTTP data recovered
LAYER 7: HTTP request parsed → GET /products → web server handles request
         → Builds response → process begins in reverse
```

## 5. The TCP 3-Way Handshake

### What

Before any data can be sent over TCP, the two parties must agree to communicate and synchronize their **sequence numbers**. This is done through the **3-way handshake** — three messages exchanged before the first byte of actual data.

### Why

TCP guarantees **ordered, reliable delivery**. To track which data has been received and what to retransmit if lost, both sides need to agree on starting sequence numbers. The handshake establishes:
1. That both parties are reachable and ready
2. The starting sequence numbers on both sides
3. The connection parameters (window size, etc.)

### How — The Sequence Numbers

Sequence numbers are 32-bit integers. Each side picks its own **Initial Sequence Number (ISN)** randomly (to prevent certain attacks):

```
Client                                              Server
Port 54321                                          Port 443
ISN = 1000 (random)                                 ISN = 9000 (random)

Step 1: SYN (Synchronize)
Client → Server
┌──────────────────────────────────────────────────────┐
│ TCP Segment                                          │
│  Src Port: 54321    Dst Port: 443                   │
│  Seq: 1000          ← Client's ISN                  │
│  Ack: 0             ← No acknowledgment yet         │
│  Flags: SYN         ← "I want to connect"           │
│  Window: 65535      ← I can receive up to 65535 bytes│
└──────────────────────────────────────────────────────┘
  "Hello server, I exist. My first sequence number is 1000.
   I want to start a conversation."

         ─────────────── SYN ──────────────>

Step 2: SYN-ACK (Synchronize-Acknowledge)
Server → Client
┌──────────────────────────────────────────────────────┐
│ TCP Segment                                          │
│  Src Port: 443      Dst Port: 54321                 │
│  Seq: 9000          ← Server's ISN                  │
│  Ack: 1001          ← I received up to 1000,        │
│                        send me 1001 next            │
│  Flags: SYN, ACK    ← "I hear you AND I want to    │
│                        connect too"                 │
│  Window: 65535                                      │
└──────────────────────────────────────────────────────┘
  "I got your message (seq 1000). 
   My first sequence number is 9000.
   Send me byte 1001 next."

         <──────────── SYN-ACK ────────────

Step 3: ACK (Acknowledge)
Client → Server
┌──────────────────────────────────────────────────────┐
│ TCP Segment                                          │
│  Src Port: 54321    Dst Port: 443                   │
│  Seq: 1001          ← My next byte after the SYN   │
│  Ack: 9001          ← I received your 9000,        │
│                        send me 9001 next            │
│  Flags: ACK         ← "Got it, let's talk"          │
└──────────────────────────────────────────────────────┘
  "Confirmed. I know your ISN is 9000.
   Connection is established."

         ─────────────── ACK ──────────────>

CONNECTION ESTABLISHED — Data can now flow.
```

### Complete Timeline

```
Time →

Client                    Network                   Server
  │                                                    │
  │──── SYN (seq=1000) ──────────────────────────────>│
  │                                                    │ Server: Got SYN, 
  │                                                    │ created half-open connection
  │<─── SYN-ACK (seq=9000, ack=1001) ─────────────────│
  │                                                    │
  │ Client: Got SYN-ACK                               │
  │                                                    │
  │──── ACK (ack=9001) ──────────────────────────────>│
  │                                                    │ Server: Connection ESTABLISHED
  │                                                    │
  │══════════ DATA FLOWS HERE ════════════════════════>│
  │<═════════ DATA FLOWS HERE ═════════════════════════│
  │                                                    │
```

### The 4-Way Teardown (Closing the Connection)

Closing a TCP connection requires **4 messages** because each side closes independently:

```
Client                                              Server
  │                                                    │
  │──── FIN (seq=5000) ──────────────────────────────>│ "I'm done sending"
  │<─── ACK (ack=5001) ────────────────────────────── │ "Got it, noted"
  │                                                    │ (Server may still send data)
  │<─── FIN (seq=8000) ────────────────────────────── │ "I'm done sending too"
  │──── ACK (ack=8001) ──────────────────────────────>│ "Got it"
  │                                                    │
                          CONNECTION CLOSED
```

### SYN Flood Attack — Why This Matters for Security

```
Normal 3-way handshake:
  Client sends SYN → Server creates "half-open connection" entry (uses memory)
  Client sends ACK → Server promotes to "full connection"

SYN Flood attack:
  Attacker sends millions of SYN packets with spoofed source IPs
  Server creates millions of half-open connections → runs out of memory
  Legitimate clients can't connect (DDoS attack)

Defense: SYN Cookies
  Server doesn't allocate memory for half-open connections
  Instead, encodes connection info in the SYN-ACK sequence number
  Only allocates memory when the final ACK arrives
```

## 6. TLS/SSL — Encryption and Decryption

### What

**TLS (Transport Layer Security)** — formerly called SSL — is the protocol that provides:
- **Confidentiality**: Nobody intercepting the traffic can read it
- **Integrity**: The data hasn't been tampered with in transit
- **Authentication**: You're really talking to the server you think you are (not an imposter)

When you see `https://` in your browser and a padlock icon, TLS is working.

### Why

The internet is a shared, public network. Without encryption:
- Your ISP can read everything you send
- Anyone on a public Wi-Fi network can intercept your passwords
- An attacker between you and the server (Man-in-the-Middle) can alter the response

### The Core Cryptography Concepts

Before the TLS handshake makes sense, you need to understand two types of encryption:

#### Asymmetric Encryption (Public Key Cryptography)

```
Every party has a KEY PAIR:
  Public Key:  Share it with EVERYONE — it's fine if anyone sees it
  Private Key: NEVER share — kept completely secret

The magic:
  Anything encrypted with the PUBLIC KEY can ONLY be decrypted by the PRIVATE KEY
  Anything signed with the PRIVATE KEY can be VERIFIED by the PUBLIC KEY

Analogy: A mailbox
  Public Key  = the slot in the mailbox (anyone can drop mail in)
  Private Key = the key to open the mailbox (only you can read the mail)

Example:
  Server has: Private Key (secret) + Public Key (in certificate)
  Client gets: Server's Public Key from the certificate
  
  Client encrypts message with Server's Public Key
  → Only Server can decrypt it (only Server has the Private Key)
```

#### Symmetric Encryption

```
Both parties share the SAME secret key.
  Encrypting: plaintext + key → ciphertext
  Decrypting: ciphertext + key → plaintext

MUCH faster than asymmetric encryption
Problem: How do you share the key securely in the first place?
Answer: Use asymmetric encryption to exchange the symmetric key!
```

### TLS Handshake — Step by Step (TLS 1.3)

```
CLIENT                                              SERVER
Browser                                         shop.example.com
  │                                                    │
  │ Step 1: ClientHello                                │
  │──────────────────────────────────────────────────>│
  │  "I support TLS 1.3"                               │
  │  "I support these cipher suites:"                  │
  │    - TLS_AES_256_GCM_SHA384                        │
  │    - TLS_CHACHA20_POLY1305_SHA256                  │
  │  "My random number: 0xA3F2..."  (client random)    │
  │  "My key share: [Diffie-Hellman public value]"     │
  │                                                    │
  │ Step 2: ServerHello                                │
  │<──────────────────────────────────────────────────│
  │  "Let's use TLS 1.3"                               │
  │  "Let's use TLS_AES_256_GCM_SHA384"                │
  │  "My random number: 0x8B71..."  (server random)    │
  │  "My key share: [Diffie-Hellman public value]"     │
  │                                                    │
  │  ↑ Both sides now compute the SAME session key     │
  │    using Diffie-Hellman math (without sending      │
  │    the key over the network!)                      │
  │                                                    │
  │ Step 3: Server Certificate + Finished              │
  │<──────────────────────────────────────────────────│
  │  Certificate:                                      │
  │    Subject: shop.example.com                       │
  │    Public Key: [server's RSA/EC public key]        │
  │    Signed by: DigiCert (Certificate Authority)     │
  │    Valid: 2025-01-01 to 2026-01-01                 │
  │  "Finished" (MAC to prove no tampering)            │
  │                                                    │
  │  Client verifies certificate:                      │
  │  ✓ Is the domain name correct?                     │
  │  ✓ Is it signed by a trusted CA?                   │
  │  ✓ Is it expired?                                  │
  │  ✓ Is it revoked? (OCSP check)                     │
  │                                                    │
  │ Step 4: Client Finished                            │
  │──────────────────────────────────────────────────>│
  │  "Finished" (MAC to prove no tampering)            │
  │                                                    │
  │══════════ ENCRYPTED DATA FLOWS HERE ══════════════│
  │  HTTP requests and responses now encrypted         │
  │  with the shared symmetric session key             │
  │                                                    │
```

### Diffie-Hellman Key Exchange — The Magic Explained

This is how two parties agree on a secret without ever sending the secret itself:

```
The "paint mixing" analogy:

1. Alice and Bob agree on a common color: YELLOW (public knowledge)

2. Alice picks a secret color: RED
   Alice mixes YELLOW + RED = ORANGE → sends ORANGE to Bob

3. Bob picks a secret color: BLUE
   Bob mixes YELLOW + BLUE = GREEN → sends GREEN to Alice

4. Alice takes GREEN (from Bob) + her secret RED = DARK COLOR
   Bob takes ORANGE (from Alice) + his secret BLUE = DARK COLOR

Both get the SAME DARK COLOR without ever revealing their secret colors!
An eavesdropper only saw YELLOW, ORANGE, GREEN — can't determine the secret.

In math, this uses modular exponentiation instead of paint, but the principle is identical.
```

### Certificate Authorities — How Trust Works

```
Certificate Authority (CA) Chain of Trust:

Root CA (DigiCert Root)
  └── Intermediate CA (DigiCert EV RSA CA)
        └── Server Certificate (shop.example.com)

Your browser ships with ~150 ROOT CA certificates pre-installed.
These are trusted by default (the "trust anchors").

When you connect to shop.example.com:
  Server presents: [its cert] + [intermediate CA cert]
  Browser verifies:
    shop.example.com cert signed by DigiCert Intermediate?  ✓
    DigiCert Intermediate cert signed by DigiCert Root?     ✓
    DigiCert Root is in my trusted root store?              ✓
  → TRUST ESTABLISHED

If ANY link in the chain is broken or unrecognized:
  Browser shows: "Your connection is not private" (NET::ERR_CERT_AUTHORITY_INVALID)
```

### Encryption and Decryption in Practice

```
After TLS handshake, both sides have: SESSION KEY = 0x4A8F2B9C... (256-bit AES key)

SENDING (Encryption):
  Plaintext: "GET /products HTTP/1.1\r\nHost: shop.example.com"
  
  AES-GCM encryption:
    Key:    SESSION KEY
    Nonce:  0x000000000001 (increments with each message — prevents replay)
    Input:  Plaintext bytes
    Output: Ciphertext + Authentication Tag
  
  What goes over the wire:
  [TLS Record Header] [Ciphertext: 3f8a2b1c9d...] [Auth Tag: a4f2...]

RECEIVING (Decryption):
  Browser receives ciphertext + auth tag
  
  AES-GCM decryption:
    Key:    SESSION KEY (same one)
    Nonce:  0x000000000001 (must match)
    Verifies: Auth Tag → confirms data wasn't tampered with
    Decrypts: Ciphertext → Plaintext
  
  Result: "HTTP/1.1 200 OK\r\nContent-Type: text/html..."
```

### TLS 1.2 vs TLS 1.3 — Key Differences

```
TLS 1.2 Handshake (older):
  Client Hello → Server Hello → Certificate → ServerHelloDone
  → ClientKeyExchange → [ChangeCipherSpec] → Finished (client)
  → [ChangeCipherSpec] → Finished (server)
  → Data flows
  
  Latency: 2 Round-Trip Times (RTTs) before data flows
  Weakness: Supports older, weaker cipher suites (RC4, MD5, SHA-1)

TLS 1.3 Handshake (current standard):
  Client Hello (with key share) → Server Hello + Cert + Finished
  → Client Finished → Data flows
  
  Latency: 1 RTT before data flows (MUCH faster)
  0-RTT: Resuming sessions can start sending data immediately
  Removed: All weak cipher suites. Only forward-secret suites allowed.
  Result: Faster AND more secure than TLS 1.2
```

## 7. Sticky Sessions

### What

By default, a load balancer distributes each incoming request to a different backend server (round-robin or least-connections). **Sticky sessions** (also called **session affinity**) ensures that once a user's request is sent to a particular backend, **all subsequent requests from that same user go to the SAME backend**.

### Why — The Session State Problem

Imagine a shopping website with 3 backend servers. You add items to your cart:

```
WITHOUT STICKY SESSIONS:
Request 1 (Add item A to cart)    → Server 1  [Server 1's memory: cart = {A}]
Request 2 (Add item B to cart)    → Server 2  [Server 2's memory: cart = {}!]
Request 3 (View cart)             → Server 3  [Server 3: cart = {} — empty!]

Server 1 stored your cart in its LOCAL MEMORY.
Servers 2 and 3 know nothing about it.
Your cart appears empty on the next request!

WITH STICKY SESSIONS:
Request 1 (Add item A to cart)    → Server 1  [Server 1: cart = {A}]
Request 2 (Add item B to cart)    → Server 1  [Server 1: cart = {A, B}]
Request 3 (View cart)             → Server 1  [Server 1: cart = {A, B} ✓]
```

### How Sticky Sessions Work — Cookie-Based (Most Common)

```
CLIENT                    LOAD BALANCER              SERVERS
  │                            │                         │
  │── Request 1 (no cookie) ──>│                         │
  │                            │── Forward to Server 2 ─>│
  │                            │<── Response ────────────│
  │<── Response                │                         │
  │    Set-Cookie:             │                         │
  │    SERVERID=server2;       │                         │   ← LB adds this cookie
  │    path=/                  │                         │
  │                            │                         │
  │── Request 2 ──────────────>│                         │
  │   Cookie: SERVERID=server2 │                         │
  │                            │── Forward to Server 2 ─>│  ← LB reads cookie,
  │                            │<── Response ────────────│    routes to Server 2
  │<── Response ───────────────│                         │
  │                            │                         │
  │── Request 3 ──────────────>│                         │
  │   Cookie: SERVERID=server2 │── Forward to Server 2 ─>│  ← Always Server 2
  │                            │<── Response ────────────│
  │<── Response ───────────────│                         │
```

### How Sticky Sessions Work — IP Hash

An alternative to cookies — the load balancer hashes the client's IP address to always map to the same server:

```
Client IP: 192.168.1.100
Hash function: hash(192.168.1.100) % 3 = 1
→ Always goes to Server index 1

Client IP: 192.168.1.200
Hash function: hash(192.168.1.200) % 3 = 2
→ Always goes to Server index 2

Problem: If a client is behind a NAT (many users share one IP, e.g., corporate network)
→ all users behind that NAT go to the same server (load imbalance)
```

### The Problem with Sticky Sessions — Why to Avoid If Possible

```
Server 2 crashes:

WITHOUT STICKY: Load balancer immediately sends users to Server 1 or 3
                Minor disruption (session data lost but new session created quickly)

WITH STICKY:    Users that were sticky to Server 2 now have no server
                Load balancer must pick a new server → session state is LOST anyway
                AND the transition is messier

Scaling issues:
  You add Server 4 to handle load.
  But all existing sessions are sticky to Servers 1, 2, 3.
  Server 4 sits idle until new users arrive.

The real solution: DON'T store state in server memory.
Store session state in a SHARED EXTERNAL STORE:
  Redis / Memcached / Database

When all servers share the same session store:
  Any server can handle any request → no need for sticky sessions
  Much more resilient and scalable
```

### Sticky Sessions in Kubernetes

```yaml
# Kubernetes Service with session affinity (IP-based)
apiVersion: v1
kind: Service
metadata:
  name: shop-frontend
spec:
  selector:
    app: shop-frontend
  ports:
  - port: 80
    targetPort: 8080
  sessionAffinity: ClientIP              # Sticky based on client IP
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 3600               # Session affinity lasts 1 hour
```

```yaml
# Nginx Ingress Controller with cookie-based sticky sessions
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop-ingress
  annotations:
    nginx.ingress.kubernetes.io/affinity: "cookie"
    nginx.ingress.kubernetes.io/session-cookie-name: "SHOPSERVER"
    nginx.ingress.kubernetes.io/session-cookie-expires: "172800"   # 48 hours
    nginx.ingress.kubernetes.io/session-cookie-max-age: "172800"
    nginx.ingress.kubernetes.io/session-cookie-path: "/"
spec:
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: shop-frontend
            port:
              number: 80
```

## 8. BGP — Border Gateway Protocol

### What

**BGP (Border Gateway Protocol)** is the routing protocol that makes the internet work. It is how the world's networks (called **Autonomous Systems**) exchange routing information — essentially telling each other: "To reach IP range X, send traffic through me."

BGP is called the **"protocol of the internet"** — without it, traffic couldn't find its way across the global internet.

### Why BGP Matters for Kubernetes

BGP appears in the Kubernetes world in two important places:
1. **CNI plugins** like Calico use BGP to advertise pod network routes between nodes
2. **LoadBalancer services** using MetalLB (in on-premises Kubernetes) use BGP to announce service IPs to the physical network

### The Internet is a Collection of Autonomous Systems

```
The internet is NOT one big network.
It's thousands of smaller networks (Autonomous Systems) connected together.

Autonomous System (AS): A network under a single administrative control
  Each AS has a globally unique ASN (Autonomous System Number)

Examples:
  AS15169 = Google
  AS7018  = AT&T
  AS3356  = Lumen (formerly CenturyLink, a major transit provider)
  AS2914  = NTT Communications
  AS13335 = Cloudflare

         ┌──────────────┐          ┌──────────────┐
         │  Google      │◄────────►│  AT&T        │
         │  AS15169     │          │  AS7018      │
         └──────────────┘          └──────────────┘
                │                         │
                ▼                         ▼
         ┌──────────────┐          ┌──────────────┐
         │  Lumen        │◄────────►│  NTT          │
         │  AS3356       │          │  AS2914       │
         └──────────────┘          └──────────────┘
                │
                ▼
         ┌──────────────┐
         │  Your ISP    │
         │  AS12345     │
         └──────────────┘
                │
                ▼
         Your Home Network
```

### How BGP Works — Path Vector Protocol

BGP is a **path vector protocol** — it doesn't just share distance to a destination, it shares the **entire path** (list of ASes) to reach it. This allows loops to be detected (if your own ASN appears in the path, reject it).

```
BGP Announcement example:

Google (AS15169) announces:
  "I own IP range 8.8.8.0/24. Path: [15169]"

Lumen (AS3356) receives this and re-announces to its peers:
  "To reach 8.8.8.0/24, go through me then Google. Path: [3356, 15169]"

AT&T (AS7018) receives from Lumen:
  "To reach 8.8.8.0/24, go through AT&T → Lumen → Google. Path: [7018, 3356, 15169]"

Your ISP receives multiple paths:
  Via Lumen:  8.8.8.0/24 via [12345, 3356, 15169]  (2 hops)
  Via AT&T:   8.8.8.0/24 via [12345, 7018, 15169]  (2 hops)
  Via NTT:    8.8.8.0/24 via [12345, 2914, 15169]  (2 hops)

BGP picks the BEST PATH based on multiple attributes:
  1. Shortest AS path length (fewest hops)
  2. LOCAL_PREF (prefer certain peers)
  3. MED (prefer certain entry points into a neighbor AS)
  4. Other tie-breakers
```

### BGP vs OSPF — Two Types of Routing Protocols

```
OSPF (Interior Gateway Protocol — used INSIDE one AS):
  Every router knows the COMPLETE map of the network
  Calculates the mathematically shortest path (Dijkstra's algorithm)
  Shares link state (bandwidth, latency of each link)
  Fast convergence (seconds)
  Can't scale to the internet (too many routers)

BGP (Exterior Gateway Protocol — used BETWEEN AS networks):
  Routers only know PATHS to destinations, not the full topology
  Based on policy, not just shortest path
  An ISP might prefer a path through a "settlement-free peer" 
  even if it's technically longer
  Convergence is slower (minutes)
  Scales to the entire internet (millions of routes)
```

### BGP in Kubernetes — Calico CNI Example

When you run Kubernetes, pods need to communicate across nodes. Calico uses BGP to make this work:

```
Kubernetes Cluster:
  Node 1: 10.0.1.0    Pod Network: 192.168.1.0/24
  Node 2: 10.0.2.0    Pod Network: 192.168.2.0/24
  Node 3: 10.0.3.0    Pod Network: 192.168.3.0/24

Without BGP:
  Pod on Node 1 (IP: 192.168.1.5) wants to reach Pod on Node 2 (IP: 192.168.2.7)
  Node 1 doesn't know that 192.168.2.0/24 is on Node 2
  → Packet gets lost

With Calico BGP:
  Node 1's Calico agent (BGP speaker) announces:
    "192.168.1.0/24 is on me, reachable at 10.0.1.0"
  Node 2 announces:
    "192.168.2.0/24 is on me, reachable at 10.0.2.0"
  Node 3 announces:
    "192.168.3.0/24 is on me, reachable at 10.0.3.0"

  All nodes now have routing table entries:
    192.168.1.0/24 → via 10.0.1.0 (Node 1)
    192.168.2.0/24 → via 10.0.2.0 (Node 2)
    192.168.3.0/24 → via 10.0.3.0 (Node 3)

  Pod-to-pod traffic across nodes now works!
```

### BGP in Kubernetes — MetalLB (On-Premises LoadBalancer)

On cloud providers (AWS, GCP, Azure), when you create a Kubernetes Service of type `LoadBalancer`, the cloud provider automatically assigns an external IP. On-premises, there's no cloud provider to do this. MetalLB fills the gap using BGP:

```
On-Premises Kubernetes + MetalLB:

1. You define an IP pool in MetalLB: 203.0.113.0/24
2. You create a Service of type LoadBalancer:
   kubectl expose deployment shop --type=LoadBalancer --port=80
3. MetalLB assigns an IP: 203.0.113.10
4. MetalLB's BGP speaker announces to your physical router:
   "203.0.113.10/32 is reachable via this Kubernetes node"
5. Your physical router updates its routing table
6. External traffic for 203.0.113.10 → routed to the Kubernetes node → Service → Pod

Without MetalLB + BGP, on-premises LoadBalancer Services would remain <pending> forever.
```

### BGP Security — Why BGP Hijacking is Dangerous

```
BGP has no built-in authentication (historically).
Any AS can announce ANY IP prefix.

BGP Hijacking:
  1. A malicious (or misconfigured) AS announces 8.8.8.0/24
     "To reach 8.8.8.8, come through me"
  2. BGP prefers more specific routes (longer prefix = more specific)
  3. Some ISPs start routing Google DNS traffic to the malicious AS
  4. Traffic is intercepted, dropped, or inspected

Real incidents:
  - 2010: China Telecom briefly announced 40,000 IP prefixes (15% of internet routes)
  - 2018: BGP hijacking of Amazon Route53 DNS → cryptocurrency theft
  - 2019: European mobile provider accidentally redirected Google traffic

Solution: RPKI (Resource Public Key Infrastructure)
  Cryptographically validates that an AS is authorized to announce a prefix
  Growing adoption: ~50% of internet routes now RPKI-validated (as of 2025)
```

### Deep Dive: Kubernetes Service — Which Layer?

A Kubernetes **Service** is primarily a Layer 4 construct, but it also touches Layer 3:

```
Service ClusterIP: 10.96.100.50 (Layer 3 — virtual IP)
Service Port: 80 (Layer 4 — TCP port)

kube-proxy creates iptables rules (Layer 3/4):
  "Traffic for 10.96.100.50:80 → DNAT to one of:
    10.244.1.5:8080  (Pod 1)
    10.244.2.3:8080  (Pod 2)
    10.244.1.9:8080  (Pod 3)"

The Service ITSELF operates at Layer 3/4.
The Ingress on top of it operates at Layer 7.
```

### Deep Dive: Ingress — Layer 7

```yaml
# This Ingress operates at Layer 7 — it inspects HTTP content
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop-ingress
spec:
  rules:
  # Layer 7 decision: route based on HTTP Host header
  - host: shop.example.com
    http:
      paths:
      # Layer 7 decision: route based on URL path
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              number: 80
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend-service
            port:
              number: 80
```

A pure TCP load balancer (like a Service of type LoadBalancer with `protocol: TCP`) cannot do this path-based routing — it's Layer 4 only and doesn't understand HTTP.

### Deep Dive: NetworkPolicy — Layer 3/4

```yaml
# NetworkPolicy: operates at Layer 3 (IP) and Layer 4 (port)
# It CANNOT inspect HTTP paths, methods, or headers
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: payment-policy
spec:
  podSelector:
    matchLabels:
      app: payment-service       # Layer 3: select by pod label (maps to Pod IPs)
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: order-service     # Layer 3: allow from specific pods
    ports:
    - port: 8080                 # Layer 4: only on this port
      protocol: TCP              # Layer 4: only TCP

# ❌ NetworkPolicy CANNOT do:
#   - Allow only HTTP GET requests (Layer 7)
#   - Allow only requests with a valid JWT (Layer 7)
#   - Route 10% of traffic to v2 (Layer 7)
```

### CNI Plugin — Layers 2 and 3

```
Flannel (uses VXLAN overlay):
  Wraps Layer 3 packets inside UDP packets
  This is "tunneling" — a Layer 3 network built on top of another Layer 3 network
  Operates at Layer 2/3 boundary

  Pod on Node 1 → veth pair → bridge (Layer 2) →
  VXLAN encapsulation (Layer 2/3) → UDP packet (Layer 4) → Node 2's NIC →
  VXLAN decapsulation → bridge → veth pair → Pod on Node 2

Calico (uses BGP, no overlay by default):
  Operates at Layer 3 natively
  BGP distributes pod routes to all nodes
  Packets route directly (no tunneling overhead) — better performance
  Also enforces NetworkPolicy at Layer 3/4
```

## 10. Complete Kubernetes Traffic Flow

### Scenario: External User → Kubernetes Application

```
User's browser                          Kubernetes Cluster
IP: 203.0.113.100                       AWS EKS in us-east-1

Request: GET https://shop.example.com/api/products
```

#### Step-by-Step Traffic Flow

```
STEP 1: DNS Resolution (Layer 7 / Application)
  Browser: "What's the IP for shop.example.com?"
  DNS Query → Route53 → Returns: 54.12.34.56 (AWS NLB IP)

STEP 2: TCP 3-Way Handshake (Layer 4)
  User (203.0.113.100:54321) ←→ NLB (54.12.34.56:443)
  SYN → SYN-ACK → ACK

STEP 3: TLS Handshake (Layer 6 / Presentation)
  Certificate presented for shop.example.com
  Session key negotiated
  Connection encrypted

STEP 4: HTTP Request (Layer 7 / Application)
  GET /api/products HTTP/1.1
  Host: shop.example.com
  [All encrypted by TLS]

STEP 5: AWS NLB (Layer 4 Load Balancer)
  NLB forwards TCP connection to one of the Kubernetes nodes
  NLB does NOT inspect HTTP content (Layer 4 only)
  
  User → NLB → Node (10.0.1.5)

STEP 6: Ingress Controller (Layer 7)
  NGINX Ingress Controller pod running on the node receives the TLS traffic
  
  ┌─────────────────────────────────────────────┐
  │  NGINX Ingress Controller                   │
  │                                             │
  │  TLS Termination:                           │
  │    Decrypts the HTTPS traffic               │
  │    Uses the TLS cert stored in K8s Secret   │
  │                                             │
  │  Layer 7 routing:                           │
  │    Host: shop.example.com → matches         │
  │    Path: /api/products → routes to api-svc  │
  └─────────────────────────────────────────────┘

STEP 7: Kubernetes Service — kube-proxy (Layer 3/4)
  Request forwarded to Service: api-service (ClusterIP: 10.96.50.10)
  
  iptables rule:
    DNAT: 10.96.50.10:80 → 10.244.2.7:8080 (a Pod's IP)
  
  Packet travels across the node network (BGP routes via Calico)

STEP 8: NetworkPolicy Check (Layer 3/4)
  Calico enforces NetworkPolicy:
    Source: NGINX pod (10.244.1.3) → allowed to reach api-service pods

STEP 9: Istio Sidecar — If Service Mesh Present (Layer 4-7)
  Traffic intercepted by Envoy sidecar in the destination pod
  mTLS certificate verified (Layer 6)
  AuthorizationPolicy checked (Layer 7)
  Metrics recorded
  Trace span created

STEP 10: Application Pod (Layer 7)
  Pod (IP: 10.244.2.7) receives the request
  Application processes GET /api/products
  Returns: {"products": [...]}

STEP 11: Response travels back through all the same layers in reverse
```

```

   │
   ▼
[DNS: shop.example.com → 54.12.34.56]                    L7 — Application
   │
   ▼
[AWS NLB: 54.12.34.56]  ← TCP load balancing             L4 — Transport
   │
   ▼

   │

   │

[Istio Envoy sidecar]  ← mTLS verify, AuthzPolicy, metrics L4-L7
   │
   ▼
[Application Container] ← Handles HTTP request             L7
```

## 11. Summary Reference Card

### OSI Layers Quick Reference

```
┌──────┬────────────────┬──────────────────────┬────────────────────────────────────┐
│Layer │ Name           │ Data Unit            │ Key Protocols / Devices             │
├──────┼────────────────┼──────────────────────┼────────────────────────────────────┤
│  7   │ Application    │ Data                 │ HTTP, HTTPS, DNS, SMTP, SSH, gRPC  │
│  6   │ Presentation   │ Data                 │ TLS, SSL, JSON, XML, gzip          │
│  5   │ Session        │ Data                 │ NetBIOS, RPC, Sockets              │
│  4   │ Transport      │ Segment / Datagram   │ TCP, UDP, Ports                    │
│  3   │ Network        │ Packet               │ IP, ICMP, BGP, OSPF, Routers       │
│  2   │ Data Link      │ Frame                │ Ethernet, ARP, MAC, Switches       │
│  1   │ Physical       │ Bits                 │ Cables, Wi-Fi, NICs, Hubs          │
└──────┴────────────────┴──────────────────────┴────────────────────────────────────┘
```

### TCP 3-Way Handshake

```
Client ──── SYN (seq=X) ────────────────────────────> Server
Client <─── SYN-ACK (seq=Y, ack=X+1) ─────────────── Server
Client ──── ACK (ack=Y+1) ──────────────────────────> Server
                     ← Connection Established →
```

### TLS Handshake (TLS 1.3 — 1 RTT)

```
Client ──── ClientHello + KeyShare ─────────────────> Server
Client <─── ServerHello + KeyShare + Cert + Finished ─ Server
Client ──── Finished ───────────────────────────────> Server
                     ← Encrypted data flows →
```

### Sticky Sessions

```
Problem:  Session state stored in server memory → lost on different server
Solution: Cookie or IP hash pins user to same server
Best fix:  Store session state in external shared store (Redis) → no stickiness needed
K8s:       Service.spec.sessionAffinity: ClientIP
           Ingress annotation: nginx.ingress.kubernetes.io/affinity: "cookie"
```

### BGP

```
What:   Protocol for exchanging routing information between Autonomous Systems
Why:    IP packets need to cross many different networks to reach their destination
How:    Path vector — each AS advertises reachable IP ranges + the AS path to reach them
K8s:    Calico uses BGP to distribute pod routes between nodes
        MetalLB uses BGP to advertise LoadBalancer IPs to physical routers
```

### Kubernetes Resource → OSI Layer Mapping

```
L7 (Application): Ingress, VirtualService, AuthorizationPolicy, API Gateway
L6 (Presentation): TLS Secrets, cert-manager, PeerAuthentication (mTLS)
L5 (Session):     sessionAffinity, sticky session annotations
L4 (Transport):   Service (ClusterIP/NodePort/LB), NetworkPolicy ports, kube-proxy
L3 (Network):     Pod IPs, CNI plugins, NetworkPolicy selectors, BGP, MetalLB
L2 (Data Link):   veth pairs, Linux bridges, VXLAN overlays
L1 (Physical):    Node NICs, underlying cloud/bare-metal network
```
