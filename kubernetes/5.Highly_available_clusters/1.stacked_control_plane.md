### 📌 Stacked Control Plane (Interview Style Explanation)

### ✅ What is Stacked Control Plane?

* In Kubernetes, **control plane components + etcd run on the same nodes**
* Each control plane node hosts:

  * kube-apiserver
  * kube-scheduler
  * kube-controller-manager
  * **etcd (local instance)**

👉 So **etcd is “stacked” with control plane**, not separate.

---

### 🧠 Architecture Understanding

```
Control Plane Node 1  → API + Scheduler + Controller + etcd
Control Plane Node 2  → API + Scheduler + Controller + etcd
Control Plane Node 3  → API + Scheduler + Controller + etcd
```

* Each node runs its own **etcd member**
* All etcd members form a **cluster (quorum-based)**

---

### ⚙️ Real-Time Example

#### Scenario:

You are setting up a **Highly Available Kubernetes cluster** using `kubeadm`

#### Setup:

* 3 VMs:

  * `master-1`
  * `master-2`
  * `master-3`

#### What happens:

* When you initialize cluster on `master-1`:

  * etcd runs locally on it
* When you join `master-2` & `master-3` as control plane:

  * They also start **their own etcd instances**
  * All 3 etcd instances form a **distributed etcd cluster**

---

### 🔄 Flow Example

1. User sends request → Load Balancer
2. Load Balancer → Any control plane node (say master-2)
3. API server processes request
4. State stored in **local etcd cluster (replicated across all 3 nodes)**

---

### 🎯 Key Point (Important for Interviews)

* etcd is:

  * **Distributed**
  * **Replicated across control plane nodes**
  * Uses **quorum (majority) for consistency**

👉 Example:

* 3 nodes → quorum = 2
* If 1 node fails → cluster still works
* If 2 nodes fail → cluster breaks ❌

---

### 👍 Advantages

* Less infrastructure (no separate etcd nodes)
* Easy to set up using `kubeadm`
* Cost-effective for small/medium clusters

---

### 👎 Disadvantages

* Resource contention (etcd + control plane share CPU/RAM)
* Less isolation → failure impact is higher
* Not ideal for very large production workloads

---

### 🆚 Quick Comparison

| Feature     | Stacked etcd | External etcd |
| ----------- | ------------ | ------------- |
| Infra cost  | Low          | High          |
| Setup       | Simple       | Complex       |
| Isolation   | ❌ No         | ✅ Yes         |
| Scalability | Limited      | High          |

---

### 🔥 Simple Analogy

Think of it like:

* **Stacked:** Kitchen + storage room in same house 🏠
* **External:** Kitchen in one building, storage in another 🏢

---

### 💡 When to Use?

* Small to medium production clusters
* Dev / Test environments
* When infra cost matters

# 🧠 What is Leader Election?

👉 Leader election ensures that **only one instance performs critical tasks** when multiple identical components are running.

* Used in:

  * kube-scheduler
  * kube-controller-manager

👉 Prevents:

* Duplicate actions
* Conflicts in cluster state

---

# ⚙️ Why Leader is Needed?

Imagine:

* 3 schedulers running on:

  * master-1
  * master-2
  * master-3

👉 Without leader election:

* All 3 may try to schedule the **same Pod**
* Result:

  * Duplicate assignments ❌
  * Cluster inconsistency ❌

---

# ✅ With Leader Election

👉 Only **one scheduler becomes leader**

* Leader → actively schedules pods
* Others → stay standby (watching)

* Followers:

  * Do nothing (just observe)

# 🔄 What if Leader Fails?

👉 Suppose:

* master-2 goes down

Then:

1. Leader lock is lost
2. Remaining schedulers compete
3. One becomes new leader (say master-1)

👉 Cluster continues normally ✅

# 🔐 How Leader Election Works Internally

* Uses **Lease object** in Kubernetes
* Stored in:

  ```
  kube-system namespace
  ```

👉 Example:

```bash
kubectl get lease -n kube-system
```

Each component:

* Tries to acquire lock
* Renews periodically
