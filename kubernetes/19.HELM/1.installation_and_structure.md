## What is Helm?

### Simple Definition
**Helm is a package manager for Kubernetes**, just like `npm` for Node.js, `pip` for Python, or `apt` for Ubuntu.

### Analogy: Restaurant Kitchen
Think of Helm like a recipe book for a restaurant:
- **Kubernetes** = The kitchen with all equipment (ovens, stoves, pans)
- **Docker Images** = Individual ingredients (flour, eggs, butter)
- **Kubernetes YAML files** = Detailed step-by-step instructions to make a dish
- **Helm** = A packaged recipe that includes all instructions, ingredients list, and can be customized (more salt, less sugar)

Just like you don't write cooking instructions from scratch every time, you don't write Kubernetes configuration files from scratch. Helm packages them!

### What Helm Actually Does
```
Helm = Templates + Values + Package Management + Version Control
```

Helm takes your Kubernetes configuration files and:
1. **Packages them** into a reusable unit called a "Chart"
2. **Templatizes them** so you can customize them without editing files
3. **Manages versions** so you can track changes
4. **Deploys them** to Kubernetes with a single command

## Why Do We Need Helm?

### Problem 1: YAML Repetition

Without Helm, deploying an app to Kubernetes requires multiple YAML files:

```yaml
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  namespace: default
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: my-app
        image: my-app:1.0.0
        ports:
        - containerPort: 8080
---
# service.yaml
apiVersion: v1
kind: Service
metadata:
  name: my-app-service
spec:
  selector:
    app: my-app
  ports:
  - port: 80
    targetPort: 8080
  type: LoadBalancer
---
# configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: my-app-config
data:
  DATABASE_URL: "postgres://db.example.com"
  LOG_LEVEL: "info"
```

**Problem**: If you want to deploy the same app to 5 different environments (dev, staging, prod, qa, test), you'd need 15 files! And if you want to change the replicas count, you manually edit 5 files.

### Problem 2: Configuration Management
With traditional YAML:
- Hard to maintain different configurations for different environments
- Easy to make mistakes copying/pasting files
- Version control becomes messy
- Sharing charts with the team is cumbersome

### Problem 3: Dependency Management
If your app needs a database, cache, and message queue, you manually deploy each one in the correct order and configure them to talk to each other.

### How Helm Solves These Problems

**With Helm:**
```bash
# Deploy the same app to 5 environments with one command
helm install my-app ./my-app-chart --values dev-values.yaml
helm install my-app ./my-app-chart --values staging-values.yaml
helm install my-app ./my-app-chart --values prod-values.yaml
```

No file duplication. No manual changes. Just different configuration files!

## How Does Helm Work?

### Helm Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                    Helm Workflow                             │
└─────────────────────────────────────────────────────────────┘

Step 1: Chart Creation
┌──────────────────┐
│  Write Chart:    │
│  - templates/    │ ──→ helm package my-app/
│  - values.yaml   │
│  - Chart.yaml    │
└──────────────────┘
         │
         ↓
Step 2: Packaging
┌──────────────────┐
│  Creates:        │
│  my-app-1.0.0.tgz│
└──────────────────┘
         │
         ↓
Step 3: Store/Share
┌──────────────────┐
│  Helm Repository │ (Online storage)
│  or Local File   │
└──────────────────┘
         │
         ↓
Step 4: Installation
┌──────────────────┐
│  helm install    │ ──→ Kubernetes API
│  (with values)   │
└──────────────────┘
         │
         ↓
Step 5: Kubernetes Creates Resources
┌──────────────────┐
│  Deployments,    │
│  Services,       │
│  ConfigMaps,     │
│  etc.            │
└──────────────────┘
```

### The Three Layers

```
Layer 1: Templates (Blueprints)
├── deployment.yaml (template)
├── service.yaml (template)
└── configmap.yaml (template)
    ↓
    (Contains {{ }} placeholders)

Layer 2: Values (Customization)
└── values.yaml
    ├── replicas: 3
    ├── image: my-app:1.0.0
    └── environment: prod
    ↓
    (Fills in the {{ }} placeholders)

Layer 3: Rendered Output (Final YAML)
└── Generated YAML files ready for Kubernetes
    ├── deployment.yaml (replicas: 3, image: my-app:1.0.0)
    ├── service.yaml
    └── configmap.yaml
```

### Flow Example

**Template file** (`templates/deployment.yaml`):
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Values.appName }}
spec:
  replicas: {{ .Values.replicas }}
  template:
    spec:
      containers:
      - name: {{ .Values.appName }}
        image: {{ .Values.image }}:{{ .Values.imageTag }}
```

**Values file** (`values.yaml`):
```yaml
appName: my-app
replicas: 3
image: my-app
imageTag: "1.0.0"
```

**After Helm processes them**, the output is:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: my-app
        image: my-app:1.0.0
```

## Key Concepts

### 1. Chart
A **Chart** is a package that contains:
- Templates for Kubernetes resources
- Default values for customization
- Metadata (name, version, description)
- Dependencies (other charts it needs)

**Analogy**: A Chart is like a software package (like an .exe for Windows or .deb for Linux).

### 2. Release
A **Release** is an instance of a chart deployed to Kubernetes.

**Analogy**: If a Chart is a recipe, a Release is when you actually cook that recipe in your kitchen.

**Example**:
```bash
# Same chart, three different releases
helm install my-app-dev ./my-app-chart --values dev.yaml
helm install my-app-staging ./my-app-chart --values staging.yaml
helm install my-app-prod ./my-app-chart --values prod.yaml
```

Here, one chart is deployed 3 times as 3 different releases.

### 3. Repository
A **Repository** is a collection of charts, hosted on a server.

**Analogy**: Like GitHub for code, but for Helm charts.

Common Helm repositories:
- `stable` - Official Helm charts
- `bitnami` - Community-maintained charts (Databases, monitoring tools, etc.)
- `jetstack` - Cert-Manager charts

### 4. Values
A **values.yaml** file contains default configuration that customizes how the chart behaves.

It's like:
- Settings in a software application
- Environment variables for a program
- Configuration file for a service

## Installation

### Step 1: Install Helm

#### On macOS (using Homebrew)
```bash
brew install helm
```

#### On Linux (Ubuntu/Debian)
```bash
curl https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash
```

#### On Windows (using Chocolatey)
```bash
choco install kubernetes-helm
```

#### Manual Download (All Platforms)
```bash
# Visit: https://github.com/helm/helm/releases
# Download the appropriate binary for your OS
# Extract and add to PATH
```

### Step 2: Verify Installation
```bash
helm version
# Output: version.BuildInfo{Version:"v3.12.0", GitCommit:"...", GitTreeState:"clean", GoVersion:"go1.20.3"}
```

### Step 3: Verify Kubernetes Connection
```bash
kubectl cluster-info
# Should show your Kubernetes cluster details

helm repo list
# Should show available repositories (might be empty initially)
```

```bash

# Update repositories
helm repo update

# List repositories
helm repo list
# Output:
# NAME            URL
# bitnami         https://charts.bitnami.com/bitnami
```

## Helm Chart Structure

### Directory Layout

```
my-app-chart/                    # Chart root directory
├── Chart.yaml                   # Chart metadata (name, version, description)
├── values.yaml                  # Default configuration values
├── templates/                   # Kubernetes resource templates
│   ├── deployment.yaml          # Deployment template
│   ├── service.yaml             # Service template
│   ├── configmap.yaml           # ConfigMap template
│   ├── ingress.yaml             # Ingress template
│   ├── _helpers.tpl             # Helper templates (reusable snippets)
│   └── NOTES.txt                # Post-installation notes for user
├── values/                      # (Optional) Environment-specific values
│   ├── dev-values.yaml
│   ├── staging-values.yaml
│   └── prod-values.yaml
├── charts/                      # (Optional) Dependency charts
│   └── postgres-chart/          # Sub-charts (other charts this depends on)
├── Chart.lock                   # (Auto-generated) Lock file for dependencies
├── .helmignore                  # (Optional) Files to ignore when packaging
└── README.md                    # (Optional) Chart documentation
```

## Understanding Each File & Folder

### 1. **Chart.yaml** - Chart Metadata

This file contains information **about** the chart (not the application).

```yaml
apiVersion: v2                           # Helm version (v2 is Helm 3)
name: my-app-chart                       # Name of the chart
description: A Helm chart for my-app    # What this chart does
type: application                         # Type: application or library
version: 1.0.0                           # Chart version (you increment this)
appVersion: "1.0.0"                      # Version of the application it deploys
keywords:
  - app
  - kubernetes
maintainers:
  - name: John Doe
    email: john@example.com
home: https://github.com/example/my-app  # Project homepage
sources:
  - https://github.com/example/my-app    # Source code repository
```

**Key Points**:
- `version` = Chart version (increment when you change the chart)
- `appVersion` = Application version (version of the app being deployed)
- Different from `values.yaml` - this is **static metadata**, not configuration

---

### 2. **values.yaml** - Default Configuration

This file contains **default values** for your application.

```yaml
# Global settings
namespace: default

# Deployment configuration
replicaCount: 3

image:
  repository: my-app
  tag: "1.0.0"
  pullPolicy: IfNotPresent

# Service configuration
service:
  type: ClusterIP
  port: 80
  targetPort: 8080

# Application settings
app:
  name: my-application
  environment: production
  logLevel: info
  
# Database configuration
database:
  enabled: true
  host: postgres.default.svc.cluster.local
  port: 5432
  name: myapp_db
  username: postgres
  # Never put passwords here! Use secrets instead
  
# Resource limits
resources:
  limits:
    cpu: 500m
    memory: 512Mi
  requests:
    cpu: 250m
    memory: 256Mi

# Auto-scaling
autoscaling:
  enabled: false
  minReplicas: 2
  maxReplicas: 10

# Health checks
healthCheck:
  enabled: true
  path: /health
  initialDelaySeconds: 30
  periodSeconds: 10
```

**Usage in templates**:
```yaml
# In templates/deployment.yaml
replicas: {{ .Values.replicaCount }}
image: {{ .Values.image.repository }}:{{ .Values.image.tag }}
```

---

### 3. **templates/** - Kubernetes Resource Templates

These are **templated Kubernetes YAML files** with placeholders.

#### **templates/deployment.yaml**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "my-app-chart.fullname" . }}
  namespace: {{ .Values.namespace }}
  labels:
    {{- include "my-app-chart.labels" . | nindent 4 }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      {{- include "my-app-chart.selectorLabels" . | nindent 6 }}
  template:
    metadata:
      labels:
        {{- include "my-app-chart.selectorLabels" . | nindent 8 }}
    spec:
      containers:
      - name: {{ .Values.app.name }}
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
        imagePullPolicy: {{ .Values.image.pullPolicy }}
        ports:
        - name: http
          containerPort: {{ .Values.service.targetPort }}
        env:
        - name: LOG_LEVEL
          value: {{ .Values.app.logLevel | quote }}
        - name: DATABASE_HOST
          value: {{ .Values.database.host }}
        - name: DATABASE_PORT
          value: {{ .Values.database.port | quote }}
        {{- if .Values.healthCheck.enabled }}
        livenessProbe:
          httpGet:
            path: {{ .Values.healthCheck.path }}
            port: http
          initialDelaySeconds: {{ .Values.healthCheck.initialDelaySeconds }}
          periodSeconds: {{ .Values.healthCheck.periodSeconds }}
        readinessProbe:
          httpGet:
            path: {{ .Values.healthCheck.path }}
            port: http
          initialDelaySeconds: {{ .Values.healthCheck.initialDelaySeconds }}
          periodSeconds: {{ .Values.healthCheck.periodSeconds }}
        {{- end }}
        resources:
          {{- toYaml .Values.resources | nindent 10 }}
```

**Template Syntax Explained**:
- `{{ }}` - Placeholder for values
- `{{- }}` - Remove whitespace before
- `{{ .Values.key }}` - Access value from values.yaml
- `{{ include "helper-name" . }}` - Call helper templates
- `{{- if .Values.condition }}` - Conditional logic
- `{{ .Values.value | quote }}` - Filters/pipes for formatting

#### **templates/service.yaml**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: {{ include "my-app-chart.fullname" . }}
  namespace: {{ .Values.namespace }}
spec:
  type: {{ .Values.service.type }}
  ports:
  - port: {{ .Values.service.port }}
    targetPort: {{ .Values.service.targetPort }}
    protocol: TCP
    name: http
  selector:
    {{- include "my-app-chart.selectorLabels" . | nindent 4 }}
```

#### **templates/configmap.yaml**
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ include "my-app-chart.fullname" . }}-config
  namespace: {{ .Values.namespace }}
data:
  app_name: {{ .Values.app.name }}
  environment: {{ .Values.app.environment }}
  log_level: {{ .Values.app.logLevel }}
  {{- if .Values.database.enabled }}
  database_host: {{ .Values.database.host }}
  database_port: {{ .Values.database.port | quote }}
  database_name: {{ .Values.database.name }}
  {{- end }}
```

#### **templates/_helpers.tpl** - Reusable Templates

This file contains template functions used across other templates.

```yaml
{{/*
Expand the name of the chart.
*/}}
{{- define "my-app-chart.name" -}}
{{- default .Chart.Name .Values.nameOverride | trunc 63 | trimSuffix "-" }}
{{- end }}

{{/*
Create a fully qualified app name.
*/}}
{{- define "my-app-chart.fullname" -}}
{{- if .Values.fullnameOverride }}
{{- .Values.fullnameOverride | trunc 63 | trimSuffix "-" }}
{{- else }}
{{- $name := default .Chart.Name .Values.nameOverride }}
{{- if contains $name .Release.Name }}
{{- .Release.Name | trunc 63 | trimSuffix "-" }}
{{- else }}
{{- printf "%s-%s" .Release.Name $name | trunc 63 | trimSuffix "-" }}
{{- end }}
{{- end }}
{{- end }}

{{/*
Common labels
*/}}
{{- define "my-app-chart.labels" -}}
helm.sh/chart: {{ include "my-app-chart.chart" . }}
{{ include "my-app-chart.selectorLabels" . }}
app.kubernetes.io/version: {{ .Chart.AppVersion | quote }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
{{- end }}

{{/*
Selector labels
*/}}
{{- define "my-app-chart.selectorLabels" -}}
app.kubernetes.io/name: {{ include "my-app-chart.name" . }}
app.kubernetes.io/instance: {{ .Release.Name }}
{{- end }}
```

#### **templates/NOTES.txt** - Post-Installation Instructions

Shown after `helm install` completes.

```text
1. Get the application URL:
{{- if eq .Values.service.type "LoadBalancer" }}
  NOTE: It may take a few minutes for the LoadBalancer IP to be available.
  You can watch the status by running: kubectl get svc --namespace {{ .Values.namespace }} -w {{ include "my-app-chart.fullname" . }}

  export SERVICE_IP=$(kubectl get svc --namespace {{ .Values.namespace }} {{ include "my-app-chart.fullname" . }} --template "{.status.loadBalancer.ingress[0].ip}")
  echo http://$SERVICE_IP:{{ .Values.service.port }}

{{- else if eq .Values.service.type "ClusterIP" }}
  export POD_NAME=$(kubectl get pods --namespace {{ .Values.namespace }} -l "app.kubernetes.io/name={{ include "my-app-chart.name" . }}" -o jsonpath="{.items[0].metadata.name}")
  kubectl port-forward {{ .Values.namespace }}/{{ include "my-app-chart.fullname" . }} 8080:{{ .Values.service.targetPort }}
  echo "Visit http://127.0.0.1:8080"

{{- end }}

2. Check deployment status:
  kubectl get deployment --namespace {{ .Values.namespace }} {{ include "my-app-chart.fullname" . }}

3. View logs:
  kubectl logs --namespace {{ .Values.namespace }} -l app.kubernetes.io/name={{ include "my-app-chart.name" . }}
```

### 4. **charts/** - Dependencies

Directory containing other Helm charts that this chart depends on.

**Example**: If your app needs PostgreSQL and Redis:

```yaml
# Chart.yaml
dependencies:
  - name: postgresql
    version: "12.x.x"
    repository: https://charts.bitnami.com/bitnami
  - name: redis
    version: "17.x.x"
    repository: https://charts.bitnami.com/bitnami
```

Then run:
```bash
helm dependency update
# Downloads postgresql and redis into charts/ folder
```

## Commands & Examples

### Basic Helm Commands

#### 1. **helm create** - Create new chart
```bash
helm create my-app
# Creates a complete chart structure
```

#### 2. **helm lint** - Validate chart syntax
```bash
helm lint my-app-chart/
# Validates YAML syntax, required fields, etc.
# Output:
# ==> Linting my-app-chart/
# [INFO] Chart.yaml: icon is missing
# [OK] No issues found
```

#### 3. **helm template** - Render templates without installing
```bash
# See what YAML will be generated
helm template my-release my-app-chart/

# With custom values
helm template my-release my-app-chart/ --values prod-values.yaml

# Output rendered YAML to file
helm template my-release my-app-chart/ > rendered.yaml
```

#### 4. **helm install** - Deploy chart to Kubernetes
```bash
# Basic install
helm install my-release my-app-chart/

# With values file
helm install my-release my-app-chart/ --values values.yaml

# With override values
helm install my-release my-app-chart/ \
  --set replicaCount=5 \
  --set image.tag="2.0.0"

# Into specific namespace
helm install my-release my-app-chart/ --namespace production

# Create namespace if it doesn't exist
helm install my-release my-app-chart/ --namespace production --create-namespace

# Output:
```

#### Example 5: Helm with CI/CD Pipeline

```bash
#!/bin/bash

# Script: deploy.sh
RELEASE_NAME="my-app"
CHART_PATH="./my-app-chart"
NAMESPACE="production"
IMAGE_TAG=$1  # Passed from CI/CD system

# Lint chart
helm lint $CHART_PATH

# Template validation
helm template $RELEASE_NAME $CHART_PATH \
  --set image.tag=$IMAGE_TAG > /tmp/rendered.yaml
kubectl apply -f /tmp/rendered.yaml --dry-run=client

# Deploy or upgrade
helm upgrade --install $RELEASE_NAME $CHART_PATH \
  --namespace $NAMESPACE \
  --create-namespace \
  --set image.tag=$IMAGE_TAG \
  --wait

# Verify deployment
kubectl rollout status deployment/$RELEASE_NAME -n $NAMESPACE
```

## Packaging & Releasing

### Step 1: Prepare Your Chart

Ensure your chart is complete:
```bash
# Verify structure
ls -la my-app-chart/
# Chart.yaml
# values.yaml
# charts/
# templates/
# .helmignore

# Lint for errors
helm lint my-app-chart/
# [OK] No issues found
```

### Step 2: Update Chart Version

**Chart.yaml**:
```yaml
version: 1.0.0          # ← Increment this
appVersion: "1.0.0"     # ← Increment this too
```

**Versioning Strategy**:
- `1.0.0` = First release
- `1.0.1` = Bug fix in chart
- `1.1.0` = Minor feature in chart
- `2.0.0` = Major breaking change in chart

### Step 3: Package Chart

```bash
# Package chart into .tgz file
helm package my-app-chart/

# Output:
# Successfully packaged chart and saved it to: /path/to/my-app-chart-1.0.0.tgz

# List packaged chart
ls -lh my-app-chart-1.0.0.tgz
# -rw-r--r--  1 user  staff  15K Jan 15 10:30 my-app-chart-1.0.0.tgz

# View package contents
tar -tzf my-app-chart-1.0.0.tgz | head
# my-app-chart/
# my-app-chart/Chart.yaml
# my-app-chart/values.yaml
# my-app-chart/templates/
# ...
```

### Step 4: Create Helm Repository Index

If you have multiple charts:

```bash
# Create charts directory
mkdir -p helm-repo
cp my-app-chart-1.0.0.tgz helm-repo/

# Generate index file
helm repo index helm-repo/

# View index
cat helm-repo/index.yaml
# apiVersion: v1
# entries:
#   my-app-chart:
#   - apiVersion: v2
#     appVersion: "1.0.0"
#     created: "2024-01-15T10:30:00Z"
#     description: A Helm chart for a Python web application
#     digest: "abc123..."
#     name: my-app-chart
#     type: application
#     urls:
#     - my-app-chart-1.0.0.tgz
#     version: 1.0.0
# generated: "2024-01-15T10:30:00Z"
```

### Step 5: Publish to Repository

#### Option A: Publish to GitHub Pages

```bash
# Create gh-pages branch
git checkout --orphan gh-pages
git rm -rf .
git commit --allow-empty -m "Initial commit"

# Move charts
git checkout main -- helm-repo/
git add helm-repo/
git commit -m "Add Helm charts"
git push origin gh-pages

# Add to Helm
helm repo add my-charts https://yourusername.github.io/your-repo
helm repo update
helm search repo my-charts
```

#### Option B: Publish to Helm Chart Repository Service

Services like:
- **Artifactory** (JFrog)
- **Harbor** (VMware)
- **Nexus** (Sonatype)
- **ChartMuseum** (Open source)

```bash
# Example: Push to ChartMuseum
curl -X POST --data-binary "@my-app-chart-1.0.0.tgz" \
  http://chartmuseum-server:8080/api/charts

# Add to Helm
helm repo add my-chartmuseum http://chartmuseum-server:8080
helm search repo my-chartmuseum/my-app-chart
```

### Step 6: Install from Published Repository

```bash

helm repo add my-charts https://yourusername.github.io/your-repo

# Search
helm search repo my-charts/my-app-chart

# Install
helm install my-release my-charts/my-app-chart

# Install specific version
helm install my-release my-charts/my-app-chart --version 1.0.0
```

### Complete Release Workflow

```bash
#!/bin/bash

# Script: release.sh
# Complete workflow to create and publish a release

set -e  # Exit on error

CHART_NAME="my-app-chart"
CHART_PATH="./$CHART_NAME"
REPO_DIR="./helm-repo"
VERSION="1.0.0"

echo "🔍 Linting chart..."
helm lint $CHART_PATH

echo "📦 Packaging chart..."
helm package $CHART_PATH -d $REPO_DIR

echo "📇 Creating repository index..."
helm repo index $REPO_DIR

echo "📝 Chart contents:"
tar -tzf $REPO_DIR/$CHART_NAME-$VERSION.tgz | head -10

echo "✅ Release ready!"
echo "📍 Package location: $REPO_DIR/$CHART_NAME-$VERSION.tgz"
echo "📍 Index location: $REPO_DIR/index.yaml"

# Optional: Push to Git
# git add $REPO_DIR/
# git commit -m "Release $CHART_NAME v$VERSION"
# git push origin main
```

**Usage**:
```bash
chmod +x release.sh
./release.sh
```

```yaml
# In templates
{{- if .Values.database.enabled }}
```

```yaml

{{- range $key, $value := .Values.env }}
```

```yaml
# Simplify nested value access
{{- with .Values.app }}
```
