# Stateless Application

## What is Stateless?

A stateless application does not store client/session data inside the application instance.

Each request is independent.

---

# Example

```text
User Request 1 → Pod-1
User Request 2 → Pod-2
```

Both requests can be handled by any pod.

Application does not care:

* which pod handled previous request
* previous session data

---

# Real Examples

* NGINX
* REST APIs
* Frontend applications
* Microservices
* Product catalog service

---

# Stateless Flow

```text
Client
   ↓
Load Balancer
   ↓
Any Pod Can Serve Request
```

---

# Characteristics

| Feature                      | Stateless  |
| ---------------------------- | ---------- |
| Stores session in app memory | No         |
| Easy scaling                 | Yes        |
| Pod replacement easy         | Yes        |
| Data persistence needed      | Usually no |
| Any pod can handle request   | Yes        |

---

# Example in Kubernetes

```yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: nginx-deployment

spec:
  replicas: 3

  selector:
    matchLabels:
      app: nginx

  template:
    metadata:
      labels:
        app: nginx

    spec:
      containers:
      - name: nginx
        image: nginx
```

---

# Why Deployment for Stateless Apps?

Deployment is ideal because:

* Pods are interchangeable
* Pod identity does not matter
* Easy rolling updates
* Easy scaling

---

# Stateless Example in Real Life

## Food Delivery App

Product listing service:

```text
GET /products
```

Any pod can return products.

No user-specific state stored.

# Stateful Application

## What is Stateful?

A stateful application stores data/state related to client/session/application.

Application remembers:

* previous requests
* stored data
* identity

---

# Real Examples

* MySQL
* PostgreSQL
* MongoDB
* Kafka
* Redis
* Cassandra

---

# Stateful Flow

```text
Application
    ↓
Needs Persistent Data
    ↓
Storage Required
```

---

# Example

Database stores:

* users
* passwords
* orders
* transactions

If pod restarts:

```text
Data must remain
```

---

# Characteristics

| Feature                   | Stateful |
| ------------------------- | -------- |
| Stores persistent data    | Yes      |
| Pod identity important    | Yes      |
| Stable hostname needed    | Yes      |
| Persistent storage needed | Yes      |
| Scaling complex           | Yes      |

---

# Why Pod Identity Matters?

Suppose database cluster:

```text
mysql-0
mysql-1
mysql-2
```

Each pod has:

* unique data
* unique identity

You cannot randomly replace:

```text
mysql-0 with mysql-xyz
```

because replication and clustering depend on identity.

---

# Kubernetes Solution for Stateful Apps

Kubernetes uses:

```text
StatefulSet
```

---

# Why StatefulSet?

StatefulSet provides:

* Stable pod names
* Stable storage
* Ordered startup/shutdown
* Persistent identity

---

# StatefulSet Example

```yaml
apiVersion: apps/v1
kind: StatefulSet

metadata:
  name: mysql

spec:
  serviceName: mysql

  replicas: 3

  selector:
    matchLabels:
      app: mysql

  template:
    metadata:
      labels:
        app: mysql

    spec:
      containers:
      - name: mysql
        image: mysql:8
```

---

# Pod Names in StatefulSet

```text
mysql-0
mysql-1
mysql-2
```

Stable names.

Even after restart:

```text
mysql-0 remains mysql-0
```

---

# StatefulSet + Persistent Volume

Each pod gets dedicated storage.

Example:

```text
mysql-0 → PVC-0 → PV-0
mysql-1 → PVC-1 → PV-1
mysql-2 → PVC-2 → PV-2
```

---

# Very Important Difference

## Deployment Pods

```text
random identities
```

Example:

```text
nginx-7d4cf6
nginx-5gh7jk
```

Pods can come/go.

---

## StatefulSet Pods

```text
fixed identities
```

Example:

```text
mysql-0
mysql-1
mysql-2
```

---

# Storage Difference

## Stateless

Usually:

```text
No persistent storage needed
```

or shared temporary storage.

---

## Stateful

Needs:

```text
Persistent Volumes
```

---

# Scaling Difference

## Stateless Scaling

Easy:

```bash
kubectl scale deployment nginx --replicas=10
```

Any pod can serve traffic.

---

## Stateful Scaling

Careful scaling required because:

* data replication
* synchronization
* clustering

matter.

---

# Restart Difference

## Stateless Pod Restart

```text
Old pod deleted
New pod created
No issue
```

---

## Stateful Pod Restart

```text
Data must remain intact
Identity must remain same
```

---

# Network Identity

Stateful apps often need stable DNS names.

Example:

```text
mysql-0.mysql.default.svc.cluster.local
mysql-1.mysql.default.svc.cluster.local
```

Provided using:

```text
Headless Service
```

# Session Example

## Stateless Login System

Session stored in:

* Redis
* JWT token

not inside pod.

So:

```text
Any pod can serve request
```

---

## Stateful Login System

Session stored inside pod memory.

Problem:

```text
If request goes to another pod,
session lost
```

Needs sticky session/load balancer affinity.

# Interview Question

## Why Deployment not suitable for databases?

Answer:

```text
Deployment pods are interchangeable and identities are not stable.
Databases require stable identity and persistent storage.
```

---

# Interview Question

## Why StatefulSet needed?

Answer:

```text
To provide stable pod identity, stable storage, and ordered deployment for stateful applications.
```
