## Introduction

Before diving into CronJobs, let's understand the context with a simple analogy:

**Real-world analogy:**
- **Deployment** = A restaurant that's always open, serving customers 24/7
- **Job** = Hiring someone for a one-time catering event
- **CronJob** = Setting up a **recurring appointment** - like "every Monday at 9 AM, have the janitor clean the restaurant"

Kubernetes CronJob Controllers handle **scheduled, recurring workloads** that need to run at specific times.

## What is a CronJob Controller?

### Definition

A **CronJob Controller** in Kubernetes is a built-in controller that manages **scheduled, recurring tasks**. It automatically creates Jobs on a specified schedule (using cron syntax), executes them, and cleans them up.

Think of it as a Kubernetes-native job scheduler, similar to Linux cron jobs but for containerized workloads.

### Key Characteristics

| Feature | Description |
|---------|-------------|
| **Scheduling** | Runs on a schedule (e.g., daily, weekly, monthly) |
| **Cron Syntax** | Uses standard Unix cron expression format |
| **Job Creation** | Automatically creates Job objects according to schedule |
| **Time Zone** | Can specify timezone (important for multi-region clusters) |
| **Concurrency** | Controls how concurrent executions are handled |
| **History** | Keeps history of successful and failed runs |
| **Example Use Cases** | Backups, cleanup, reports, data syncs, health checks |

## Why Do We Need CronJobs?

### Problem Scenario

**Without CronJobs (Manual Approach):**
```
Monday, 9:00 AM  → Admin manually runs backup script
Tuesday, 9:00 AM → Admin remembers to run backup (maybe)
Wednesday        → Admin forgets, no backup taken! ❌
Thursday, 9:00 AM → Admin runs backup
Friday           → Admin on vacation, no backup ❌
Saturday         → No one to run backup
Sunday           → Manual backup finally runs

Problems:
- Human error (forgetful admins)
- Inconsistent scheduling
- No way to ensure tasks always run
- Someone has to remember every single time
```

**With CronJobs (Automated Approach):**
```
Monday, 9:00 AM    → CronJob automatically creates Job → Backup runs ✓
Tuesday, 9:00 AM   → CronJob automatically creates Job → Backup runs ✓
Wednesday, 9:00 AM → CronJob automatically creates Job → Backup runs ✓
Thursday, 9:00 AM  → CronJob automatically creates Job → Backup runs ✓
Friday, 9:00 AM    → CronJob automatically creates Job → Backup runs ✓
Saturday, 9:00 AM  → CronJob automatically creates Job → Backup runs ✓
Sunday, 9:00 AM    → CronJob automatically creates Job → Backup runs ✓

Benefits:
- Automated, no human intervention
- Consistent scheduling
- Guaranteed execution (unless cluster is down)
- Self-documenting (everyone can see the schedule)
```

### Real-World Use Cases

#### 1. **Database Backups**
```
Schedule: Every day at 2:00 AM (when traffic is lowest)
Task: Dump production database to cloud storage
Benefit: Automated disaster recovery, no manual overhead
```

#### 2. **Log Cleanup**
```
Schedule: Every Sunday at 3:00 AM
Task: Delete logs older than 30 days
Benefit: Prevents disk from filling up, reduces storage costs
```

#### 3. **Report Generation**
```
Schedule: Every Monday at 8:00 AM
Task: Generate weekly performance reports
Benefit: Reports ready before team standup
```

#### 4. **Cache Invalidation**
```
Schedule: Every hour at minute 0
Task: Flush Redis cache, warm up new data
Benefit: Fresh data without manual cache management
```

#### 5. **Health Checks**
```
Schedule: Every 5 minutes
Task: Ping critical services, alert if down
Benefit: Early detection of issues
```

#### 6. **Data Synchronization**
```
Schedule: Every 6 hours
Task: Sync data from old system to new system
Benefit: Zero-downtime migration over weeks
```

#### 7. **Certificate Renewal**
```
Schedule: Every 30 days
Task: Renew SSL/TLS certificates
Benefit: Prevents certificate expiration downtime
```

#### 8. **Cleanup Tasks**
```
Schedule: Every day at midnight
Task: Delete temporary files, clean up failed deployments
Benefit: Keeps cluster clean and organized
```

## How Do CronJobs Work?

### CronJob Lifecycle

```
┌──────────────────────────────────────────────────────────────────┐
│                      CRONJOB LIFECYCLE                            │
├──────────────────────────────────────────────────────────────────┤
│                                                                    │
│  STEP 1: SCHEDULING                                              │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ CronJob Controller watches the clock                     │   │
│  │ Checking: "Is it time to run?"                           │   │
│  │ Schedule: "0 2 * * *" (2:00 AM daily)                   │   │
│  │ Current time: 1:59 AM → Not time yet                     │   │
│  │ Current time: 2:00 AM → TIME TO RUN! ✓                 │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                    │
│  STEP 2: JOB CREATION                                            │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ CronJob creates a new Job object                         │   │
│  │ Job template from CronJob spec is used                   │   │
│  │ Job name: backup-job-1234567890                          │   │
│  │ Job inherits all container specs from CronJob template   │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                    │
│  STEP 3: JOB EXECUTION                                           │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ Job Controller takes over                                │   │
│  │ Creates pods according to Job spec                       │   │
│  │ Pods run the actual workload (e.g., backup.sh)          │   │
│  │ Pod completes and reports status back to Job            │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                    │
│  STEP 4: CLEANUP & TRACKING                                     │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ Job completion recorded in CronJob history              │   │
│  │ successfulJobsHistoryLimit: Keep last 3 successful jobs │   │
│  │ failedJobsHistoryLimit: Keep last 1 failed job          │   │
│  │ Old completed jobs deleted to save resources             │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                    │
│  STEP 5: WAITING FOR NEXT SCHEDULE                              │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ CronJob Controller goes back to Step 1                   │   │
│  │ Monitors time, waiting for next schedule trigger         │   │
│  │ Cycle repeats infinitely                                 │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                    │
└──────────────────────────────────────────────────────────────────┘
```

### Concurrency Control

```
┌─────────────────────────────────────────────────────┐
│   WHAT HAPPENS IF PREVIOUS JOB HASN'T FINISHED?    │
├─────────────────────────────────────────────────────┤
│                                                     │
│  Scenario: Job takes 45 minutes, but schedule     │
│  says run every 30 minutes                         │
│                                                     │
│  Schedule:     ◄──30 min──►◄──30 min──►           │
│                                                     │
│  Job 1:        Start────────────────Finish         │
│                   (45 min)                         │
│                                                     │
│  What to do?                                        │
│                                                     │
│  concurrencyPolicy: Allow                          │
│  Job 1:    Start────────────────Finish             │
│  Job 2:                Start────────────Finish     │
│  Job 3:                         Start──────Finish  │
│  Result: Multiple jobs run simultaneously          │
│                                                     │
│  concurrencyPolicy: Forbid                         │
│  Job 1:    Start────────────────Finish             │
│  Job 2:                         (Skipped) ✗        │
│  Job 3:                         Start───Finish     │
│  Result: Overlapping run is skipped                │
│                                                     │
│  concurrencyPolicy: Replace                        │
│  Job 1:    Start──(terminated)                     │
│  Job 2:                    Start──────Finish       │
│  Job 3:                              Start─Finish  │
│  Result: New job cancels old one                   │
│                                                     │
└─────────────────────────────────────────────────────┘
```

## Understanding Cron Syntax

### Cron Expression Format

A cron expression has **5 fields**:

```
┌─────────────── Minute (0-59)
│ ┌───────────── Hour (0-23)
│ │ ┌─────────── Day of Month (1-31)
│ │ │ ┌───────── Month (1-12)
│ │ │ │ ┌─────── Day of Week (0-7, where 0 and 7 = Sunday)
│ │ │ │ │
  *  *  *  *  *
  
0 2 * * *    → 02:00 every day
0 */4 * * *  → Every 4 hours
*/5 * * * *  → Every 5 minutes
0 0 1 * *    → 1st of every month at midnight
0 9 * * 1    → Every Monday at 9 AM
```

### Common Cron Expressions

```
EXPRESSION            TIME DESCRIPTION                FREQUENCY
──────────────────────────────────────────────────────────────────
*/5 * * * *          Every 5 minutes                  Every 5 min
0 * * * *            Every hour                       Hourly
0 2 * * *            2:00 AM every day                Daily
0 2 * * 0            2:00 AM every Sunday             Weekly
0 2 1 * *            2:00 AM on 1st of month         Monthly
0 2 1 1 *            2:00 AM on Jan 1st               Yearly
0 0 * * *            Midnight every day               Daily
0 9 * * 1-5          9:00 AM Mon-Fri                  Weekdays
0 0 1,15 * *         Midnight on 1st and 15th        Twice monthly
0 */6 * * *          Every 6 hours                    4 times daily
```

### Cron Syntax Examples Explained

#### Example 1: Daily at 2:00 AM
```
    0   2   *   *   *
    ↑   ↑   ↑   ↑   ↑
    │   │   │   │   └─ Day of week: * = every day (0=Sun, 1=Mon, etc.)
    │   │   │   └───── Month: * = every month (1-12)
    │   │   └───────── Day of month: * = every day (1-31)
    │   └───────────── Hour: 2 = 2 AM (0-23)
    └─────────────────minute: 0 = 00 minutes

Result: Run at 02:00:00 every single day
```

#### Example 2: Every 5 minutes
```
    */5  *   *   *   *
    ↑    ↑   ↑   ↑   ↑
    │    │   │   │   └─ Day of week: * = every day
    │    │   │   └───── Month: * = every month
    │    │   └───────── Day of month: * = every day
    │    └───────────── Hour: * = every hour
    └─────────────────Minute: */5 = every 5 minutes (0,5,10,15,20,...)

Result: Run at 00:00, 00:05, 00:10, 00:15... 23:55
        (288 times per day!)
```

#### Example 3: Monday to Friday at 9:00 AM
```
    0   9   *   *   1-5
    ↑   ↑   ↑   ↑   ↑
    │   │   │   │   └─ Day of week: 1-5 = Monday to Friday
    │   │   │   └───── Month: * = every month
    │   │   └───────── Day of month: * = every day
    │   └───────────── Hour: 9 = 9 AM
    └─────────────────Minute: 0 = 00 minutes

Result: Run at 09:00:00 every Monday, Tuesday, Wednesday, Thursday, Friday
```

#### Example 4: 1st and 15th of every month at midnight
```
    0   0   1,15   *   *
    ↑   ↑   ↑      ↑   ↑
    │   │   │      │   └─ Day of week: * = any day
    │   │   │      └───── Month: * = every month
    │   │   └───────────── Day of month: 1,15 = 1st and 15th
    │   └─────────────────Hour: 0 = midnight
    └───────────────────Minute: 0 = 00 minutes

Result: Run at 00:00:00 on 1st and 15th of every month
```

#### Example 5: Every 6 hours
```
    0   */6   *   *   *
    ↑   ↑     ↑   ↑   ↑
    │   │     │   │   └─ Day of week: * = every day
    │   │     │   └───── Month: * = every month
    │   │     └───────── Day of month: * = every day
    │   └───────────── Hour: */6 = every 6 hours (0,6,12,18)
    └─────────────────Minute: 0 = 00 minutes

Result: Run at 00:00, 06:00, 12:00, 18:00 every day
```

### Special Characters

```
CHAR   MEANING           EXAMPLE              RESULT
─────  ──────────────────────────────────────────────────────
  *    Any value         * * * * *           Always
  ,    List              0 0 1,15 * *        1st and 15th
  -    Range             0 0 * * 1-5          Mon-Fri
  /    Step              */5 * * * *         Every 5 min
  ?    No specific value 0 0 ? * *           Any day
       (use in day fields only)
```

## CronJob vs Job vs Deployment

### Comparison Table

| Aspect | CronJob | Job | Deployment |
|--------|---------|-----|-----------|
| **Purpose** | Scheduled recurring tasks | One-time task | Continuous service |
| **Created By** | Manual (CronJob spec) | Manual or CronJob | Manual |
| **Execution** | Automatic on schedule | Manual trigger | Always running |
| **Frequency** | Periodic (daily/hourly/etc.) | Once | Infinite |
| **Lifespan** | Permanent (until deleted) | Temporary (until done) | Permanent |
| **Example** | Daily backup at 2 AM | Database migration | Web server |
| **Status** | Active (waiting for next run) | Succeeded/Failed | Running |

## CronJob Object Structure

### Complete YAML Structure with Annotations

```yaml
apiVersion: batch/v1              # CronJob uses batch API group
kind: CronJob                     # Type of resource
metadata:
  name: daily-backup              # CronJob identifier
  namespace: default              # Kubernetes namespace
  labels:
    app: backup                   # Custom labels
spec:
  # ═══════════════════════════════════════════════════════════
  # SCHEDULING CONFIGURATION
  # ═══════════════════════════════════════════════════════════
  
  schedule: "0 2 * * *"           # Cron expression
                                  # Runs daily at 2:00 AM
                                  # Format: minute hour day month day-of-week
                                  # Timezone: UTC by default
  
  timezone: "Asia/Kolkata"        # Timezone for schedule
                                  # Default: UTC
                                  # Alternative: "America/New_York", "Europe/London"
                                  # Makes 2 AM in specified timezone, not UTC
  
  # ═══════════════════════════════════════════════════════════
  # CONCURRENCY CONTROL
  # ═══════════════════════════════════════════════════════════
  
  concurrencyPolicy: Allow        # What if previous job still running?
                                  # Allow: Let new job start (default)
                                  # Forbid: Skip this run
                                  # Replace: Kill old job, start new one
  
  # ═══════════════════════════════════════════════════════════
  # HISTORY & CLEANUP
  # ═══════════════════════════════════════════════════════════
  
  successfulJobsHistoryLimit: 3   # Keep last 3 successful jobs
                                  # Default: 3
                                  # 0 = don't keep any
                                  # Useful for viewing past runs
  
  failedJobsHistoryLimit: 1       # Keep last 1 failed job
                                  # Default: 1
                                  # Good for debugging failures
  
  startingDeadlineSeconds: 10     # Grace period for missed runs
                                  # Default: infinity
                                  # If cluster down for 1 hour, and grace = 10s,
                                  # missed runs are not executed
  
  suspend: false                  # Pause CronJob without deleting it
                                  # Default: false
                                  # true = all scheduled runs are skipped
  
  # ═══════════════════════════════════════════════════════════
  # JOB SPECIFICATION
  # (This defines what job to create when schedule triggers)
  # ═══════════════════════════════════════════════════════════
  
  jobTemplate:                    # Template for Jobs created by CronJob
    metadata:
      labels:
        job-type: backup          # Labels for Jobs
    
    spec:                         # Job specification
      completions: 1              # Job completes when 1 pod succeeds
      parallelism: 1              # Max 1 pod at a time
      backoffLimit: 3             # Retry up to 3 times on failure
      activeDeadlineSeconds: 1800 # Job timeout: 30 minutes
      ttlSecondsAfterFinished: 3600  # Auto-delete job after 1 hour
      
      template:                   # Pod template (what to run)
        metadata:
          labels:
            app: backup
        
        spec:
          # Pod specification (identical to Deployment/Job pods)
          containers:
          - name: backup-container
            image: postgres:15     # Container image
            
            command:               # Command to execute
            - "/bin/bash"
            - "-c"
            - |
              echo "Starting scheduled backup at $(date)"
              pg_dump -h postgres.db.svc.cluster.local \
                      -U backup_user \
                      -d production_db > /backup/db_$(date +%Y%m%d_%H%M%S).sql
              
              if [ $? -eq 0 ]; then
                echo "Backup completed successfully at $(date)"
                exit 0
              else
                echo "Backup failed at $(date)"
                exit 1
              fi
            
            env:                  # Environment variables
            - name: PGPASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: password
            
            resources:             # Resource limits
              requests:
                cpu: "200m"
                memory: "256Mi"
              limits:
                cpu: "1000m"
                memory: "1Gi"
            
            volumeMounts:          # Mount volumes
            - name: backup-storage
              mountPath: /backup
          
          volumes:                 # Define volumes
          - name: backup-storage
            persistentVolumeClaim:
              claimName: backup-pvc
          
          restartPolicy: OnFailure # Restart policy
                                   # OnFailure: retry on failure
                                   # Never: don't retry (Job handles retry)
```

### Explanation of Key Fields

#### 1. **schedule**
```
Purpose: Define when the job should run

Syntax: "minute hour day month day-of-week"

Examples:
"0 2 * * *"        → 2:00 AM every day
"*/5 * * * *"      → Every 5 minutes
"0 */4 * * *"      → Every 4 hours
"0 9 * * 1-5"      → Weekdays at 9 AM
"0 0 1 * *"        → 1st of every month at midnight
```

#### 2. **timezone**
```
Purpose: Specify timezone for schedule

Why it matters: 
Without timezone, all schedules are in UTC
If you want "2 AM" in your local time, must specify timezone

Examples:
timezone: "UTC"                 → 2 AM UTC
timezone: "Asia/Kolkata"        → 2 AM IST (UTC+5:30)
timezone: "America/New_York"    → 2 AM EST/EDT
timezone: "Europe/London"       → 2 AM GMT/BST

Default: UTC (if not specified)
```

#### 3. **concurrencyPolicy**
```
Purpose: Handle situation where previous job still running

Example Scenario:
- Schedule: Every 30 minutes
- Job takes: 45 minutes
- Question: What happens to the job that would start at 30 min mark?

Option 1: concurrencyPolicy: Allow
Time:     0    30    60    90
Job1:    Run──────────────End
Job2:           Run──────────────End
Job3:                  Run──────────────End
Result: Multiple jobs run simultaneously
Use case: When parallel execution is safe

Option 2: concurrencyPolicy: Forbid
Time:     0    30    60    90
Job1:    Run──────────────End
Job2:           (Skip) ✗
Job3:                  Run──────────────End
Result: Overlapping run is skipped
Use case: Cannot have concurrent execution

Option 3: concurrencyPolicy: Replace
Time:     0    30    60    90
Job1:    Run──(Killed by Job2)
Job2:           Run──────────────End
Job3:                  (Skip)
Result: New job kills the old one
Use case: Only latest job matters
```

#### 4. **startingDeadlineSeconds**
```
Purpose: Grace period for missed scheduled runs

Scenario: Cluster goes down for 2 hours
When back up, many scheduled runs were missed

startingDeadlineSeconds: 10 seconds
→ Missed runs only triggered if within 10 seconds of missed time
→ Runs more than 10 seconds ago are ignored

startingDeadlineSeconds: infinity (default, unspecified)
→ All missed runs are executed (one after another)
→ Could overload cluster after downtime

Example Timeline:
Schedule: Every 10 minutes

Normal:
10:00 - Job runs
10:10 - Job runs
10:20 - Job runs

With Cluster Downtime (cluster down from 10:12 to 10:35):
10:00 - Job runs
10:10 - Job runs
10:12 - Job SHOULD run, but cluster down
...
10:35 - Cluster back up, catches missed runs

If startingDeadlineSeconds: 10
→ Only 10:30 run executed (within 10s grace period)
→ Runs from 10:20, 10:25 skipped (too old)

If startingDeadlineSeconds not set (infinity)
→ All missed runs executed: 10:20, 10:25, 10:30
→ Could cause spike in resource usage
```

#### 5. **successfulJobsHistoryLimit / failedJobsHistoryLimit**
```
Purpose: Control how many old jobs to keep for reference

Scenario: CronJob runs daily for a year
→ 365 Job objects created
→ Keeps cluster database cluttered

Solution: Set history limits

successfulJobsHistoryLimit: 3
→ Keep only last 3 successful jobs
→ Older successful jobs automatically deleted
→ Can still view recent job logs

failedJobsHistoryLimit: 1
→ Keep only last 1 failed job
→ Good for debugging

Why keep history at all?
→ View logs of past runs
→ Understand what happened on a specific date
→ Detect patterns of failures

Example:
Day 1-7:   Backup succeeds daily (Jobs 1-7 created)
Day 8:     New run (Job 8 created)
Day 8:     CronJob deletes Job 6 (exceeds limit of 3)
           Now keeping: Jobs 8, 7 (success), Job 5 (maybe failed)
```

```python
#!/usr/bin/env python3
import os
import psycopg2
import smtplib
import boto3
from email.mime.multipart import MIMEMultipart
from email.mime.text import MIMEText
from datetime import datetime, timedelta

def connect_db():
    """Connect to PostgreSQL database"""
    conn = psycopg2.connect(
        host=os.environ['DB_HOST'],
        port=int(os.environ['DB_PORT']),
        database=os.environ['DB_NAME'],
        user=os.environ['DB_USER'],
        password=os.environ['DB_PASSWORD']
    )
    return conn

def generate_report():
    """Generate weekly performance report"""
    print("[{}] Starting report generation...".format(datetime.now()))
    
    try:
        # Connect to database
        conn = connect_db()
        cursor = conn.cursor()
        
        # Get last week's data
        print("[{}] Querying data from database...".format(datetime.now()))
        
        last_week = datetime.now() - timedelta(days=7)
        
        cursor.execute("""
            SELECT 
                DATE_TRUNC('day', created_at) as day,
                COUNT(*) as request_count,
                AVG(response_time) as avg_response_time,
                MAX(response_time) as max_response_time
            FROM requests
            WHERE created_at >= %s
            GROUP BY DATE_TRUNC('day', created_at)
            ORDER BY day
        """, (last_week,))
        
        rows = cursor.fetchall()
        
        # Generate HTML report
        html = """
        <html>
        <body style="font-family: Arial, sans-serif;">
            <h1>Weekly Performance Report</h1>
            <p>Report generated: {}</p>
            <p>Period: {} to {}</p>
            
            <table border="1" cellpadding="10" style="border-collapse: collapse;">
                <tr style="background-color: #f2f2f2;">
                    <th>Day</th>
                    <th>Requests</th>
                    <th>Avg Response Time (ms)</th>
                    <th>Max Response Time (ms)</th>
                </tr>
        """.format(
            datetime.now().strftime('%Y-%m-%d %H:%M:%S'),
            last_week.strftime('%Y-%m-%d'),
            datetime.now().strftime('%Y-%m-%d')
        )
        
        total_requests = 0
        total_response_time = 0
        
        for row in rows:
            day, count, avg_time, max_time = row
            html += f"""
                <tr>
                    <td>{day.strftime('%Y-%m-%d')}</td>
                    <td>{count}</td>
                    <td>{avg_time:.2f}</td>
                    <td>{max_time:.2f}</td>
                </tr>
            """
            total_requests += count
            total_response_time += avg_time
        
        avg_response = total_response_time / len(rows) if rows else 0
        
        html += f"""
            </table>
            
            <h2>Summary</h2>
            <ul>
                <li>Total Requests: {total_requests}</li>
                <li>Average Response Time: {avg_response:.2f} ms</li>
            </ul>
        </body>
        </html>
        """
        
        # Save report to file
        report_filename = f"report_{datetime.now().strftime('%Y%m%d_%H%M%S')}.html"
        with open(f'/tmp/{report_filename}', 'w') as f:
            f.write(html)
        
        print("[{}] Report saved to /tmp/{}".format(datetime.now(), report_filename))
        
        # Upload to S3
        print("[{}] Uploading report to S3...".format(datetime.now()))
        s3 = boto3.client('s3')
        with open(f'/tmp/{report_filename}', 'rb') as f:
            s3.put_object(
                Bucket=os.environ['AWS_S3_BUCKET'],
                Key=f"weekly_reports/{report_filename}",
                Body=f.read(),
                ContentType='text/html'
            )
        
        print("[{}] Uploaded to S3: weekly_reports/{}".format(datetime.now(), report_filename))
        
        # Send email
        print("[{}] Sending email...".format(datetime.now()))
        send_email(html)
        
        # Cleanup
        cursor.close()
        conn.close()
        
        print("[{}] Report generation completed successfully ✓".format(datetime.now()))
        return 0
        
    except Exception as e:
        print("[{}] Error during report generation: {}".format(datetime.now(), str(e)))
        return 1

def send_email(html_content):
    """Send email with report"""
    msg = MIMEMultipart('alternative')
    msg['Subject'] = f"Weekly Performance Report - {datetime.now().strftime('%Y-%m-%d')}"
    msg['From'] = os.environ['SMTP_USER']
    msg['To'] = os.environ['REPORT_RECIPIENTS']
    
    msg.attach(MIMEText(html_content, 'html'))
    
    # Send email
    server = smtplib.SMTP(os.environ['SMTP_HOST'], int(os.environ['SMTP_PORT']))
    server.starttls()
    server.login(os.environ['SMTP_USER'], os.environ['SMTP_PASSWORD'])
    server.send_message(msg)
    server.quit()
    
    print("[{}] Email sent successfully".format(datetime.now()))

if __name__ == '__main__':
    exit_code = generate_report()
    exit(exit_code)
```

                echo "[$(date)] Compressing: $file"
                gzip "$file"
              done
              
              # Generate summary
              TOTAL_SIZE=$(du -sh "$LOGS_DIR" | cut -f1)
              echo "[$(date)] =========================================="
              echo "[$(date)] Cleanup Summary:"
              echo "[$(date)] Total logs directory size: $TOTAL_SIZE"
              echo "[$(date)] Cleanup completed successfully ✓"

              requests:
                cpu: "100m"

## Best Practices

### 1. **Always Use Explicit Timezone**

```yaml
# ✅ Good (explicit timezone)
spec:
  schedule: "0 2 * * *"
  timezone: "Asia/Kolkata"

# ❌ Bad (assumes UTC)
spec:
  schedule: "0 2 * * *"
  # Person expects 2 AM IST, actually runs at 2 AM UTC!
```

### 2. **Set Appropriate Concurrency Policy**

```yaml
# ✅ Good (prevents overlapping)
concurrencyPolicy: Forbid

# ❌ Bad (can cause issues)
concurrencyPolicy: Allow
# If job takes longer than interval, multiple concurrent jobs!
```

### 3. **Configure History Limits**

```yaml
# ✅ Good (keeps relevant history)
successfulJobsHistoryLimit: 3
failedJobsHistoryLimit: 2

# ❌ Bad (unbounded growth)
# No history limits = thousands of old jobs clutter cluster
```

### 4. **Set Job Timeout**

```yaml
jobTemplate:
  spec:
    activeDeadlineSeconds: 1800  # 30 minutes
    
    # Without timeout: hung job runs forever
    # With timeout: job killed after 30 min
```

### 5. **Use ttlSecondsAfterFinished for Cleanup**

```yaml
jobTemplate:
  spec:
    ttlSecondsAfterFinished: 86400  # Auto-delete after 1 day
    
    # Keeps cluster clean
    # But keeps logs long enough for troubleshooting
```

### 6. **Comprehensive Logging**

```bash
# ✅ Good (timestamp and status)
echo "[$(date)] Step 1: Starting backup..."
echo "[$(date)] Step 2: Database dump complete"
echo "[$(date)] Step 3: Upload to S3 done"

# ❌ Bad (no indication of progress)
./backup_script  # Silent execution
```

### 7. **Test Schedule Expression**

```bash
# Tools to validate cron expressions:
# https://crontab.guru/

# Example: "0 9 * * 1-5"
# Description: At 09:00 on every day-of-week from Monday through Friday

# Verify in kubectl:
kubectl get cronjob
kubectl describe cronjob daily-backup
# Shows: SCHEDULE, TIMEZONE, LAST SCHEDULE, NEXT SCHEDULE
```

### 8. **Handle Timezone Changes**

```yaml
# Problem: CronJob created with implicit UTC timezone
# Then explicit timezone added later
# Old jobs still run on UTC, new jobs on specified timezone

# Solution: Always specify timezone from the beginning
spec:
  schedule: "0 2 * * *"
  timezone: "Asia/Kolkata"  # Be explicit!
```

## Troubleshooting

### Problem 1: CronJob Not Creating Jobs

```bash
# Check CronJob status
kubectl describe cronjob daily-backup

# Look for conditions:
# - Active: true/false
# - CronScheduleNotAllowed: error in schedule syntax

# Check events for errors
# Most common: Invalid cron syntax

# Solution: Validate schedule
# Use https://crontab.guru/ or kubelet logs
```

**Common Schedule Errors:**
```yaml
# ❌ Wrong: Too many fields
schedule: "0 2 * * * *"  # 6 fields (wrong)

# ✅ Correct: 5 fields
schedule: "0 2 * * *"    # 5 fields (right)

# ❌ Wrong: Invalid hour
schedule: "0 25 * * *"   # Hour 25 doesn't exist

# ✅ Correct: Hour range 0-23
schedule: "0 23 * * *"   # 11 PM

# ❌ Wrong: Invalid day of week
schedule: "0 0 * * 8"    # Day 8 doesn't exist

# ✅ Correct: Day range 0-7
schedule: "0 0 * * 0"    # Sunday
```

### Problem 2: Jobs Not Running at Expected Time

```bash
# Check last scheduled time
kubectl describe cronjob daily-backup

# Look for: "Last Schedule" field
# If old, schedule might be wrong

# Verify timezone
kubectl get cronjob daily-backup -o yaml | grep timezone

# Problem: Schedule is "0 2 * * *" but timezone shows "UTC"
# Expected: 2 AM in your timezone
# Actual: 2 AM UTC (might be different)

# Solution: Add explicit timezone
kubectl patch cronjob daily-backup -p '{"spec":{"timezone":"Asia/Kolkata"}}'
```

### Problem 3: Job Keeps Failing

```bash
# Check job status
kubectl get jobs -l cronjob=daily-backup

# View latest job logs
LATEST=$(kubectl get jobs -l cronjob=daily-backup --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1].metadata.name}')
kubectl logs job/$LATEST

# Common failures:
# 1. Image not found
# 2. Environment variable missing
# 3. Volume mount issues
# 4. Permissions

# Solution:
# Fix the underlying issue, then manually test the job
kubectl create job test-job-$(date +%s) --from=cronjob/daily-backup
kubectl logs job/test-job-...
```

### Problem 4: Too Many Old Jobs

```bash
# Check job count
kubectl get jobs | wc -l

# If too many, increase history limits
kubectl patch cronjob daily-backup -p '{"spec":{"successfulJobsHistoryLimit":3}}'

# This cleans up old jobs automatically

# Or manually delete old jobs
kubectl delete jobs -l cronjob=daily-backup
```

### Problem 5: Timezone Not Working

```bash
# Check if timezone is set
kubectl get cronjob daily-backup -o jsonpath='{.spec.timezone}'

# If empty, timezone not set
# Check Kubernetes version (timezone support added in 1.25+)

# Workaround for older versions:
# Use UTC schedule + UTC timezone
schedule: "0 2 * * *"
timezone: "UTC"

# Then manually convert to UTC
# Example: Want 2 AM IST (UTC+5:30)
# IST 2:00 AM = UTC 8:30 PM previous day
# So: schedule: "30 20 * * *"
```

## Conclusion

**CronJob is essential for:**
- Scheduled recurring tasks (daily, weekly, monthly)
- Automated maintenance (backups, cleanup, reports)
- Guaranteed execution (runs on schedule, not dependent on manual intervention)

**Key Takeaways:**
1. **CronJob creates Jobs on schedule** - Automation through scheduling
2. **Cron syntax** - Standard Unix format (5 fields: minute hour day month day-of-week)
3. **Timezone matters** - Explicitly set timezone to avoid confusion
4. **Concurrency control** - Choose appropriate policy (Allow/Forbid/Replace)
5. **History tracking** - Keep useful history, clean up old jobs
6. **Timeout protection** - Prevent hung jobs with activeDeadlineSeconds
7. **Monitoring** - Track successful and failed runs

**Remember:**
- CronJob ≠ scheduled container
- CronJob = Automated Job creator on a schedule
- Each scheduled execution creates a separate Job object
- Old Jobs can be cleaned up automatically
