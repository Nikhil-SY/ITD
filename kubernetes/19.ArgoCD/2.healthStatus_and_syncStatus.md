## Introduction

### What is ArgoCD?
ArgoCD is a declarative, GitOps continuous delivery tool for Kubernetes. It allows you to define your desired application state in a Git repository, and ArgoCD automatically syncs your Kubernetes cluster to match that desired state.

### Why Do We Need Status Indicators?
Imagine you're managing a restaurant: you need to know:
- **Sync Status**: Is the current menu (in the kitchen) the same as the menu we decided (on our website)?
- **Health Status**: Is each dish being prepared correctly and is it edible?

Similarly, in ArgoCD:
- **Sync Status**: Does the running application match what's in Git?
- **Health Status**: Are all components of the application running properly?

## Core Concepts

### The Three-Tier Architecture

```
┌─────────────────────────────────────────────────────┐
│               Git Repository (Source of Truth)      │
│         Contains YAML manifests/Helm charts         │
└────────────────┬────────────────────────────────────┘
                 │
                 │ ArgoCD watches and compares
                 ▼
┌─────────────────────────────────────────────────────┐
│            ArgoCD Controller Server                  │
│    • Fetches desired state from Git                 │
│    • Compares with actual state in cluster          │
│    • Reports Sync Status & Health Status            │
└────────────────┬────────────────────────────────────┘
                 │
                 │ Applies manifests
                 ▼
┌─────────────────────────────────────────────────────┐
│           Kubernetes Cluster (Actual State)          │
│    • Running Pods, Services, ConfigMaps, etc.       │
└─────────────────────────────────────────────────────┘
```

### Key Definitions

**Sync Status**: Compares Git (desired) vs Cluster (actual)
**Health Status**: Evaluates if resources are running correctly

## Sync Status Types

Sync Status tells you whether your cluster matches the Git repository. It's about **consistency**, not **correctness**.

### 1. **Synced** ✅

**What it means**: 
The application in the Git repository matches exactly what's running in the Kubernetes cluster.

**Why it exists**:
Confirms that your desired configuration has been successfully deployed.

**How it works**:
- ArgoCD compares YAML from Git with actual resources in the cluster
- If every resource matches, status = Synced
- This happens every ~3 minutes (default sync interval) or when you manually sync

**Example**:
```yaml
# Git Repository (app.yaml)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-app
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: nginx
        image: nginx:1.21

# Kubernetes Cluster (kubectl get deployment nginx-app -o yaml)
# Returns the EXACT same configuration
# Result: STATUS = SYNCED ✅
```

**Visual Example**:
```
Git State              vs    Cluster State
nginx: 3 replicas           nginx: 3 replicas  ✓ Match
image: nginx:1.21           image: nginx:1.21  ✓ Match
memory: 512Mi               memory: 512Mi      ✓ Match
──────────────────────────────────────────────
Result: SYNCED
```

---

### 2. **OutOfSync** 🔄

**What it means**:
The application in Git doesn't match what's currently running in the cluster. They are **misaligned**.

**Why it exists**:
Alerts you that:
- Git has changed but not yet applied to cluster
- Someone manually edited something in the cluster (drift detection)
- A sync operation is in progress
- A sync operation failed

**How it works**:
- ArgoCD detects any difference between Git and cluster
- Example: Git says 3 replicas, cluster has 2 replicas
- Status = OutOfSync until differences are resolved

**Example Scenario 1: Someone Manually Changed the Cluster (Drift)**
```yaml
# Git Repository (app.yaml)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-app
spec:
  replicas: 3

# Someone manually did: kubectl scale deployment nginx-app --replicas=1
# Cluster now has 1 replica

# ArgoCD detects the mismatch:
# Git wants 3, Cluster has 1
# Result: STATUS = OUT OF SYNC 🔄
```

**Example Scenario 2: Git Was Updated, Sync Hasn't Happened Yet**
```yaml
# Original Git (10:00 AM)
spec:
  replicas: 2

# Updated Git (10:15 AM)
spec:
  replicas: 5

# Cluster still has 2 replicas (hasn't synced yet)
# Result: STATUS = OUT OF SYNC 🔄
# (Will automatically sync in ~3 minutes, or immediately if manual sync)
```

**Visual Comparison**:
```
Git State              vs    Cluster State
nginx: 5 replicas           nginx: 3 replicas  ✗ Mismatch
image: nginx:1.22           image: nginx:1.21  ✗ Mismatch
memory: 1Gi                 memory: 512Mi      ✗ Mismatch
──────────────────────────────────────────────
Result: OUT OF SYNC
```

---

### 3. **Unknown** ❓

**What it means**:
ArgoCD cannot determine the sync status because it lacks information about the application.

**Why it exists**:
Occurs when ArgoCD hasn't been able to fetch and analyze the desired state yet.

**When it happens**:
- Application is being created/initialized
- Git repository is inaccessible (network issue, authentication failure)
- ArgoCD controller hasn't yet evaluated the application
- The Git reference (branch/tag) doesn't exist

**Example**:
```yaml
# New Application Created
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: new-app
spec:
  source:
    repoURL: https://github.com/nonexistent/repo  # Invalid repo
    path: apps

# ArgoCD tries to fetch from this repo
# Repository is unreachable
# Result: STATUS = UNKNOWN ❓
# Error message: "Failed to fetch repository"
```

**When does this resolve?**
- Once Git becomes accessible
- Once the Application resource is properly configured
- After ArgoCD successfully evaluates the application (usually within 1-2 minutes)

## Health Status Types

Health Status evaluates whether resources are **functioning correctly**. It's about **correctness**, not **deployment**.

### 1. **Healthy** 💚

**What it means**:
All resources in the application are running correctly and have reached their desired state.

**Why it exists**:
Confirms your application is working as expected, not just deployed.

**How it works**:
- ArgoCD checks each resource (Deployment, Service, Pod, etc.)
- Each resource type has specific health criteria
- All resources must be healthy for overall app to be healthy

**Health Criteria by Resource Type**:

```
┌─────────────────────────────────────────────────────────┐
│           Resource Type      │  Health Criteria         │
├──────────────────────────────┼──────────────────────────┤
│ Deployment                   │ All replicas running &   │
│                              │ ready                    │
├──────────────────────────────┼──────────────────────────┤
│ StatefulSet                  │ All replicas ready &     │
│                              │ at target generation     │
├──────────────────────────────┼──────────────────────────┤
│ DaemonSet                    │ All scheduled pods ready │
├──────────────────────────────┼──────────────────────────┤
│ Service                      │ Has endpoints (if type   │
│                              │ is not ExternalName)     │
├──────────────────────────────┼──────────────────────────┤
│ Pod                          │ All containers running   │
│                              │ & ready                  │
├──────────────────────────────┼──────────────────────────┤
│ Job                          │ Completed successfully   │
├──────────────────────────────┼──────────────────────────┤
│ CronJob                      │ No failed jobs in last   │
│                              │ run                      │
├──────────────────────────────┼──────────────────────────┤
│ ConfigMap/Secret             │ Always healthy           │
│                              │ (no running requirements)│
└─────────────────────────────────────────────────────────┘
```

**Example: Healthy Application**
```yaml
# Git (app.yaml)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.21
        ports:
        - containerPort: 80

---
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  type: ClusterIP
  ports:
  - port: 80
    targetPort: 80
  selector:
    app: nginx

# Cluster Status
# Deployment: 3 desired, 3 ready, 3 updated ✓
# Service: Has 3 endpoints pointing to pods ✓
# All Pods: Running and Ready ✓
# Result: HEALTH = HEALTHY 💚
```

---

### 2. **Progressing** 🔵

**What it means**:
The application is in the process of becoming healthy. It's not broken, just not there yet.

**Why it exists**:
Provides visibility into deployment progress. Shows that work is being done.

**How it works**:
- Deployment has replicas rolling out or updating
- StatefulSet is scaling up/down
- Pods are being scheduled or starting
- The resource shows it's moving toward the desired state

**When it occurs**:
- Immediately after deployment
- During rolling updates
- When scaling replicas
- When new images are being pulled

**Example Scenario 1: Initial Deployment**
```yaml
# Just deployed nginx with 3 replicas
# At time T0:
# Deployment: 3 desired, 0 ready, 0 updated
# Result: HEALTH = PROGRESSING 🔵
# (ArgoCD: "Waiting for 3 replicas to be ready")

# At time T5 (5 seconds later):
# Deployment: 3 desired, 1 ready, 2 updating
# Result: HEALTH = PROGRESSING 🔵

# At time T15 (15 seconds later):
# Deployment: 3 desired, 3 ready, 3 updated
# Result: HEALTH = HEALTHY 💚
```

**Example Scenario 2: Rolling Update**
```yaml
# Original: nginx:1.20 with 3 replicas (all running)
# Updated: nginx:1.21 with 3 replicas

# During update:
# 1 pod running nginx:1.20
# 2 pods starting nginx:1.21 (pulling image)
# Result: HEALTH = PROGRESSING 🔵

# After update completes:
# 3 pods running nginx:1.21
# Result: HEALTH = HEALTHY 💚
```

**Progressing vs Healthy Timeline**:
```
Time     Status              What's happening
────────────────────────────────────────────────────
T0       PROGRESSING 🔵      Deployment created
T3       PROGRESSING 🔵      1/3 pods running
T8       PROGRESSING 🔵      2/3 pods running
T15      HEALTHY 💚          3/3 pods ready
T30      HEALTHY 💚          Stable, all running
```

---

### 3. **Degraded** 🔴

**What it means**:
The application is partially working or has errors, but it's not completely down.

**Why it exists**:
Alerts you that something is wrong but the app hasn't fully failed.

**How it works**:
- Some resources failed to deploy
- Some resources are running but with errors
- Health checks are failing
- Resource quotas have been exceeded
- ImagePullBackOff or similar errors

**When it occurs**:

```
Scenario 1: ImagePullBackOff
────────────────────────────────
# Git asks for: image: myapp:nonexistent
# Cluster tries to pull this image
# Image doesn't exist in registry
# Pod remains in Pending
# Result: HEALTH = DEGRADED 🔴

Scenario 2: CrashLoopBackOff
────────────────────────────────
# Pod starts but crashes immediately
# Kubernetes restarts it
# It crashes again (repeats)
# Result: HEALTH = DEGRADED 🔴

Scenario 3: Insufficient Resources
────────────────────────────────────
# Pod requests 10Gi memory
# Node only has 2Gi available
# Pod cannot be scheduled
# Result: HEALTH = DEGRADED 🔴

Scenario 4: Liveness Probe Failure
────────────────────────────────────
# Pod is running but health check fails
# Kubernetes keeps restarting it
# Pod cannot become Ready
# Result: HEALTH = DEGRADED 🔴
```

**Example YAML: Degraded Application**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: app
        image: myrepo/app:v1  # This image doesn't exist!
        resources:
          requests:
            memory: 10Gi  # Node only has 2Gi!
        livenessProbe:
          httpGet:
            path: /health
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 10

# Cluster Status
# Deployment: 3 desired, 0 ready (ImagePullBackOff)
# Pods: Pending (cannot pull image, insufficient resources)
# Result: HEALTH = DEGRADED 🔴
# Message: "Pods are not ready. ImagePullBackOff"
```

### 4. **Suspended** ⏸️

**What it means**:
The application or specific resources have been intentionally paused/disabled.

**Why it exists**:
Allows you to temporarily stop an application without deleting it (useful for maintenance, cost savings, etc.).

**How it works**:
- Application is paused at the ArgoCD Application level
- Specific resources have suspend fields set to true
- Example: CronJobs can be suspended

**When it occurs**:
- When you pause an ArgoCD Application
- CronJob with `suspend: true`
- Manual pause to prevent auto-sync

**Example: Suspended CronJob**
```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup-job
spec:
  suspend: true  # This job won't run
  schedule: "0 2 * * *"  # Would run at 2 AM
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup
            image: backup:latest

# Result: HEALTH = SUSPENDED ⏸️
# The job exists but won't execute until suspend is set to false
```

**Example: Paused Application in ArgoCD**
```bash
# Pause an application (via CLI or UI)
argocd app pause myapp

# Application status:
# SYNC: Unknown
# HEALTH: Suspended ⏸️
# (Auto-sync disabled, no automatic updates)

# Resume later:
argocd app resume myapp
```

---

### 5. **Missing** ❌

**What it means**:
Required resources don't exist in the cluster but are defined in Git.

**Why it exists**:
Indicates a deployment failure where expected resources were never created.

**How it works**:
- Resource is defined in Git
- ArgoCD tries to create it in cluster
- Creation fails for some reason
- Resource never appears in cluster

**When it occurs**:
- RBAC permissions missing (can't create resources)
- Custom Resource Definition (CRD) not installed
- Cluster quota exceeded
- Invalid resource syntax

**Example Scenario 1: CRD Not Installed**
```yaml
# Git has this custom resource
apiVersion: mycompany.com/v1
kind: CustomApp
metadata:
  name: my-custom-app
spec:
  replicas: 3

# But the CRD isn't installed in the cluster
# kubectl get crd customapps.mycompany.com
# # Error: not found

# ArgoCD tries to create it
# Fails because CRD doesn't exist
# Result: HEALTH = MISSING ❌
```

**Example Scenario 2: RBAC Permission Denied**
```yaml
# Git defines this resource
apiVersion: v1
kind: Secret
metadata:
  name: prod-secrets
  namespace: restricted-namespace

# ArgoCD's ServiceAccount doesn't have permission to create secrets
# In that namespace

# kubectl get rolebindings -n restricted-namespace
# # (ArgoCD's account is not listed)

# Result: HEALTH = MISSING ❌
# Error: "forbidden: User 'argocd' cannot create secrets"
```

## State Transition Scenarios

### Scenario 1: Fresh Deployment

```
Time    Sync Status         Health Status       What's happening
────────────────────────────────────────────────────────────────────
T0      OutOfSync 🔄        Unknown ❓          App created, initial sync
        ↓                   ↓
T1      Synced ✅           Progressing 🔵      Manifests applied to cluster
        ↓                   ↓
T5      Synced ✅           Progressing 🔵      Pods being scheduled
        ↓                   ↓
T10     Synced ✅           Progressing 🔵      Images being pulled
        ↓                   ↓
T20     Synced ✅           Healthy 💚          All resources ready
```

**What to do in each stage**:
- **OutOfSync + Unknown**: Wait a moment for ArgoCD to evaluate
- **Synced + Progressing**: Monitor logs, normal deployment in progress
- **Synced + Healthy**: Application ready for use

---

### Scenario 2: Manual Cluster Change (Drift)

```
Time    Sync Status         Health Status       What happened
────────────────────────────────────────────────────────────────────
T0      Synced ✅           Healthy 💚          Normal running state

        Someone manually edits cluster:
        kubectl scale deployment myapp --replicas=1

T0.5    OutOfSync 🔄        Healthy 💚          Drift detected!
        ↓                   ↓
T3      Synced ✅           Degraded 🔴         ArgoCD auto-synced
                                                (still 1 replica, pods
                                                 starting back up)
T8      Synced ✅           Progressing 🔵      Pods scaling up
        ↓                   ↓
T15     Synced ✅           Healthy 💚          All replicas running
```

**Why this happens**:
1. Manual change creates drift → OutOfSync
2. Auto-sync kicks in → replicas correct but still starting
3. Pods take time to become ready → Progressing → Healthy

**How to prevent**:
```yaml
# Set sync policy to prevent drifting
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: myapp
spec:
  syncPolicy:
    automated:
      prune: true      # Delete resources removed from Git
      selfHeal: true   # Auto-sync when drift detected
    syncOptions:
    - CreateNamespace=true
```

---

### Scenario 3: Image Pull Failure

```
Time    Sync Status         Health Status       What's happening
────────────────────────────────────────────────────────────────────
T0      OutOfSync 🔄        Unknown ❓          Deployment submitted

T2      Synced ✅           Progressing 🔵      Trying to pull image

        Docker registry returns 404 (image doesn't exist)

T5      Synced ✅           Degraded 🔴         ImagePullBackOff
        ↓                   (stuck here)        Pod cannot start
```

**How to recover**:
```bash
# Check pod events
kubectl describe pod <pod-name>
# Shows: "Failed to pull image 'myimage:typo': repository not found"

# Fix the image in Git
# (correct: myimage:latest, was: myimage:typo)

# Commit and push to Git

# ArgoCD detects change
# Re-syncs with corrected image
# Pod pulls successfully

T15     Synced ✅           Healthy 💚          Running with correct image
```

---

### Scenario 4: Resource Update (No Downtime)

```
Time    Sync Status         Health Status       What's happening
────────────────────────────────────────────────────────────────────
T0      Synced ✅           Healthy 💚          All 3 pods running

        Update committed to Git: image nginx:1.20 → nginx:1.21

T0.5    OutOfSync 🔄        Healthy 💚          Change detected in Git

T1      Synced ✅           Progressing 🔵      Rolling update starts
                                                Old: 3 running
                                                New: 1 pod new image

T3      Synced ✅           Progressing 🔵      2 old, 1 new running

T6      Synced ✅           Progressing 🔵      1 old, 2 new running

T10     Synced ✅           Healthy 💚          All 3 new image running
```

**What this shows**:
- Service remains available throughout (rolling update)
- Sync and Health track deployment progress
- No downtime during update

## Troubleshooting Guide

### Problem 1: OutOfSync Status Won't Go Away

**Symptoms**:
```
Application Status: OutOfSync
Message: "Waiting for sync"
Time stuck: > 5 minutes
```

**Root Causes & Solutions**:

| Cause | How to detect | Solution |
|-------|---------------|----------|
| Auto-sync disabled | Check Application.spec.syncPolicy | Enable auto-sync in UI or CLI: `argocd app set myapp --sync-policy automated` |
| Invalid Git credentials | ArgoCD logs: "authentication failed" | Update Git credentials in ArgoCD settings |
| Git branch doesn't exist | Check Git repo for the branch | Change target branch in Application.spec.source.targetRevision |
| Sync failed silently | Check ArgoCD controller logs | Check detailed error in UI, fix manifests |
| ArgoCD has no permissions | Logs: "forbidden" or "permission denied" | Update RBAC for ArgoCD's ServiceAccount |

**How to manually trigger sync**:
```bash
# Via CLI
argocd app sync myapp

# Via kubectl
kubectl patch application myapp -p '{"spec":{"syncPolicy":{"automated":{"selfHeal":true}}}}' --type merge

# Via UI
# Click "Sync" button in ArgoCD dashboard
```

**Diagnostic commands**:
```bash
# Check if app is syncing
argocd app get myapp

# Check ArgoCD controller logs
kubectl logs -n argocd deployment/argocd-application-controller

# Check specific application events
kubectl describe application myapp -n argocd

# Compare Git vs Cluster
argocd app diff myapp
```

### Problem 2: Synced but Health is Degraded

**Symptoms**:
```
Sync Status: Synced ✅
Health Status: Degraded 🔴
Everything deployed, but app not running
```

**Root Causes & Solutions**:

| Cause | Symptoms | Solution |
|-------|----------|----------|
| ImagePullBackOff | Pod pending, image not found | Verify image exists in registry, check image name/tag |
| CrashLoopBackOff | Pod restarts repeatedly | Check pod logs: `kubectl logs <pod> --previous` |
| Insufficient resources | Pod pending, node selector mismatch | Increase node resources or reduce pod requests |
| Liveness probe failing | Pod keeps restarting | Check probe configuration, may be too strict |
| ConfigMap/Secret missing | App can't start without config | Verify ConfigMap/Secret are applied: `kubectl get configmap <name>` |

**Debug degraded app**:
```bash
# 1. List all resources in the app
kubectl get all -l app=myapp

# 2. Check pod status
kubectl get pods -l app=myapp
# Output: NAME                READY  STATUS               RESTARTS
#         myapp-abc123        0/1    ImagePullBackOff     0

# 3. Describe the problematic pod
kubectl describe pod myapp-abc123
# Shows detailed error information

# 4. Check container logs (if available)
kubectl logs myapp-abc123
# If pod can't start, check previous logs
kubectl logs myapp-abc123 --previous

# 5. Check resource quotas
kubectl describe nodes
# Look for "Allocated resources" section

# 6. Check events
kubectl get events --sort-by='.lastTimestamp'
```

---

### Problem 3: Health Status is Unknown

**Symptoms**:
```
Sync Status: Unknown ❓ or OutOfSync
Health Status: Unknown ❓
App status won't update
```

**Root Causes & Solutions**:

| Cause | How to detect | Solution |
|-------|---------------|----------|
| Git repo unreachable | ArgoCD logs: "connection refused" or "timeout" | Check Git URL, network connectivity, firewall |
| Git credentials invalid | UI shows auth errors | Update credentials in ArgoCD UI (Settings → Repositories) |
| Invalid Application manifest | App definition has syntax errors | Validate YAML: `kubectl apply -f app.yaml --dry-run=client` |
| ArgoCD not installed properly | Controller pod not running | Check ArgoCD deployment: `kubectl get deployment -n argocd` |
| CRD not installed | Error: "unknown kind Application" | Install ArgoCD CRDs: `kubectl apply -k https://github.com/argoproj/argo-cd/manifests/crds` |

**Recovery steps**:
```bash
# 1. Check if ArgoCD is running
kubectl get pods -n argocd

# 2. Check ArgoCD controller logs
kubectl logs -n argocd -l app.kubernetes.io/name=argocd-application-controller -f

# 3. Check if Application CRD exists
kubectl get crd applications.argoproj.io

# 4. Test Git connectivity from ArgoCD pod
kubectl exec -it deployment/argocd-application-controller -n argocd -- \
  git ls-remote https://github.com/yourusername/yourrepo main

# 5. Manually re-evaluate application
argocd app get myapp --refresh
```

### Problem 4: Synced but Status Shows OutOfSync (False Positive)

**Symptoms**:
```
Sync Status shows: OutOfSync 🔄
But cluster actually matches Git
(Status is lying)
```

**Root Causes & Solutions**:

| Cause | Why it happens | Solution |
|-------|----------------|----------|
| Computed fields | K8s adds fields not in Git | Use `argocd app diff` to see differences |
| Default values | Resources get default values | Add defaults to Git YAML to match cluster |
| Floating values | Fields that change (timestamps) | Ignore these in ArgoCD: spec.syncOptions[ignoreDifferences] |
| Server-side apply | K8s modifies during apply | Add `spec.syncOptions[]: [ServerSideApply=true]` |

**Example: Default Values Causing False Positive**
```yaml
# Git version (minimal)
apiVersion: v1
kind: Service
metadata:
  name: myservice
spec:
  type: ClusterIP  # Explicitly set
  ports:
  - port: 80
    targetPort: 8080

# Cluster version (Kubernetes adds defaults)
apiVersion: v1
kind: Service
metadata:
  name: myservice
spec:
  type: ClusterIP
  sessionAffinity: None  # ← Added by Kubernetes
  sessionAffinityConfig: null  # ← Added by Kubernetes
  ipFamilies: [IPv4]  # ← Added by Kubernetes
  ipFamilyPolicy: SingleStack  # ← Added by Kubernetes
  ports:
  - port: 80
    targetPort: 8080
    protocol: TCP  # ← Added by Kubernetes
    name: ""  # ← Added by Kubernetes

# Result: OutOfSync (false positive)

# Solution: Check with
argocd app diff myapp
# See exactly what's different

# Then add fields to Git or ignore differences:
spec:
  syncPolicy:
    syncOptions:
    - ignoreDifferences:
      - group: ""
        kind: Service
        jsonPointers:
        - /spec/sessionAffinity
        - /spec/sessionAffinityConfig
        - /spec/ipFamilies
```

### Problem 5: Health Status Stuck in Progressing

**Symptoms**:
```
Health Status: Progressing 🔵 (for more than 5 minutes)
Pods not becoming Ready
"Waiting for all replicas to be ready"
```

**Root Causes & Solutions**:

| Cause | How to detect | Solution |
|-------|---------------|----------|
| Pod waiting to be scheduled | `kubectl get pods`: NAME        READY  STATUS  `Pending` | Check node resources: `kubectl describe nodes` |
| Image still being pulled | Pod events show `Pulling` | Check image size, network bandwidth, registry timeout |
| Init container stuck | Pod shows `Init:0/1` | Check init container logs: `kubectl logs <pod> -c <init-name>` |
| Readiness probe failing | Pod shows `Running` but `0/1 Ready` | Adjust probe settings or fix app health endpoint |
| Persistent volume not available | Pod pending with volume errors | Check PV status: `kubectl get pv` |

**Diagnostic checklist**:
```bash
# 1. Check pod status
kubectl get pods -o wide
# Look for: NAME  READY  STATUS  NODE
#           app   0/1    Pending node-1

# 2. If Pending, check why
kubectl describe pod <pod-name>
# Look at "Events" section

# 3. If Running but not Ready, check readiness probe
kubectl get pod <pod-name> -o yaml | grep -A 10 readinessProbe

# 4. Check container logs
kubectl logs <pod-name> -c <container-name>

# 5. Check for resource constraints
kubectl top nodes
kubectl top pods

# 6. Manual pod test (if image supports it)
kubectl run -it --rm debug --image=busybox -- /bin/sh
# Try to hit the app endpoint
wget http://<pod-ip>:8080
```

**How to fix readiness probe issues**:
```yaml
# Original (too strict)
readinessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 5    # Too short
  periodSeconds: 5          # Too frequent
  failureThreshold: 3       # Fails too quick

# Fixed (more lenient)
readinessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 30   # Give app time to start
  periodSeconds: 10         # Check every 10s
  failureThreshold: 5       # Allow failures
  timeoutSeconds: 5         # Per-check timeout
```

## Best Practices

### 1. Enable Auto-Sync with SelfHeal
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: myapp
spec:
  syncPolicy:
    automated:
      prune: true    # Remove resources deleted from Git
      selfHeal: true # Auto-sync on drift detection
    syncOptions:
    - CreateNamespace=true
    retry:
      limit: 5
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m
```

**Why**: Prevents drift, keeps cluster in sync with Git

### 2. Set Appropriate Timeouts
```yaml
spec:
  syncPolicy:
    syncOptions:
    - Timeout=5m  # Wait max 5 min for sync
```

**Why**: Prevents indefinite waiting for stuck resources

### 3. Use Resource Limits
```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      containers:
      - name: app
        resources:
          requests:
            cpu: 250m
            memory: 256Mi
          limits:
            cpu: 500m
            memory: 512Mi
```

**Why**: Prevents runaway resource usage, enables better health prediction

### 4. Configure Readiness Probes
```yaml
readinessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10
  failureThreshold: 3
  timeoutSeconds: 5
```

**Why**: Accurate health reporting, prevents traffic to broken pods

### 5. Monitor Status Changes
```bash
# Watch status in real-time
argocd app wait myapp --sync --timeout=600s

# Get detailed status
argocd app get myapp --refresh --show-operation

# Watch cluster as well
kubectl get deployment -w
kubectl get pods -w
```

## Conclusion

**Key Takeaways**:

1. **Sync Status** (Git ↔ Cluster): Is config aligned?
   - Synced ✅: Yes
   - OutOfSync 🔄: No, need sync
   - Unknown ❓: Can't tell yet

2. **Health Status** (Are resources working?): Is app functional?
   - Healthy 💚: Yes, all working
   - Progressing 🔵: Deploying, not ready yet
   - Degraded 🔴: Broken, errors present
   - Other: Suspended, Missing, Unknown

3. **They're Independent**: App can be Synced but Degraded (deployed but broken)

4. **Use Both for Troubleshooting**:
   - OutOfSync + Degraded → Fix and re-sync
   - Synced + Degraded → Fix the running app
   - Synced + Progressing → Wait, it's normal
   - Synced + Healthy → You're good!

5. **Automate Everything**:
   - Enable auto-sync with selfHeal
   - Set resource limits
   - Configure probes
   - Monitor actively

This understanding allows you to quickly diagnose and resolve any ArgoCD application issues in production.
