# RBAC in Kubernetes (Role-Based Access Control) — From Scratch

## 1. What is RBAC?

**RBAC (Role-Based Access Control)** is Kubernetes authorization mechanism used to control **who can do what** on Kubernetes resources.

Example:

* Developer → Can view pods and deploy applications
* Tester → Can only view logs
* Admin → Full cluster access

Without RBAC → Anyone with kubeconfig can do anything.
With RBAC → Permissions are restricted.

---

# 2. Authentication vs Authorization

Before RBAC, understand:

### Authentication = Who are you?

Kubernetes checks identity:

* User (`nikhil`)
* ServiceAccount (`jenkins-sa`)
* Group (`dev-team`)

Example:

```bash
kubectl config view
```

Checks current logged-in user.

---

### Authorization = What can you do?

After identity is verified, RBAC checks permissions:

Example:
Can user delete pod?

```bash
kubectl delete pod nginx
```

RBAC decides:
✅ Allowed
❌ Denied

---

# 3. RBAC Components Overview

Main components:

```text
User / ServiceAccount
        ↓
    Role / ClusterRole
        ↓
RoleBinding / ClusterRoleBinding
```

Think:

```text
Identity → Permission → Attach Permission
```

---

# 4. Component 1: Subjects (Who)

RBAC permissions are assigned to:

## A. User

Human user.

Example:

```text
nikhil
john
dev-team-user
```

Kubernetes itself does **not create/manage users directly**. Usually from:

* OpenID Connect
* Certificates
* Cloud IAM

Example:

```bash
kubectl config set-credentials nikhil
```

---

## B. Group

Collection of users.

Example:

```text
developers
admins
qa-team
```

Assign one role to whole group.

---

## C. ServiceAccount

Used by applications/pods.

Example:

* Jenkins pod accessing cluster
* Deployment controller

Create:

```bash
kubectl create serviceaccount myapp-sa
```

YAML:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: myapp-sa
  namespace: default
```

Apply:

```bash
kubectl apply -f sa.yaml
```

Check:

```bash
kubectl get sa
```

---

# 5. Component 2: Role (Namespace Permissions)

Role defines **what actions are allowed inside one namespace**.

Example:
Developer can:

* get pods
* list pods
* create deployments

Cannot:

* delete namespace
* access other namespaces

---

## Role YAML Example

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get","list","watch"]
```

---

## Explanation

### apiGroups

API group of resource.

Examples:

Core resources:

```yaml
apiGroups: [""]
```

Apps resources:

```yaml
apiGroups: ["apps"]
```

Examples:

* Pod → `""`
* Service → `""`
* Deployment → `"apps"`

---

### resources

Which resources.

Example:

```yaml
resources:
- pods
- services
```

---

### verbs

Allowed actions.

Common verbs:

| Verb   | Meaning        |
| ------ | -------------- |
| get    | Read one       |
| list   | List all       |
| watch  | Live changes   |
| create | Create         |
| update | Modify         |
| patch  | Partial modify |
| delete | Delete         |

---

# 6. Component 3: ClusterRole

Cluster-wide role.

Used for:

* Nodes
* Namespaces
* Cluster-wide access
* Same role reusable in many namespaces

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: cluster-pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get","list"]
```

---

## Difference: Role vs ClusterRole

| Feature | Role                | ClusterRole       |
| ------- | ------------------- | ----------------- |
| Scope   | Namespace only      | Whole cluster     |
| Use     | Namespace resources | Cluster resources |
| Example | Pods in dev         | Nodes             |

Examples:

* Read pods in namespace → Role
* Read nodes → ClusterRole

---

# 7. Component 4: RoleBinding

Connects:

```text
User/SA → Role
```

Namespace level.

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-binding
  namespace: dev
subjects:
- kind: User
  name: nikhil
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

Meaning:

* User `nikhil`
* Gets role `pod-reader`
* Only in namespace `dev`

---

# 8. Component 5: ClusterRoleBinding

Connects:

```text
User/SA → ClusterRole
```

Cluster-wide.

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: cluster-read-binding
subjects:
- kind: User
  name: nikhil
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: cluster-pod-reader
  apiGroup: rbac.authorization.k8s.io
```

---

# 9. Practical Flow (Most Important)

Step-by-step:

```text
1. Create ServiceAccount/User
2. Create Role
3. Create Binding
4. Use that identity
5. Test access
```

---

# Practical Example 1: Give Pod Read Access to Jenkins

---

## Step 1 Create ServiceAccount

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: jenkins-sa
  namespace: dev
```

Apply:

```bash
kubectl apply -f sa.yaml
```

---

## Step 2 Create Role

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-read-role
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get","list","watch"]
```

---

## Step 3 Create RoleBinding

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: jenkins-pod-binding
  namespace: dev
subjects:
- kind: ServiceAccount
  name: jenkins-sa
  namespace: dev
roleRef:
  kind: Role
  name: pod-read-role
  apiGroup: rbac.authorization.k8s.io
```

---

## Step 4 Use in Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: testpod
spec:
  serviceAccountName: jenkins-sa
  containers:
  - name: app
    image: nginx
```

Now pod can read pods.

# 10. How to Test RBAC

Very important.

Check permission:

```bash
kubectl auth can-i list pods --as=system:serviceaccount:dev:jenkins-sa
```

Output:

```text
yes
```

Check denied:

```bash
kubectl auth can-i delete pods --as=system:serviceaccount:dev:jenkins-sa
```

Output:

```text
no
```

Best debugging command.

# 11. Common Built-in ClusterRoles

Check:

```bash
kubectl get clusterroles
```

Important ones:

| Role          | Use              |
| ------------- | ---------------- |
| cluster-admin | Full access      |
| admin         | Namespace admin  |
| edit          | Modify resources |
| view          | Read only        |

Example binding:

```bash
kubectl create rolebinding dev-view \
--clusterrole=view \
--serviceaccount=dev:jenkins-sa \
--namespace=dev
```

# Interview Quick Answer

## What is RBAC?

RBAC controls access in Kubernetes by assigning permissions through roles and bindings.

---

## Components

* User
* Group
* ServiceAccount
* Role
* ClusterRole
* RoleBinding
* ClusterRoleBinding

---

## Role vs ClusterRole

* Role → Namespace scope
* ClusterRole → Cluster scope

---

## RoleBinding vs ClusterRoleBinding

* RoleBinding → Namespace permission assignment
* ClusterRoleBinding → Cluster-wide permission assignment

---

## Verify Permission

```bash
kubectl auth can-i <verb> <resource>
```

Example:

```bash
kubectl auth can-i create deployment
```
