# User and ServiceAccount in Kubernetes (RBAC) — Detailed Explanation with YAML

These are the **identities (subjects)** in RBAC.

```text
Authentication (Who are you?)
        ↓
User / ServiceAccount
        ↓
Authorization (What can you do?)
        ↓
Role + Binding
```

---

# 1. User in Kubernetes

## What is a User?

A **User** is usually a **human identity**.

Examples:

* `nikhil`
* `devops-engineer`
* `admin-user`

Used when a human runs:

```bash
kubectl get pods
```

Kubernetes checks:

**Who is this user?**

---

## Important: Kubernetes does NOT create/manage users

Unlike ServiceAccounts, Kubernetes has **no `User` object YAML**.

There is **no**:

```yaml
kind: User   ❌
```

Users are managed externally through:

* **Client certificates (most common in self-managed clusters)**
* OpenID Connect (SSO)
* Cloud IAM:

  * Amazon Web Services IAM
  * Microsoft Azure Active Directory
  * Google Cloud IAM

Kubernetes only **recognizes** the username passed during authentication.

---

## Practical Example: Create a User (Certificate-based)

### Step 1: Generate private key

```bash
openssl genrsa -out nikhil.key 2048
```

Creates:

```text
nikhil.key
```

---

### Step 2: Create CSR (Certificate Signing Request)

```bash
openssl req -new -key nikhil.key -out nikhil.csr -subj "/CN=nikhil"
```

`CN=nikhil`

This becomes the Kubernetes username.

---

### Step 3: Create Kubernetes CSR YAML

```yaml
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: nikhil-csr
spec:
  request: <BASE64_ENCODED_CSR>
  signerName: kubernetes.io/kube-apiserver-client
  usages:
  - client auth
```

Apply:

```bash
kubectl apply -f csr.yaml
```

---

### Step 4: Approve certificate

```bash
kubectl certificate approve nikhil-csr
```

---

### Step 5: Add user to kubeconfig

```bash
kubectl config set-credentials nikhil \
  --client-certificate=nikhil.crt \
  --client-key=nikhil.key
```

Now Kubernetes knows:

```text
User = nikhil
```

---

## Give permissions to User

Example RoleBinding:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: nikhil-read-binding
  namespace: dev
subjects:
- kind: User
  name: nikhil
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

Meaning:

```text
User "nikhil" → gets "pod-reader" role
```

# 2. ServiceAccount in Kubernetes

## What is ServiceAccount?

A **ServiceAccount** is an identity for **applications/pods**.

Used when:

* Jenkins deploys apps
* Prometheus reads metrics
* Your app talks to Kubernetes API

Instead of human login, pods use ServiceAccounts.

---

## Every namespace gets a default ServiceAccount

Check:

```bash
kubectl get sa
```

Output:

```text
NAME      SECRETS   AGE
default   1         5d
```

If you don't specify one:

```yaml
serviceAccountName: default
```

Pod automatically uses `default`.

Usually **not recommended** for production.

---

# Create a ServiceAccount

## YAML

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-sa
  namespace: dev
```

Apply:

```bash
kubectl apply -f sa.yaml
```

Check:

```bash
kubectl get sa -n dev
```

Output:

```text
NAME      AGE
app-sa    5s
```

---

## Use ServiceAccount in Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  namespace: dev
spec:
  serviceAccountName: app-sa
  containers:
  - name: nginx
    image: nginx
```

Now this pod becomes:

```text
Identity = system:serviceaccount:dev:app-sa
```

Kubernetes internally identifies it like this.

---

# ServiceAccount Token

Pods authenticate using **tokens**.

Inside pod:

```bash
kubectl exec -it nginx-pod -- sh
```

Check token:

```bash
ls /var/run/secrets/kubernetes.io/serviceaccount/
```

You’ll see:

```text
token
ca.crt
namespace
```

Token is automatically mounted.

Pod uses it to call Kubernetes API.

---

# Example: Pod calling Kubernetes API

Inside pod:

```bash
curl https://kubernetes.default.svc/api
```

Authentication happens using ServiceAccount token.

---

# Give permissions to ServiceAccount

## Step 1: Create Role

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get","list"]
```

---

## Step 2: Bind Role to ServiceAccount

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: app-sa-binding
  namespace: dev
subjects:
- kind: ServiceAccount
  name: app-sa
  namespace: dev
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

---

## Result

```text
Pod
 ↓
Uses ServiceAccount app-sa
 ↓
RoleBinding connects app-sa to pod-reader
 ↓
Pod can list/get pods
```

---

# Difference: User vs ServiceAccount

| Feature           | User                     | ServiceAccount    |
| ----------------- | ------------------------ | ----------------- |
| Used by           | Humans                   | Pods/Applications |
| Kubernetes object | No                       | Yes               |
| YAML exists       | No                       | Yes               |
| Authentication    | External (cert/OIDC/IAM) | Token             |
| Example           | `nikhil`                 | `jenkins-sa`      |

---

# How to verify permissions

### For User

```bash
kubectl auth can-i get pods --as=nikhil
```

---

### For ServiceAccount

```bash
kubectl auth can-i list pods \
--as=system:serviceaccount:dev:app-sa
```

# Real-world DevOps Example

For your **GoCD / GitHub Actions / Jenkins pipelines:**

Create:

### ServiceAccount

```yaml
kind: ServiceAccount
metadata:
  name: cicd-sa
```

### Role

Allow:

* create deployments
* update services
* read pods

### Binding

Attach role to `cicd-sa`

### Pod uses:

```yaml
serviceAccountName: cicd-sa
```

Then your CI/CD tool can safely deploy to Kubernetes.

# Interview Quick Answer

## What is User?

Human identity authenticated externally and granted permissions via RBAC.

---

## What is ServiceAccount?

Pod/application identity inside Kubernetes used to access cluster resources.

---

## Key difference

```text
User = Human
ServiceAccount = Pod
```

---

## Important point

Kubernetes **does not create User objects**, but **does create ServiceAccount objects** with YAML.
