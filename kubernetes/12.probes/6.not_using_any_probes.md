# If you don’t configure **any probes** (`readiness`, `liveness`, `startup`)

Kubernetes will still run your Pod—but it **won’t actively check your application health**.

## What happens by default

```text
Pod created
   ↓
Container starts
   ↓
Container state = Running
   ↓
Pod marked Ready
   ↓
Service sends traffic immediately
```

### Important:

Kubernetes only checks:

* **Did the container process start?**
* **Is the process still running?**

It does **not** check:

* Is the app ready to serve traffic?
* Is the app hung/deadlocked?
* Is the app still initializing?

---

# 1. No **readiness probe**

### Problem: Traffic may come too early

Example:

* **Spring Boot** app takes **40 sec** to start
* Container process starts in **2 sec**

Without readiness probe:

```text
Container Running
      ↓
Pod marked Ready immediately
      ↓
Service sends traffic
      ↓
App still starting
      ↓
Users get 503 / connection refused
```

### Kubernetes assumes:

```text
Running container = Ready app
```

That assumption can be wrong.

---

# 2. No **liveness probe**

### Problem: Hung app won’t recover automatically

Example:

* App enters deadlock
* Health endpoint stops responding
* Process is still alive

Without liveness probe:

```text
Container process still running
      ↓
Kubernetes thinks everything is fine
      ↓
Broken app stays broken forever
```

No automatic restart.

---

# 3. No **startup probe**

### Problem: Slow apps can be hard to handle safely

If you configure **liveness probe** but no startup probe:

```text
App starts slowly
Liveness checks too early
Liveness fails
Container restarts
CrashLoopBackOff
```

Startup probe prevents that.

---

# Kubernetes defaults (without probes)

| Check                              | Default behavior                       |
| ---------------------------------- | -------------------------------------- |
| **Container running?**             | ✅ Checked automatically by **kubelet** |
| **App ready?**                     | ❌ Not checked                          |
| **App healthy?**                   | ❌ Not checked                          |
| **App startup complete?**          | ❌ Not checked                          |
| **Automatic restart on app hang?** | ❌ No                                   |
| **Traffic blocked until ready?**   | ❌ No                                   |

---

# Example

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: no-probe-pod
spec:
  containers:
  - name: app
    image: myapp
```

No probes.

Kubernetes behavior:

```text
Container starts
Pod = Ready
Service sends traffic
```

That’s it.

---

# When is it okay to skip probes?

Sometimes acceptable for:

* Simple stateless apps
* Very small internal tools
* Short-lived batch **Kubernetes Job**s

But for production apps, probes are usually recommended.

---

## Interview one-liner

**Without probes, Kubernetes only checks whether the container process is running; it does not verify application readiness or health, so traffic may reach an unready app and hung applications may not recover automatically.**
