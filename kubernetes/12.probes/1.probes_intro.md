## Kubernetes Probes — Order, Purpose, and How Each Helps

Kubernetes probes are **health checks** used by **kubelet** to decide:

* **Can container start?**
* **Is container alive?**
* **Is container ready to receive traffic?**

There are **3 probes**:

1. **Startup Probe**
2. **Liveness Probe**
3. **Readiness Probe**

---

# Order of Probe Execution

Kubernetes checks probes in this order:

```text
Container starts
     ↓
Startup Probe (if configured)
     ↓
(once startup succeeds)
Liveness Probe + Readiness Probe start
```

### Important rule

If **startupProbe** exists:

* Kubernetes **disables liveness and readiness** until startup succeeds.

Why?

To prevent killing slow-starting apps.

---

# 1. Startup Probe

## Purpose

Checks:

**"Has application fully started?"**

Used for:

* Slow boot applications
* Spring Boot apps
* Java apps
* Apps needing DB migrations

---

## Why needed?

Without startup probe:

```text
Container starts
App needs 2 minutes to initialize
Liveness probe checks after 30 sec
Probe fails
Kubernetes restarts pod
```

Pod enters:

```text
CrashLoopBackOff
```

---

## How it helps

It gives app **startup grace period**.

Until startup probe succeeds:

* No liveness checks
* No readiness checks
* No restarts due to probe failure

---

## Example

```yaml
startupProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
  failureThreshold: 30
```

---

## Option explanation

### `httpGet`

Kubernetes sends HTTP request:

```text
GET /health on port 8080
```

Success if:

```text
HTTP 200–399
```

---

### `initialDelaySeconds: 10`

Wait 10 sec after container starts before first check.

---

### `periodSeconds: 5`

Check every 5 sec.

---

### `failureThreshold: 30`

Fail only after 30 failures.

Total allowed startup time:

```text
30 × 5 = 150 sec
```

So app gets **2.5 minutes** to start.

---

---

# 2. Liveness Probe

## Purpose

Checks:

**"Is app still alive?"**

Used to detect:

* Deadlock
* Hung application
* Infinite loop
* Memory corruption

---

## How it helps

If liveness fails:

```text
Kubernetes kills container
Container restarted
```

Automatic recovery.

---

## Example

```yaml
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  periodSeconds: 10
  failureThreshold: 3
```

---

## Failure flow

Example:

```text
Probe every 10 sec
Fails 3 times
```

After:

```text
30 sec
```

Kubernetes restarts pod.

---

## Important

Liveness should check:

```text
Is app alive?
```

NOT:

```text
Can app reach database?
```

Bad example:

```text
DB down → liveness fails → pod restarts endlessly
```

Wrong behavior.

---

---

# 3. Readiness Probe

## Purpose

Checks:

**"Can app receive traffic?"**

---

## How it helps

If readiness fails:

```text
Pod stays running
But removed from Service endpoints
```

Traffic stops.

Pod is **not restarted**.

---

## Example

```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  periodSeconds: 5
```

---

## Failure behavior

Example:

Application running, but:

```text
Database connection pool exhausted
```

Readiness fails.

Kubernetes does:

```text
Remove pod from load balancer
```

Users stop hitting bad pod.

Once healthy again:

```text
Add pod back
```

No restart needed.

---

# Key Difference

| Probe         | Main question          | On failure                              |
| ------------- | ---------------------- | --------------------------------------- |
| **Startup**   | Did app start?         | Kill/restart if startup never completes |
| **Liveness**  | Is app alive?          | Restart container                       |
| **Readiness** | Can app serve traffic? | Remove from service only                |

---

# Probe Types (How checks are done)

Each probe can use:

---

## HTTP Probe

Most common.

```yaml
httpGet:
  path: /health
  port: 8080
```

Kubernetes sends HTTP request.

Good for web apps.

---

## TCP Socket Probe

Checks only if port is open.

```yaml
tcpSocket:
  port: 8080
```

Good when no health endpoint exists.

Limitation:

Only checks:

```text
Port open?
```

Not application logic.

---

## Exec Probe

Runs command inside container.

```yaml
exec:
  command:
  - cat
  - /tmp/healthy
```

Success if command exits:

```text
0
```

Useful for custom checks.

---

# Real Example (Best Practice)

```yaml
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  periodSeconds: 10
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  periodSeconds: 5
  failureThreshold: 2

startupProbe:
  httpGet:
    path: /actuator/health
    port: 8080
  periodSeconds: 5
  failureThreshold: 30
```

# Interview Answer (Short)

**What is the order of Kubernetes probes?**

1. **Startup probe runs first**

   * Ensures app has fully started
   * Prevents premature restarts

2. **Readiness probe**

   * Decides whether pod receives traffic
   * Failure removes pod from service

3. **Liveness probe**

   * Detects hung/dead app
   * Failure restarts container

**Startup disables readiness and liveness until it succeeds.**


# Yes — automatically.

That’s one of the main benefits of **readiness probe**.

## How it works

If readiness probe fails:

```text
Pod is still RUNNING
But removed from Service endpoints
```

Meaning:

* Pod **does not get traffic**
* Container **is NOT restarted**
* Kubernetes keeps checking readiness probe

---

## Once pod becomes healthy again

When readiness probe starts succeeding:

```text
Readiness probe → Success
```

Kubernetes automatically:

```text
Adds pod back to Service endpoints
```

Traffic starts flowing to that pod again.

You do **not** need to manually add it back.

---

# Example flow

Suppose you have **3 pods** behind a service:

```text
my-service
   ├── pod-1
   ├── pod-2
   └── pod-3
```

---

### Step 1: pod-2 readiness fails

Maybe:

* DB connection issue
* Cache unavailable
* App warming up

Readiness probe fails:

```text
pod-2 → NotReady
```

Service endpoints become:

```text
my-service
   ├── pod-1
   └── pod-3
```

Traffic skips pod-2.

---

### Step 2: issue resolves

DB reconnects.

Readiness probe starts returning:

```text
HTTP 200
```

---

### Step 3: Kubernetes detects success

Automatically updates endpoints:

```text
my-service
   ├── pod-1
   ├── pod-2   ← back again
   └── pod-3
```

Traffic resumes.

---

# How Kubernetes knows

Run:

```bash
kubectl get pod
```

You may see:

```text
NAME      READY
pod-2     0/1
```

Means readiness failed.

Later:

```text
NAME      READY
pod-2     1/1
```

Means readiness recovered.

---

Check service endpoints:

```bash
kubectl get endpoints my-service
```

You’ll see pod IP disappear and reappear automatically.

---

# Important difference from liveness probe

### Readiness probe failure:

```text
Pod removed from service
No restart
Can come back automatically
```

---

### Liveness probe failure:

```text
Pod restarted
```

Different purpose.

---

# Real-world example

App depends on DB.

DB temporarily down:

```text
/readiness → FAIL
/liveness → PASS
```

Result:

* Pod stays alive
* Removed from traffic
* Waits

DB comes back:

```text
/readiness → PASS
```

Pod automatically added back.

That’s exactly how it should work.

####################################################################################################

## Short answer

**The `Service` adds the Pod back—but it does so automatically based on the Pod’s readiness status.**

More precisely:

**`kubelet → updates Pod Ready condition`
`Endpoints Controller / EndpointSlice Controller → watches that condition`
`Service → routes traffic based on updated endpoints`**

---

# Full flow: who is responsible?

When readiness probe becomes healthy again:

## 1. **Kubelet runs the readiness probe**

Kubelet (running on the node) keeps checking:

```text
/readiness endpoint
```

Example:

```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
```

If probe succeeds:

```text
HTTP 200
```

Kubelet marks Pod:

```text
Ready = True
```

You can see this:

```bash
kubectl describe pod my-pod
```

Output:

```text
Conditions:
  Ready   True
```

---

## 2. **Pod status is updated in API Server**

Kubelet sends update to **Kubernetes API Server**:

```text
Pod condition changed:
Ready=False → Ready=True
```

---

## 3. **Endpoints Controller (or EndpointSlice Controller) detects it**

This is the key component.

It watches:

```text
Pods + Services
```

When it sees:

```text
Pod Ready=True
```

It updates:

```text
Endpoints / EndpointSlices
```

Example:

Before:

```text
my-service endpoints:
10.1.1.5
10.1.1.6
```

After pod becomes ready:

```text
my-service endpoints:
10.1.1.5
10.1.1.6
10.1.1.7   ← added back
```

---

## 4. **Service starts routing traffic again**

The **Service** itself uses those endpoints.

For example:

```yaml
kind: Service
selector:
  app: myapp
```

Service sends traffic only to Pods listed in:

```text
Endpoints / EndpointSlice
```

Once pod IP is re-added → traffic resumes.

---

# Who actually does what?

| Component                                           | Responsibility                                   |
| --------------------------------------------------- | ------------------------------------------------ |
| **Kubelet**                                         | Runs readiness probe and sets `Ready=True/False` |
| **API Server**                                      | Stores updated Pod status                        |
| **Endpoints Controller / EndpointSlice Controller** | Adds/removes Pod IP from Service endpoints       |
| **Service (kube-proxy)**                            | Routes traffic based on current endpoints        |

# Interview-style answer

**Which resource adds the Pod back to the Service after readiness probe passes?**

**Kubelet** marks the Pod as `Ready=True` after the readiness probe succeeds.
Then the **Endpoints Controller (or EndpointSlice Controller)** detects this and updates the **Service endpoints**, which causes the **Service** to automatically route traffic to the Pod again.
